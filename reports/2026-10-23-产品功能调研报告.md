## 二、产品定位梳理

### 2.1 定位演进（三次调整，已收敛）

| 版本 | 表述 | 问题 |
|---|---|---|
| v1.1 | 包管理器与分发层 | 位置已被 skills-manager 占位（54 Agent、两年迭代） |
| v1.2 | 账本与分发层 | 准确但偏描述，不回答"凭什么需要你" |
| **v1.4（现行）** | **Agent 能力治理的控制台** | 形态句（看得见）+ 能力句（不只是分发，还要能被验证）✅ |

### 2.2 四层能力模型（定位的骨架）

| 层 | 内容 | 本期状态 |
|---|---|---|
| 第 1 层 · 装得上 | 安装/分发/多端同步 | ✅ 已实现 |
| 第 2 层 · 数得清 | 跨端清单/漂移告警/版本账本 | ✅ 本期主体 |
| 第 3 层 · 说得清 | 稳定身份/溯源（谁改的） | ✅ 最小版（git 溯源） |
| 第 4 层 · 用得住 | 质量门禁/折旧/健康度 | ✅ 仅**静态分析**部分（运行时评测 = OUT-2，V2） |

**关键口径（对外必须守住）**：折旧是「静下来看」（做满），跑分是「跑起来测」（不做）。"评测回归"本期 = 门禁回归，不得混用。

### 2.3 双读者结构

- **个人侧是产品**：单机 Skill 库、多端分发、版本回滚、溯源 —— 赛后即自用（62 个真实 Skill）。
- **公司侧是生意**：付费主体是**不写 Skill 的决策者**，买的是治理预算（覆盖度/僵尸占比/健康度分布/成员贡献）。
- 实现约束已落定：管理者视图与个人总览**同一页面两种读法**（FR-2.1.1），不做两套 UI。

### 2.4 三级演进与商业出口

| 层级 | 形态 | 主要读者 | 现状 |
|---|---|---|---|
| L1 个人 | 单机库 + 多端分发 + 回滚溯源 | 写 Skill 的人 | ✅ 本期做满 |
| L2 团队 | 共享库 + 变更审查 + 管理者视图 | 决策者 | ✅ 部分（协作模块最小版） |
| L3 企业 | 准入 + 安全扫描 + 审计 + 交付 | 治理与合规 | 仅叙事（企业功能 08 §8 硬边界：一个都不做） |

### 2.5 硬边界（不做清单摘要）

OUT-1 协同编辑 / OUT-2 运行时跑分 / OUT-3 Marketplace / OUT-4 编排 / OUT-5 知识图谱 / OUT-6 移动端 / OUT-11 块内合并 / OUT-13 大资产承载 / OUT-14 通用命令透传 / OUT-16 窄克隆 / OUT-17 对象级合并。另有 08 §8 企业功能硬边界（SSO/RBAC/多租户/私有部署）。**这些是"想清楚后的不做"，新增功能建议不得与它们隐性冲突。**

## 四、需要细化的功能（缺口清单）

> 判定标准：需求已立项，但**规则/口径/交互细节未定义到"可直接写测试用例"的程度**。按风险排序。

| # | 功能 | 现状 | 缺口 | 细化建议 | 优先级 |
|---|---|---|---|---|---|
| G-01 | **健康度合成公式**（FR-1.0.24） | "门禁结果 + 折旧三维合成 0-100 分" | 权重、映射函数、error/warn 各扣多少分均未定义 → 同一 Skill 两次算分可能不一致，"可下钻"变成"可下钻但看不懂" | 在 `04` 补一节：分值 = 100 − Σ(规则扣分)，error/warn/info 定档（如 20/5/1，估算），折旧三维各占权重并给出 unknown 时的处理（建议 unknown 不扣分但标灰） | 高 |
| G-02 | **折旧三维判定口径**（FR-1.0.23） | staleness 依赖"被引用次数"，依赖失效依赖"声明的依赖与正文引用" | ① "被引用"怎么统计（跨 Skill 引用？Skill 内脚本引用？没定义）② staleness 的过期阈值（30 天？90 天？）③ 依赖声明格式（frontmatter 字段名未定） | 定义引用来源 = frontmatter `dependencies` 字段 + 正文相对路径引用两处；阈值给默认值并允许 Settings 配置 | 高 |
| G-03 | **门禁规则清单**（FR-1.0.11 → `04` §2.1.4） | 三级分级框架已有 | 规则数量、每条规则的判定逻辑、是否允许用户自定义规则集，均需对照 `04` 逐条验收；规则集**不可扩展**会让"治理"叙事停在 6 条内置规则 | ① 逐条核对内置规则实现；② V2 候选：自定义规则（YAML 声明式，不做插件运行时） | 高 |
| G-04 | **相似/重复检测**（FR-1.0.12，P3，砍单序靠后） | 只有需求名 | 算法未定（frontmatter 相似？正文 shingle？目录结构指纹？）、相似阈值未定、结果如何呈现（合并建议？仅提示？） | 最小版：description + 名称的归一化编辑距离，阈值 0.85（估算），只在 Dashboard 出"疑似重复"列表，不自动合并 | 中 |
| G-05 | **Change Request 流程**（FR-2.3.3） | 最小版：提交/评论/审查/合并 | 缺：CR 与门禁的关系（CR 合并前是否强制 check？建议强制 error 级）、CR 被拒后的状态流转、通知机制（无通知 = 审查流形同虚设） | CR 状态机补一版（draft → review → approved/rejected → merged），合并前置门禁复用同一判定（对齐 NFR-10.5 单一实现） | 中 |
| G-06 | **沙盒演示数据与重置**（FR-2.4.3 / FR-3.10） | 可写隔离 + 一键重置已定 | "预置演示数据"的剧本化程度：评委改坏 → 回滚的演示链路是否有 seed 脚本保障每次重置后状态一致 | seed 脚本纳入沙盒入口（`sandbox/entrypoint-sandbox.sh`）并在重置后自证数据就位 | 中 |
| G-07 | **新建 Skill 入口**（FR-2.1.7，P3） | 只有"入口"两个字 | 从模板新建？字段默认值？建完是否自动纳管？ | 最小版：从内置模板（3 个，估算）生成 frontmatter 骨架 → 直接进 canonical 仓库并 commit（走既有溯源） | 低 |
| G-08 | **上游跟踪**（FR-1.0.13，P7） | 需求已在，依赖 upstream_sources 表 | 更新检测的周期（手动/daemon 定时？）、`upstream_divergence` 折旧维度的触发条件未细化 | daemon 定时（每日，估算）+ 手动刷新两档；分叉判定复用漂移 7 态的 MODIFIED 语义 | 低 |

**小结**：G-01~G-03 是「第 4 层 · 用得住」叙事的承重墙 —— 治理故事讲得再好，健康度算不清、门禁规则说不全，评审一问就穿。建议赛后第一优先补这三个口径（改 `04`，不动 `00` 编号）。

## 五、建议新增的功能（候选池）

> 全部为**候选**，落地前须在 `00` 立新 FR 编号。已按 Kano 分类 + RICE 粗评（Reach/Impact 为估算，Confidence 标注依据）。

### 5.1 短期（赛后 1 个月内，服务"长期自用"）

| # | 功能 | 描述 | Kano | RICE（估） | 建议 |
|---|---|---|---|---|---|
| N-01 | **Skill 使用遥测（本地）** | 记录每个 Skill 被 Agent 实际调用/读取的次数（可从 MCP 调用日志 + Runtime 目录访问时间近似），喂给"僵尸 Skill 占比" | 期望型 | (62×3×0.8)÷2 ≈ **74** | **首推**。管理者视图最大的软肋是"僵尸占比"只能靠 staleness 推断；有了实测调用数，L2/L3 的核心指标从"猜"变"测"，且实现集中在 daemon 日志聚合，成本低 |
| N-02 | **定时体检报告** | daemon 每日/每周汇总：新增漂移、门禁失败、折旧恶化 Top N，CLI 输出 + Web 通知中心 | 期望型 | (62×2×0.8)÷1.5 ≈ 66 | 推荐。"静下来看"的资产需要有人推给你看，否则漂移矩阵变成被动查询 |
| N-03 | **门禁规则自定义**（G-03 的产品化） | YAML 声明式规则（正则/文件存在性/frontmatter 字段校验），存仓库随 git 版本化 | 兴奋型 | (40×2×0.5)÷3 ≈ 13 | 缓。"声明式 + 进仓库"与现有元数据版本化（FR-1.0.30）同构，但规则引擎是新增执行面，先做 3~5 个高频规则验证需求 |

| # | 功能 | 对应 OUT | 解冻条件 | 建议 |

### 5.3 远期（L3 企业叙事兑现，08 §8 硬边界解冻前提）

| # | 功能 | 说明 |
|---|---|---|
| N-08 | **Skill 安全扫描** | 密钥/token 泄露检测、危险命令模式识别 —— 08 §4 已写"公司多一层：合规吗 + 有没有泄露密钥"，但无对应 FR。这是 L3 准入的第一块砖，且技术上是门禁规则集的超集（可先以 N-03 的自定义规则形态预研） |

```
先补口径（G-01~G-03，改文档不改代码） → N-01 遥测（僵尸判定实测化）
→ N-02 体检报告 → N-03 规则自定义试点 → 视真实需求解冻 N-04/N-05
```

## 七、结论

1. **定位已收敛且自洽**：从"包管理器"三次调整到"治理控制台"，差异化卡位（质量与治理）经竞品验证成立，四层能力模型本期做满 1~3 层 + 第 4 层静态部分。
2. **功能骨架完整，短板在"口径"而非"数量"**：健康度公式、折旧判定、门禁规则清单三处（G-01~03）是当前最需要细化的地方 —— 它们直接承托产品最核心的差异化叙事。
3. **最值得加的一个功能是 N-01 使用遥测**：让"僵尸 Skill 占比"从推断变实测，是 L2 管理者视图从"能看"到"可信"的关键一跳，成本可控。
4. **流程提醒**：本报告所有新增建议（N-01~N-10）与细化建议（G-01~G-08）均未改动基线；采纳任意一项，第一步是在 `docs/00-需求定稿.md` 立新编号，再同步 `04`。
