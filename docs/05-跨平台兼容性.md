## 0. 一句话结论

**风险存在但可控。真正的坑不是"跑不起来"，而是三类：**

1. **同一份 skill 在不同平台算出的哈希 / git 状态不一致** —— 会让核心功能（漂移检测）**持续误报**，比崩溃更难查。
2. **中文 + Windows 控制台编码** —— 你的 62 个 skill 描述全是中文，CLI 一输出就崩。
3. **静默发生的"成功"** —— 三类最坏形态，全部来自 `07` 的真实事故：**迁移失败后应用静默退出**（没有界面也没有日志）、**符号链接静默退化为全量复制**（占满磁盘）、**路径写错但报同步成功**（Agent 里什么都没有）。它们的共同点是**看起来一切正常**。

崩溃是好事（立刻发现），**持续误报与静默成功才是地狱**。所以下面 P0 项无一可省。

## 2. P0 清单

### P0-1 git 换行策略：两层口径必须一致

**症状**：Windows 的 git 默认 `core.autocrlf=true`，checkout 时把 LF 换成 CRLF。

**我们的哈希口径是字节级的（`FR-1.0.5`，v1.3 修正为两级结构）** —— `hash_bytes` **不做任何归一化**，字节不同就是不同。这带来一个**必须同时满足**的要求：**git 也不能做任何换行转换**。否则：

- 工作区字节（CRLF）≠ 索引字节（LF）→ `git status` **永远显示文件被改过**
- `git diff` 整篇标红
- 回滚 / 提交历史被无意义的换行变更污染
- 更糟的是：同一份逻辑内容在 Windows（CRLF）与 Linux（LF）上**算出两个不同 hash** → 双端"永远可更新"，**互相来回推送**（上游 `1.39.0` 的真实事故，`07` D6）

> **v1.3 修正（重要）**：早先这里写的是"哈希口径做了归一化（`\r\n` → `\n`），但 git 没做，两边不一致"。**现在两边都统一到"字节"这一侧** ——
>
> - `hash_bytes`：字节级，**不归一化**（存储身份）
> - 行尾差异由**独立的第二级比较**（`compare_normalized_line_endings`）解释，**只在字节 hash 已不等时调用**，仅作提示、不进存储身份
> - git：`.gitattributes` 的 `* -text` 让**检出字节跨平台一致**
>
> 三者合起来才是自洽的。**"归一化进哈希"的旧写法已废除**（依据 `07` D6：归一化进哈希会稀释"不可读文件 / 非法 UTF-8 按字节严格比较"的严格性，且任何口径调整都要重算全部已存 hash 并迁移）。

**更隐蔽的一点**：SkillOS 用 subprocess 调 git，**用户的全局 git config 会直接影响行为**。依赖它 = 依赖用户环境。

**对策**：

1. repo 根放 `.gitattributes`：
   ```
   * -text
   ```
   完全禁用换行转换 —— 任何平台检出**字节一致**。这比 `text=auto eol=lf` 更彻底。
2. **所有 git 调用显式传参**，不继承用户配置：
   ```bash
   git -c core.autocrlf=false -c core.safecrlf=false -c core.quotepath=false <cmd>
   ```
   `quotepath=false` 让中文文件名正常显示（否则是 `\344\270\255` 八进制乱码）。
3. 写文件统一 LF：Monaco 保存、frontmatter 写回、导入 skill 时的内容规范化，全部 `\n`。

**落点**：`core/vcs`（git 封装）+ `core/fs`（写文件）

### P0-2 中文 Windows 控制台编码

**症状**：中文 Windows 控制台默认 **cp936**。Python 打印中文时抛：

```
UnicodeEncodeError: 'gbk' codec can't encode character '\u2026'
```

你的 skill 名和描述**全是中文** —— 这条必踩，且是 `skillos scan` 第一次跑就会遇到的。

**对策**：

1. CLI 入口强制 UTF-8：
   ```python
   for s in (sys.stdout, sys.stderr):
       s.reconfigure(encoding="utf-8", errors="replace")
   ```
2. 打包 / 分发时确保 `PYTHONUTF8=1`（用 Typer 的 entry point 处理）。
3. 输出表格宽度计算按**显示宽度**（中文占 2 列），别用 `len()` —— 否则列会错位。Rich 已处理，自己写格式化时要注意。

**落点**：`cli` 层入口

### P0-3 跨平台文件锁

**症状**：`fcntl.flock` 是 **Unix-only**，Windows 上 `import fcntl` 直接崩；`msvcrt.locking` 又只 Windows 能用。

**对策**：统一用 **`filelock`**（纯 Python、跨平台、支持超时、无 C 扩展）。

- 锁文件 `~/.skillos/.lock`（设计已有）
- 禁用 `fcntl` / `msvcrt` 直接调用
- 加超时（如 30s）并明确超时行为：**报错退出，不静默跳过**
- **锁文件不得放在会被克隆 / 整体替换的目录内** —— 上游 `1.17.0`：Windows 上克隆远端仓库因仓库锁阻塞失败，**克隆目标必须保持空目录**

**P0-3b 持锁期间禁止 `fsync`（`07` D5 / M4）**

**症状**：macOS 上 `fsync` 一个文件会**刷新整个卷的缓存**，把其中所有脏页（**包括其他进程的**）都算到本应用头上。上游 `1.40.0` 实测：每次获取中央仓库锁都 `fsync` 锁标记文件，约 75 个技能的库每轮 75 次全卷屏障，持续一小时被系统记为 **2.1 GB 的 "file backed memory dirtied"，超出磁盘写入上限 24 倍**。

而那个锁标记文件的用途只是"在『仓库忙』提示里说明是谁占着锁"—— **互斥来自 `flock`，与文件内容无关**。

**对策**：

1. **锁标记文件写内容后不 `fsync`**：内容只用于提示，丢了不影响正确性。
2. **持锁期间不得做**：`fsync` / 全量目录 `rename` / 更新目录 `mtime`。
3. **网络 I/O 永不在锁内**：上游 `#315` 的整个 `git ls-remote` 往返持锁 → 用户操作等满 20 秒后直接失败报 `repository is busy`；改成两段式（锁外并发解析 → 锁内只写状态列）后**锁从 30 秒降到毫秒级**。
4. 实现为**可检查的约束**：`with lock:` 块内不得出现网络调用、`fsync`、目录整体 rename（单测用 mock 断言持锁期间未被调用）。
5. **前后台语义分级**（`06` A6）：后台任务（daemon 批量 push）可能持锁 10–15s，**前台交互必须等待而不是立即失败** —— 等待上限 20s，超时才报 `BUSY`。上游"前台等 20s"的取值即来自此：立即失败会把"后台正在批量分发"变成"你现在什么都干不了"。
6. **抢锁不得按异常类型分支**（`06` A6）：Windows 的 `LockFileEx` 冲突返回 **`ERROR_LOCK_VIOLATION`，不会映射成 `WouldBlock`** —— 写成 `except WouldBlock: retry` 会在 Windows 上**直接抛出**，且**只在并发时复现**（单人开发最难撞见）。规则：抢锁循环**不对异常类型做分支**，统一退避重试直到超时。
7. **锁诊断 stamp**（`06` B7）：锁文件旁记录 `pid` / `hostname` / `operation` / `start_time`，抢占失败时一并报给用户（`FR-2.4.9`）—— 让 `repository is busy` 可追责到具体操作，而不是让用户干等 30 秒凭空猜。**该 stamp 写内容后不 fsync**（与第 1 条同源）。

**落点**：`core`（daemon 任务串行写锁）+ `core/fs`

### P0-7 git 仓库格式与初始分支

**症状**：git 2.48+ 支持 `reftable` 引用格式，**如果 git 默认创建 reftable 仓库，我们的库会以旧工具读不了的格式建出来** —— 上游 `1.40.3` 的后果是：每次同步都失败，`HEAD` 指向 `refs/heads/.invalid`，**仓库看起来像坏了**（`#504`）。

另一面：**CI runner 通常没有全局 `init.defaultBranch`**，导致克隆出的仓库停在**未诞生分支**上（unborn branch），测试在开发机以外必然失败。

**对策**：

1. `skillos init` 必须**显式指定**，不吃任何用户全局配置：
   ```bash
   git init -b main --ref-format=files
   ```
2. 已在用 reftable 的库给出**明确提示与转换命令**（需 Git 2.48+），不静默失败。
3. **所有测试里建裸仓库都要 `init -b main`**。
4. 首次 push 到远端**必须 `push -u` 建跟踪**：上游 `1.22.5` —— `no_upstream` 状态下 `ahead` 恒为 0，首次推送到空远程的条件判断被完全跳过，只本地提交、远程一直空，**UI 却显示"已同步"**。
5. **ref 解析按完整 ref 名精确匹配**，优先级：分支 → annotated tag 的 peeled commit → tag 对象（上游 `1.36.2`：取 `ls-remote` 第一行会拿到 annotated tag 的对象 sha，导致每次检查都误报有更新）。

**落点**：`core/version.py`（`init` / `resolve_ref`）+ 测试夹具

### P0-8 路径比较与"不做路径整理"

**症状 A —— 同一目录被当成两个**：`C:\Users\x\.claude` 与 `c:\users\x\.claude`、8.3 短名 `PROGRA~1`、经软链接的等价路径 —— 字符串不同但**是同一个目录**。

上游 `1.40.1` 的真实事故：迁移完成后，仅大小写 / 8.3 / 软链接不同的同一目录被误判为"需要迁移"→ 此后每次启动都提示，**永久循环**（`#449`/`#469`/`#393`）。

**症状 B —— "顺手美化"引入校验绕过**：Unix 上**结尾空格与反斜杠都是合法的目录名字符**。若 `sanitize_filename` 顺手把它们修剪掉，路径会**缩到隔壁目录**，而这个改写后的路径**能通过校验** —— 调用方读的是检出里根本没有的那个路径（上游 `1.38.0`）。

**对策**：

1. **路径比较一律先 `canonicalize`**（`Path.resolve()` / `os.path.realpath`），比较的是解析后的形态。
2. **`sanitize_filename` 只做必须做的校验**，明确列白名单：拒绝 Windows 非法字符与保留名、拒绝大小写冲突 —— **但绝不修剪、绝不改写、绝不"整理"**。
3. **迁移只在空目标上进行**，且**残留物（锁文件、空文件夹、系统元数据）不得阻挡迁移**。
4. **运行时切换 repo 路径必须要求重启**：上游 `1.40.1` —— 运行中的应用立刻切到新路径，此后写入的第一样东西（锁文件、安装的技能）落进新文件夹；下次启动的迁移只接受空文件夹 → 此后每次启动都拒绝迁移，设置页一直显示旧路径。跨磁盘迁移时旧副本改名 `<名称>.moved-<时间>` 保留。
5. **路径显示层统一**：存储用 `/`，显示时才按平台转 —— 上游 `1.40.2` 出现过 `~\.workbuddy/skills` 这种混合分隔符，且 `compactHomePath` 有两份实现。

**落点**：`core/fs`（`safe_path` / `sanitize_filename`）+ 启动迁移

### P0-9 迁移与启动期异常不得静默

**症状**：上游最惨的一类事故是"**应用打不开、没有界面、也没有日志**"。链路是：未完成的迁移在目标留下只读 Git pack 文件 → 下次启动覆盖时报 `os error 5` → 而这一步在**建窗口和 logger 之前**执行 → **静默退出**（`1.28.3` `#252`）。

同类：`explorer.exe` 因非零退出码被误报为错误 —— 实际是正常行为。

**对策**：

| # | 措施 |
|---|---|
| 1 | 迁移只在**空目标**上进行（同 P0-8） |
| 2 | 迁移失败**返回决策而非抛错**，绝不经过启动早期的 `.expect` / `assert` |
| 3 | 失败时用运行时 override **回退到完好源库**，保证进程能起来 |
| 4 | **错误延迟到 logger 就绪后再落盘** —— pre-logger 的日志调用是**空操作** |
| 5 | **"非零退出码 ≠ 失败"**：调用外部命令时不要只看 `returncode`，要看实际语义（上游 `W6`） |
| 6 | **只杀自己 spawn 的进程**：Linux 上用进程组要极其小心，上游曾误杀其他应用甚至**整个桌面会话**（`M6`） |
| 7 | Windows 会**短暂锁住刚运行过的程序** —— 若 daemon 要自更新或复制 `skillos.exe`，必须**等锁释放后重试**（上游 `1.40.3` `#487`："文件正被另一个进程使用"） |

**落点**：daemon 启动路径 + `core/fs` 迁移

### P0-10 CI 必须一开始就三平台矩阵

**症状**：上游的教训是"**Linux 只在发版 workflow 中编译**"，于是**依赖库的平台差异拖到发版才暴露**（`keyring` 的 vendored libdbus 只在 Linux 编译失败，`1.26.0`）；另一条是"本次均为前端改动，而**仓库没有前端测试框架，`test.yml` 也不覆盖 `src/`**"（`N28`）。

**对策**：

1. **CI 从第一天起就矩阵化 `windows-latest` + `ubuntu-latest`**，哪怕只跑 `--help`、`import` 和 `core` 纯函数单测。
2. **macOS 列**：不常驻（Actions runner 单价高），但**至少每月 / 发版前手动跑一次**；设计意图保留在 §5.1 矩阵里。
3. **前端（vitest）从 P3 起必须进 CI** —— 我们的编辑器 / diff / 冲突解决全在前端，"发版才编译"的代价在 12 天里承受不起。
4. 这是**单人开发 + 时间紧**下最便宜的保险：一次平台差异的暴露成本，远低于发版时才发现。

**落点**：`.github/workflows/test.yml`

### P0-4 路径大小写与非法字符

**症状 A —— 大小写**：
Windows 与 macOS 默认**大小写不敏感**（APFS 默认 case-insensitive），Linux **敏感**。

| 文件名 | Windows / macOS | Linux |
|---|---|---|
| `SKILL.md` vs `skill.md` | **同一个文件** | 两个不同文件 |

后果：`struct.skill_md` 检查、跨端漂移比对在 Linux 上可能给出不同结论；两个仅大小写不同的 skill 在 Win/Mac 上会**互相覆盖**。

**症状 B —— 非法字符**：

| 平台 | 禁止 |
|---|---|
| Windows | `< > : " / \ | ? *`、结尾的 `.` 和空格、保留名 `CON PRN AUX NUL COM1-9 LPT1-9` |
| macOS | `:` 和 `/` |

skill 包名一般是 kebab-case slug，风险低；但 **`assets/` 里的文件是自由命名**（截图、导出物、模板），跨端分发会失败。

**症状 C —— Unicode 归一化（`06` A7）**：

同一串中文 / 组合字符可能存在**两种合法的 Unicode 编码**（`é` = `U+00E9` 或 `e + U+0301`；全角与半角；韩文音节组合）。**macOS（APFS 默认）在写入时会把文件名做 NFD 规范化**，Windows / Linux 则保留原样。结果：

- 同一份 Skill 在 macOS 上写出去、在 Windows 上读回来，**文件名看起来一样、字节不同** → 被当成两个不同的 Skill；
- **仅比较大小写的冲突检测完全漏掉这一类** —— 而我们本机 62 个 Skill 全是中文名，这不是边角场景。

**对策**：

1. SkillOS 自己创建的路径一律 **kebab-case + 小写 + ASCII**。
2. 导入时校验**路径冲突**（仅大小写不同、**或仅 NFC 归一化形式不同**的同名 skill）→ 报 `NAME_COLLISION`，**不自动改名**。
3. 写入前统一走 **`safe_path()`**（`04` §2.2.0）：命中非法字符或 Windows 保留名 → 报 `INVALID_PATH`；解析后越出 root → 报 `PATH_TRAVERSAL`。两种情况都**列出冲突文件、不静默改名**（静默改名会让 hash 与用户认知都对不上）。
4. 判定"两个路径是否同一个"必须走统一 **`path_key()`**：按分隔符**分段**，逐段 `unicodedata.normalize("NFC", part)` + `str.casefold()`，再校验唯一性（`FR-1.0.31`，实现见 `04` §2.2.0 第 10 条）。**`path_key` 只用于比较**，不得替换用户可见的真实路径。
5. 质量检查加两条规则：`path.illegal_char`（warn）、`path.case_collision`（error）。**`path.case_collision` 必须同时覆盖大小写与 NFC 两类冲突** —— 只查大小写等于漏一半。

**落点**：`core/fs`（`sanitize_filename` / `path_key`）+ `checks.py`

### P0-5 repo 不得放在云同步目录里

**症状**：OneDrive / iCloud Drive / Dropbox 会把文件变成**按需下载占位符**（dataless file）：

- `stat()` 大小可能为 0，读取时才触发下载
- 后台持续改 mtime，与 git / 哈希竞争
- 文件被锁住，rename / delete 失败

另外 Windows Defender 与搜索索引服务会**短暂锁住刚写入的文件**，导致原子写的 rename 步骤随机失败。

**对策**：

1. 默认位置 `~/.skillos/repo`（家目录通常不被 OneDrive 接管）。
2. 启动时检测配置路径是否落在 OneDrive / iCloud / Dropbox 根内 → **警告 + 要求显式确认**（`--allow-unsynced-repo` 或配置 `allow_unsynced_repo = true`），**不直接拒绝启动**。
   > 命名注意：这个开关**不要叫 `--force`** —— `force` 在本项目里已被「冲突策略」占用（`on_conflict: abort|skip|force`）。两个"强制"含义完全不同，同名会在 CLI 与 API 之间制造误解。
   理由：过严的拦截会在演示现场把自己锁死；且 `~/.skillos` 位于**家目录根**，OneDrive **默认不接管**（只有用户手动开启"备份桌面/文档/图片"时才接管对应子目录），误触发概率本就很低。
3. 写入重试：捕获 `PermissionError` / `OSError` → 指数退避重试 3 次（50 / 150 / 400 ms），仍失败才报错。

**落点**：启动检查 + `core/fs`

---

### P0-6 WSL 文件系统边界

**症状**：Windows 上用 WSL 开发时，最容易犯的错是把 daemon 装在 WSL 里。

- daemon 在 WSL → 它操作的是 WSL 命名空间下的 `/home/x/.claude/skills`（ext4）
- Agent Runtime 在 Windows → 读的是 `C:\Users\x\.claude\skills`（NTFS）
- **这是两个完全不同的目录**

结果：`skillos push` 报成功，drift 显示 `SYNCED`，**但 Windows 侧的 Claude Code 完全看不到变化**。演示现场这是致命的——因为看起来"一切正常"。

**对策**：

| 部署方式 | 是否支持 |
|---|---|
| daemon 与 Runtime 全在 Windows | ✅ |
| daemon 与 Runtime 全在 WSL | ✅ |
| **daemon 在 WSL，Runtime 在 Windows** | ❌ **明确不支持**，启动即拒绝 |

判定方式：比较 daemon 进程可见的 Runtime 根路径与配置值是否同源（`/mnt/c/...` 前缀视为跨命名空间）。

**落点**：daemon 启动校验 + `doctor` 检查项 6（`04` §2.5.1）

---

### P0-11 Python 运行产物污染漂移判定（`06` A3）

**症状**：Skill 里常带 Python 脚本（本机就有 `scripts/` 目录）。脚本一运行就生成 `__pycache__/*.pyc`。若哈希枚举不排除它们：

- 每次使用该 Skill 后，**部署副本永久显示"已变更"** —— 漂移矩阵长期飘红，用户很快不再相信它；
- 本机现状已能扫出 **54 个 `.pyc`**，这不是假设。

**对策**：

1. `list_content_files()` 的**第一类排除集（影响 hash）必须含** `__pycache__/` 与 `*.pyc`；同类还需含 `.git/` / `.DS_Store` / `Thumbs.db` / `.gitignore` / `.skillos/`（`04` §2.1.3）。
2. **排除必须发生在哈希之前**，而不是"算完再过滤" —— 后者会让 `pack_hash` 随文件出现与否变化。
3. 单测断言：**运行 Skill 内的 py 脚本后 `pack_hash` 不变**。

> 上游把这条写成了实锤缺陷。我们提前纳入，成本只是一条排除规则。

**落点**：`core/algorithm`（`list_content_files()`）+ 单测

## 3. P1 清单

### P1-1 `localhost` 会解析成 IPv6

**症状**：Windows 上 `localhost` 优先解析为 `::1`。若后端只 bind `127.0.0.1:9080`，前端 / daemon 连 `http://localhost:9080` 会 `ECONNREFUSED`（Node 17+ 已改为 IPv6 优先，所以这个问题会被放大）。

**对策**：**全链路统一 `127.0.0.1`，禁止 `localhost`** —— 前端 `baseURL`、daemon 连接、健康检查、`npm run gen:api` 的目标 URL 全部替换。

**落点**：`web` + `daemon` + 脚本

---

### P1-2 符号链接权限 → 降级为目录联接（junction）

**症状**：Windows 创建 symlink 需要**管理员权限或开发者模式**；`mklink /J`（junction）不需要但**只支持目录**，且 path 必须是绝对路径。

上游 `1.23.1` 的真实后果（`#126` / `#38`）：symlink 创建失败时**静默退化为全量复制**，大体积 skill 迅速占满磁盘。

**对策**：

1. 这印证同步形态的决策 —— **拷贝为默认模式**；软链仅作可选模式。
2. Windows 上先探测权限：不足则**降级为目录联接 junction**（本地 NTFS 卷不需任何特权），全量复制**仅作最后兜底**（如 WSL 的 `\\wsl.localhost\...`，用户态无法建链接）。
3. **已知限制要处理**：上游明确写了"**已退化为复制的目标不会自动转换**，需要显式重新同步"。→ 我们的 `push` 要能**发现并修复历史退化**（目标形态与期望形态不符时提示"可原地转为链接"），而不是默默继续复制。

**落点**：`services/sync`（同步形态）+ `core/fs`

---

### P1-6 长路径 > 260

**症状**：`~/.skillos/repo/<cat>/<skill>/references/*` 一般够用，但**嵌套子 skill**（如 `test-automation/subskills/<name>/`）会加深。

**对策**：Windows 上 Python 3.6+ 需系统启用长路径支持（`LongPathsEnabled`），或在路径前加 `\\?\` 前缀；安装文档里提示开启。

> **一条通用的教训**（上游 `1.28.3` `#298`/`#299`）：他们通过 `build.rs` 嵌入应用清单声明长路径感知，踩到的坑是"**`app_manifest()` 会替换默认清单，因此必须重新声明 Common-Controls v6 依赖**"。
>
> 通用化为：**改任何全局配置都要检查副作用** —— 我们改 `pyproject.toml` / CI 配置 / 打包清单时同理。

**落点**：`core/fs` + 安装文档

---

### P1-7 语言与编码的前缀匹配陷阱

**症状**：上游 `1.35.0` 的实例 —— `startsWith("zh")` 会连 **`zha`（壮语）** 一起匹配，`startsWith("en")` 会匹配 **`enm`（中古英语）**；一旦匹配就**吞掉该项、丢弃列表中的下一项**，而后者才是用户真正偏好的语言。

另一个：**首次启动硬编码简体中文** → 不读中文的用户必须先在一个自己看不懂的界面里找到"设置 → 语言"（`#374`）。

**对策**：

1. **语言 / 编码 / 协议名一律按主语言子标签精确匹配**（`zh-Hans` / `zh-Hant` / `en`），**禁止 `startsWith` / 前缀匹配**。
2. 语言策略遵循 `06` 的既有决定；缺翻译时**回落英文，繁体除外（回落简体）**。
3. **首次启动的语言从系统推导，不硬编码。**

**落点**：`web` i18n / `cli` 输出

---

### P1-8 测试与校验要打在"真正被消费的产物"上

**症状**：上游 `1.30.0` 的教训 —— 更新断言的正确对象是 **`.app.tar.gz`**，而不是 `.app` / `.dmg`："用户更新时被解包覆盖到运行中安装位置的**正是这个归档**"。同类：**不在挂载的 `.dmg` 里或 macOS 隔离沙箱副本中做应用内更新** —— 替换后的应用会被写到随后即被丢弃的位置；正确做法是**提前识别并提示，而不是下载完才失败**。

**两条通用纪律**：

1. **测试 / 校验要打在真正被消费的那个产物上**（我们的场景：断言"分发到磁盘后的字节"，而不是断言"渲染函数的返回值"）。
2. **环境不支持的能力要在入口就拒绝**，不要跑到最后才失败。

**落点**：测试规范 + `cli` 入口检查

---

### P1-9 断言"结果"而不是"配置"

**症状**：上游 `1.38.0` 做窄克隆时的做法值得直接抄 —— 他们用真实的 `file://` partial clone **断言结果**，"**而不是断言设置的名字**"。

**对策（写进我们的测试规范）**：

| 反例（断言配置） | 正例（断言结果） |
|---|---|
| 断言 `.gitattributes` 里写了 `* -text` | 断言**同一份内容在 CRLF / LF 两种输入下 `hash_bytes` 结果符合预期**，且 `git status` 干净 |
| 断言调用了 `init(branch="main")` | 断言**建出来的仓库 HEAD 指向 `refs/heads/main`** |
| 断言传了 `--allow-unsynced-repo` | 断言**检测函数对 OneDrive 路径返回了警告** |

> 这条对 `07` N27 的"变异验证"是互补的：**变异验证保证测试能失败，断言结果保证测试失败在正确的位置。** 上游的经验是"两条既有测试原本是**靠这个 bug 才通过的**"（各自伪造一个够老的 `updated_at` 来冒充"年龄"）—— 测试因为假造条件而通过，与我们做漂移 / 共享库测试时的风险完全同源。

**落点**：测试规范

---

### P1-3 skill 内的可执行脚本

**症状**：POSIX 的 exec bit 在 Windows 上不存在；git `core.fileMode` 在 Windows 默认 `false`，exec bit 检出不保留。`#!/usr/bin/env python3` shebang 在 Windows 上不生效；`scripts/*.sh` 需要 Git Bash 或 WSL。

**对策**：

1. repo 层不依赖 exec bit。
2. **约定**：skill 里的脚本一律用显式解释器调用（`python scripts/x.py`），不依赖 shebang —— 写进 Skill 编写规范。
3. 后续可提供 `skillos run <skill>:<script>` 包装抹平差异（**本期不做**，记入后续）。

**落点**：约定 + 文档

---

### P1-4 daemon 服务化与退出

**症状**：Windows 无 SIGTERM / SIGHUP 语义；常驻方式与 macOS 完全不同（`launchd` plist vs 任务计划程序 / NSSM）。信号退出在 Windows 上不可靠。

**对策**：

1. **退出统一走 IPC**（发 `{"op":"shutdown"}`），不依赖信号。
2. 服务化**本期不做** —— P2 只要求手动 `skillos daemon` 前台运行（演示时终端挂着）。开机自启写成**文档**（Windows 用任务计划程序 / macOS 用 `launchd`），不写代码。

**落点**：`daemon`

---

### P1-5 凭据存储

**症状**：`keyring` 库可跨平台（Windows Credential Manager / macOS Keychain），但**无桌面会话 / 无后端时不可用**（如纯 SSH、CI）。

**对策**：保持已有设计（NFR-2）—— 优先 `keyring`，失败回退到 **0600 权限文件**。

**Windows 特别注意**：`chmod` 在 Windows 上几乎无效，回退方案不能只靠 chmod，要显式设 ACL（或用 `icacls`）。本期可先只做 0600 文件 + 文档明确告知，ACL 加固记入后续。

**落点**：`daemon`

## 5. 架构级风险：开发环境 ≠ 运行环境

| 环境 | 平台 | 关键特性 |
|---|---|---|
| **你的开发机** | Windows | 大小写不敏感、CRLF 风险、cp936 控制台 |
| **云端后端** | Linux 容器 | 大小写敏感、LF |
| **沙盒 runtime** | Linux 容器 | 同上，且为虚拟目录 |

**推论：沙盒里测不出 Windows 的坑。** 编码、大小写、路径、锁、非法字符在容器里全都不复现。所以：

1. **单元测试放跨平台夹具** —— CRLF 输入、`CON` / `a:b` 之类非法名、大小写冲突对，用 `core` 纯函数覆盖（这也正是 NFR-8「core 可不依赖文件系统做单测」的用处）。
2. **CI 跑双平台矩阵**（GitHub Actions：`windows-latest` + `ubuntu-latest`），只跑 `core` 单测 + CLI 冒烟，不跑 daemon / 前端。
3. **演示前在本机 Windows 真实数据上跑一遍** —— 这正是 NFR-6 的要求。
4. **WSL 是第四种环境，且最容易被忽略** —— 见 P0-6。若你习惯在 WSL 里跑 Python，务必先确认 daemon 与 Runtime 处于同一命名空间，否则会出现"同步成功但 Agent 看不到"。

### 5.1 跨平台测试矩阵（可执行规格）

含义：**该用例在目标平台上的期望结果**。

- ✅ = 必须通过，且结果与其它平台一致
- ⚠️ = 平台行为不同但可用，**断言的是"降级行为"**，不是"结果一致"
- ❌ = 明确不支持，**断言的是"拒绝"**，不能静默改写
- — = 该平台不适用

| 用例 | Windows | Linux | macOS |
|---|---:|---:|---:|
| LF → LF（字节不变） | ✅ | ✅ | ✅ |
| CRLF vs LF（字节 hash **必须不等**；第二级比较须识别为"仅行尾差异"） | ✅ | ✅ | ✅ |
| `__pycache__` / `node_modules` 排除（跑一次脚本后不得显示"已变更"） | ✅ | ✅ | ✅ |
| 中文文件名 / 中文内容输出 | ✅ | ✅ | ✅ |
| 保留名 `CON` / `PRN` / `NUL` | ❌ 拒绝 | ✅ 允许 | ✅ **允许** |
| 非法字符 `a:b` | ❌ 拒绝 | ✅ 允许 | ❌ 拒绝 |
| 大小写冲突对（`Foo` vs `foo`） | ⚠️ 报 `NAME_COLLISION` | ✅ 视为两个不同 skill | ⚠️ 同 Windows |
| 路径长度 > 260 | ⚠️ 需系统开启长路径 | ✅ | ✅ |
| 软链接跟随 | ⚠️ 需管理员 / 开发者模式 | ✅ | ✅ |
| 文件锁（`filelock`） | ✅ | ✅ | ✅ |
| 云同步目录检测（OneDrive / iCloud） | ✅ | — 不适用 | — 不适用 |
| 路径穿越（`..` / symlink 逃逸） | ✅ 拒绝 | ✅ 拒绝 | ✅ 拒绝 |
| git 换行（`* -text` + 显式参数） | ✅ | ✅ | ✅ |
| 控制台中文输出 | ✅ 强制 UTF-8 | ✅ | ✅ |
| git 仓库格式（`--ref-format=files` + `-b main`） | ✅ | ✅ | ✅ |
| 路径比较（仅大小写 / 8.3 / 软链差异） | ✅ 视为同一目录 | ✅ 同 | ✅ 同 |
| 路径整理（结尾空格 / 反斜杠名） | ❌ 拒绝改写，报错 | ✅ 保留原名 | ✅ 保留原名 |
| 符号链接降级为 junction | ⚠️ 无权限时降级为目录联接，**并标记"可原地转链接"** | ✅ | ✅ |
| 持锁期间无 fsync / 无网络 | ✅ | ✅ | ✅ |
| 部署自证（写后回读） | ✅ | ✅ | ✅ |
| 运行中切换 repo 路径 | ✅ 要求重启 | ✅ 要求重启 | ✅ 要求重启 |
| **Unicode 归一化冲突**（同一个中文名的 NFC 与 NFD 两种字节形式） | ⚠️ 报 `NAME_COLLISION`（`path_key` 判定为同一路径） | ✅ 视为两个不同 skill | ⚠️ 同 Windows（APFS 写入即 NFD 化） |
| **抢锁（并发进程持有）** | ⚠️ 断言**无论抛何种异常都会重试**（`ERROR_LOCK_VIOLATION` 不映射 `WouldBlock`） | ✅ 断言重试 | ✅ 断言重试 |
| **锁诊断报文**（抢占失败时） | ✅ 含 `pid` / `hostname` / `operation` / `start_time` | ✅ | ✅ |
| **同步形态：拷贝 / 软链** | ⚠️ 软链无权限时降级 junction | ✅ 软链可用 | ✅ 软链可用 |

> **macOS 那两格特意纠正过一次**：`CON` 在 macOS 上**是合法文件名**（macOS 只禁 `:` 和 `/`），所以是 ✅ 而不是 ❌。macOS 与 Windows 的**真正差异只在「大小写不敏感」**，不在保留名上 —— 这两件事经常被混为一谈。

**自动化的边界（重要）**

| 项 | 决定 | 理由 |
|---|---|---|
| CI job 集合 | **`windows-latest` + `ubuntu-latest`** | 目标声明是「Windows 优先、兼容 macOS」 |
| macOS 列 | **设计意图，不自动验证** | Actions 的 macOS runner 单价更高，不值得为"兼容"常驻 CI |
| 沙盒 | **测不出任何一行** | 容器是 Linux，编码 / 大小写 / 保留名全都不复现 —— 这正是不依赖沙盒验证跨平台的原因 |

**断言语义（写测试时的硬要求）**

- ⚠️ 行：**两个平台都要断言"降级行为"**，例如 Windows 上断言 `NAME_COLLISION` 被抛出，Linux 上断言两个 skill 各自独立存在。不要写"结果一致"。符号链接那行要额外断言**降级后产生了"可原地转链接"的标记**（否则"静默退化为全量复制"会一直复制下去）。
- ❌ 行：**断言拒绝**。Windows 上写 `CON` 必须报错，**不得静默改名**（改名会让 hash 与用户认知同时错位）。**路径整理那行同样断言"原名被保留"** —— 不修剪、不替换分隔符。
- **Unicode 归一化行**：⚠️ 行 —— Windows / macOS 上断言报 `NAME_COLLISION`；**Linux 上断言两个 skill 独立存在**（Linux 不规范化文件名，两者是真不同的目录）。它与"大小写冲突对"是**同一类问题的两种编码**，两条用例必须都存在 —— 只测大小写会漏掉中文名场景，而本机 62 个 Skill 全是中文名。
- 平台差异夹具（CRLF 输入、`CON`、`a:b`、大小写冲突对、**NFC/NFD 路径对**）用 `core` 纯函数覆盖，不依赖真实文件系统 —— 这正是 NFR-8 的用处。
- **断言结果而不是配置**（`P1-9`）：不写"断言 `.gitattributes` 里有 `* -text`"，写"**断言同一内容在 CRLF / LF 两种输入下，`git status` 干净且 `hash_bytes` 符合预期**"。

## 7. 与 T1 决策的呼应

T1 定的是「`core` 根路径参数化，**不引入 VFS 抽象层**」。这份清单里 P0-4（非法字符）、P0-5（云同步目录）、P2-1（长路径）都是**文件系统语义差异** —— 它们说明：

> 不做 VFS 抽象，不代表可以忽略平台差异。
> 抽象层省掉的是**"同一逻辑两套实现"**，省不掉的是**"同一套校验规则"**。

所以这些校验（`safe_path` / 大小写冲突 / 保留名）必须作为**`core/fs` 里唯一的、跨平台统一的入口校验**，而不是散在各调用点。这与 T1 的「路径穿越校验在 core/fs 统一实现」正是同一条约束 —— 在 `04` 中已落为 `safe_path()`（§2.2.0，FR-1.0.14）。

同理，**写锁**也必须是三个入口（CLI / daemon / MCP）共享的下沉实现（FR-1.0.17），而不是每个模式各加一次 —— 前者是"一套规则"，后者是"三套实现"，后者一定漏。

**这三个"统一入口"就是本文件与 `04` 的接缝**，实现时不得分散：

| 统一入口 | 承担 | 落点 |
|---|---|---|
| `safe_path()` | 路径穿越 / 保留名 / 非法字符 / 软链循环 / canonicalize | `04` §2.2.0 |
| `sanitize_filename()` | **只校验、不改写**（P0-8） | `04` §2.2.0 |
| 写锁 + 锁内约束 | 三入口共享；网络 / fsync 出锁（P0-3 / P0-3b） | `04` §2.5.2 |

## 8. 与 v1.3 / v1.4 新增需求的呼应

从 `07` / `06` 吸收的**安全与正确性需求**，其正确性直接压在跨平台约束上：

| 需求 | 为什么依赖跨平台 | 本文件对应项 |
|---|---|---|
| **FR-1.0.27 部署自证**（写后回读） | "写成功"与"它在那"是两件事 —— 上游的失效形态正是**在某个平台上静默退化**（symlink 退化复制、迁移静默失败）。回读是唯一不依赖平台假设的验证方式 | P0-9 / P1-2 / 落地 23 |
| **FR-1.0.26 删除守卫**（列路径再动手） | removals 的"形态变化一律计为移除"直接对应**文件 / 目录 / 符号链接 / junction 的跨平台差异**；只按内容比对会漏掉形态变化 | P0-8 / P1-2 |
| **FR-1.0.31 路径键归一化**（v1.4） | 大小写与 Unicode 归一化都是**平台行为**（macOS 写盘即 NFD 化、Windows 大小写不敏感）。靠"看起来一样"做判定，必然跨平台分叉 | P0-4 症状 C / 落地 25 |
| **FR-2.4.9 锁诊断 + `FR-1.0.17` 抢锁语义**（v1.4） | 抢锁失败的**异常类型本身是平台相关的**（Windows `ERROR_LOCK_VIOLATION` vs POSIX `WouldBlock`）；按类型分支的代码**只在 Windows 上坏，且只在并发时复现** | P0-3b 第 5·6·7 条 / 落地 26·27 |
| **NFR-7.9 同步双模式**（v1.4） | 软链是**权限相关**能力（Windows 需管理员 / 开发者模式），必须能力探测 + 降级，不能假设可用 | P1-2 / 落地 29 |

> 一句话把上面串起来：**跨平台的失败模式不是"报错"，而是"在一个平台上报成功"**。所以自证与守卫不是额外的功能，是**跨平台正确性的验收手段**。
