# Skill OS 发行与编译手册

> 📘 **落地手册（第二步交付）** —— 与 `09-部署手册.md` 同性质：不含新需求、不改任何 `FR-*` / `NFR-*` / `OUT-*` 编号。口径冲突时以 `00`/`02`/`04` 为准。
>
> **本文档解决什么**：`09` 讲的是「源码形态怎么部署」（compose / 本地三件套）。本文档讲的是**编译发行形态**：把 `skillos` 编成原生机器码、以「使用者看不到源码、且零安装」的方式交付。两者共用同一份代码，只换发行物。

## 0. 一句话结论

**同一个内核，三种发行形态**：源码形态（`09`）用于开发与比赛演示；**D1 编译发行**（默认，下文详述）用于商业交付；全量 standalone（退路）用于「连运行时都不自带」的极端约束。

切换只改一处 —— `build/nuitka.json` 的顶层 `route`，脚本一行不动。

**D1 的取舍**（2026-10-10 定案，全部实测）：只把 `skillos/` 自己的 76 个模块编成机器码，第三方公开依赖交给随包 venv 装。

| | D1 实测 | 全量 standalone 实测 |
|---|---|---|
| 冷编译耗时 | **10 分 50 秒** | ~2.5 小时（1637 模块 / 941 MB C 源码） |
| 编译模块数 | 77 | 1637 |
| 产物 | `skillos.cp311-win_amd64.pyd` **4.5 MB** | 约 150 MB 目录 |
| 源码保护 | 强（机器码） | 强（机器码） |

> **为什么这么选**：保密需求只覆盖**我们自己的代码（76 个模块，占编译面 4.6%）**，另外 1560 个是公开代码。为 95% 的公开代码付编译成本，是方向性的浪费。

**交付形态（2026-10-10 定案）：装配产物本身就是一个 skill 包。**
`build/dist/skillos-<平台>/` 的根目录有 `SKILL.md`，下面带 `scripts/`、`references/`、
`runtime/`（编译载荷）、`vendor/<平台>/python`（便携 CPython）、`start.cmd`/`start.sh` ——
**压缩即交付，解压拷进 Agent 的 skills 目录即被识别**。用户拿到手的是「一个 skill」，
而不是「一个 SKILL.md + 一堆散落的兄弟目录」。

> 这条决定了载荷的落位：编译产物在**包内** `runtime/skillos/`，所以
> `manifest.frozen.dir = "runtime/skillos"`（相对包根），而不是早期的 `../skillos`。
> 早期把 `.pyd` 放在包外平级，交付物就不是一个自足的 skill 了 —— 那正是
> 「编译后的前后端代码没到指定地方」的根因。

## 2. 编译管线结构

```text
build/
├── nuitka.json               # ★ 唯一真相：route / include / exclude / 数据文件 / 便携运行时
├── build.py                  #   构建驱动（纯标准库）：组装命令 → 执行 → 装配发行目录
├── smoke.py                  #   产物四重冒烟（形态保密 / 运行时 / CLI / MCP / ASGI）
├── entrypoints/              #   仅 standalone 路线使用（module 路线的输入是整个包）
│   ├── skillos_main.py       #   统一入口（multicall：按 argv[0] 分派角色）
│   ├── skillos_cli.py        #   单角色入口（shared_runtime=false 的退路）
│   ├── skillos_mcp.py
│   └── skillos_server.py     #   程序化 uvicorn（避开字符串加载入口）
└── README.md
```

**规格驱动**：`build.py` 里没有任何业务性硬编码 —— 要加一个库、要换一条路线，只改 `nuitka.json`。

### 2.1 D1 编译面：自动排除第三方（核心机制）

```
--mode=package skillos --include-package=skillos      ← 编我们自己的 76 个模块
--nofollow-import-to=<第三方 68 个>  ← 由 build.py 扫描构建 venv 的 site-packages 自动生成
--no-deployment-flag=excluded-module-usage            ← 关掉「import 了被排除模块」的安全阀
--python-flag=no_docstrings --mingw64
```

排除清单**不是手工维护的**：`build.py::collect_exclude_packages()` 扫描构建 venv 的 `site-packages`，把所有第三方顶层包翻成 `--nofollow-import-to`。新增依赖会自动被挡在编译面外。两道安全网：

- `never_exclude: ["skillos"]` —— 构建 venv 里它以 editable 形式存在，会被扫到，必须排除在排除清单外；
- `sys.stdlib_module_names` —— 万一 site-packages 里有与标准库同名的包，排掉它会让 stdlib 一起消失，这类名字一律不排除。

### 2.2 交付物：一个自足的 skill 包

```text
build/dist/skillos-<platform>/          ← 整目录就是那个 skill 包
├── SKILL.md                            Agent 使用说明（启动三步 + 铁律 + 启动后可用 MCP 工具）
├── manifest.json                       发行清单（构建期改写为 mode=dist + frozen 块）
├── README.md / README.txt              给人看的说明
├── .gitignore                          仓库内忽略载荷用
├── scripts/                            启动器（纯标准库）：detect / bootstrap / start / stop / status …
├── references/troubleshooting.md       逐条现象 → 原因 → 处置
├── references/agent-config.md          Claude Code / Codex 的 MCP 接入配置
├── runtime/                            ★ 编译载荷（全部在包内）
│   ├── skillos/                        .pyd + 数据目录（**PYTHONPATH 注入点**；源码不可见）
│   ├── web/                            前端预构建产物（零 Node 的前提）
│   └── requirements.txt                第三方依赖清单（启动时装它，不装 skillos）
├── vendor/<平台>/python/               便携 CPython
├── start.cmd / start.sh                零安装双击入口（见 §2.4）
└── BUILD-INFO.json                     版本 / Python / Nuitka / git commit / sha256 / **源码泄漏自检**
```

外加 `build/dist/skillos-<version>-<platform>.zip`（`--no-archive` 可跳过）。

构建时可用 `--out-dir <路径>` 把包装配到任意位置（例如直接落到交付目录）。

### 2.3 launcher 怎么识别 frozen 形态

`manifest.json` 由 `build.py` 生成为 `mode=dist` + `frozen` 块（路径**相对本包根**）：

```json
"frozen": {
  "dir": "runtime/skillos",              // PYTHONPATH 注入点（.pyd 在这里）
  "requirements": "runtime/requirements.txt",
  "python_tag": "cp311",
  "python_pin": "3.11"
}
```

`scripts/_common.py::web_dist_candidates()` 也相应把 `runtime/web` 排在最前（并保留
旧布局的 `<包>/../web` 作为兼容回落）。

判据与 `binary` 块同源：**只信实物** —— `_common.is_frozen_mode()` 会真的去 `dir` 下找 `.pyd`/`.so`，找不到就当自己不是 frozen 形态（所以源码仓库里不会误判）。

launcher 的启动链因此分叉为：

| 形态 | 装什么 | skillos 从哪来 | 拉起后端 |
|---|---|---|---|
| repo | `pip install -e .` | venv 里的源码 | `python -m uvicorn ...` |
| **frozen** | `pip install -r requirements.txt` | **PYTHONPATH → `.pyd`** | `python -m uvicorn ...`（同左，env 注入） |
| binary | 什么都不装 | 编译进二进制了 | 直接跑 exe |

> ⚠️ frozen 形态下探测/拉起**必须用 `-P`，不能用 `-I`**。`-I` 隐含 `-E`，会把 `PYTHONPATH` 一并忽略 —— 而 frozen 的 skillos 只能靠 `PYTHONPATH` 找到（它不在 venv 里），用 `-I` 会永远判「没就绪」。`-P` 只阻止把 cwd 塞进 `sys.path`（这正是修「从仓库根跑 → 假阳性」要的），同时保留 `PYTHONPATH`。

### 2.4 零安装闭环：为什么需要 `start.cmd`

`start.py` 本身是 Python 脚本 —— 用户机器**完全没有 Python** 时，连「启动」这一步都迈不出去。所以构建期额外生成两个薄壳（`build.py::write_entry_scripts`）：

```bat
:: start.cmd（Windows）
set "PY=%HERE%vendor\win-x64\python\cpython-3.11.17-...\python.exe"
if not exist "%PY%" set "PY=python"
"%PY%" "%HERE%scripts\start.py" %*
```

```sh
# start.sh（macOS / Linux）
PY="$HERE/vendor/<平台>/python/..."
[ -x "$PY" ] || PY=python3
exec "$PY" "$HERE/scripts/start.py" "$@"
```

优先用包内自带的 CPython，缺了才回落系统 `python`。**这是「用户零安装」的最后一块拼图。**
（路径里没有 `launcher/` 了 —— 包根本身就是那个 skill。）

## 3. 怎么构建

### 3.1 前置：构建机必须是 Python 3.11

D1 的产物**只认 CPython 3.11 的 ABI**。`build.py::check_python()` 会在构建开始前拦住其他版本并给出三条出路（换 3.11 / 改走 standalone / 交 CI）。

> **产物名随平台变（实测，容易踩）**：同一个 ABI 在 Nuitka 下有两种写法 ——
> Windows 是 `skillos.cp311-win_amd64.pyd`，macOS / Linux 是
> `skillos.cpython-311-darwin.so` / `skillos.cpython-311-x86_64-linux-gnu.so`。
> `cpython-311` 里**不含**子串 `cp311`，所以 `build.py` 的产物名校验必须两种都认
> （只认 Windows 写法会把 mac/linux 全误判成「构建机 Python 版本不对」，CI 上
> 三个非 Windows 平台就是这样全红的）。运行期不受影响：判据一律是
> 「`dir` 下有没有 `.pyd`/`.so` 实物」（`_common.is_frozen_mode()`）。

```bash
# 0) 前置：前端已有预构建产物（且不带 sourcemap）
cd web && npm ci && npm run build && cd ..

# 1) 只看命令（无编译器也能跑，用来核对排除清单）
python build/build.py --dry-run

# 2) 真构建（首次 ~11 分钟；ccache 命中后 5 分钟内）
python build/build.py --vendor-python /path/to/cpython   # 指定要随包的便携 CPython
python build/build.py --no-archive                       # 先不打包，便于本地冒烟

# 3) 四重自证
python build/smoke.py --mirror cn
```

**便携 CPython 从哪来**，按优先级：`--vendor-python` > 环境变量 `SKILLOS_VENDOR_PYTHON` > 现场用 `uv python install`（CI 有网时走这条）。三条都不通时会**降级**：发行物不自带运行时，用户机器需有 Python 3.11，或首次启动由 vendor 内 uv 联网自举 —— 构建日志会明确警告。

```bash
# 单独预置一份便携 CPython（1 分 37 秒 / 下载 24MB、解压 76MB）
uv python install 3.11 --install-dir ./vendor-python
```

**Nuitka 不需要你预装编译器**：`--assume-yes-for-downloads` 已写进管线，缺 MSVC 时它会自动拉 winlibs MinGW64（约 255 MB，首次构建会慢）。

**构建环境要独立**（别污染系统 Python）：`check_nuitka()` 读的是**当前解释器的 `importlib.metadata`**，所以跑 `build.py` 的那个 Python 必须能查到 nuitka —— **`--skip-build` 也不例外**（虽然它只复用 `build/out` 里的 `.pyd`、根本不调 Nuitka）：

```bash
# 本机复现（2026-10-10 实测记录，全程可用）
D:/App/Python/Python311/python.exe -m venv build/.venv-build     # 必须 3.11
build/.venv-build/Scripts/python.exe -m pip install nuitka        # 离线：pip 缓存里有 nuitka-4.2.2-cp311 wheel

build/.venv-build/Scripts/python.exe build/build.py \
    --skip-build --vendor-python build/out/vendor-python --no-archive
```

**`--skip-build` 也必须有 `--vendor-python`**：`assemble_module()` 会先 `rmtree(<dist>)` 再重建，所以装配前**发行目录会被整个删掉**（包括里面那份便携 CPython）。如果构建机上没有第二份便携 CPython 源，就会静默丢掉「零安装」能力。稳妥做法：预置一份到 `build/out/vendor-python/`，装配时从它拷。

**`--clean` 在本机跑不通**：它走 `shutil.rmtree(build/out, build/dist)`，批量删除超过安全阈值会被环境拦下（`[safe-delete] ... count:3794`）。先手工删掉这两个目录再重跑即可 —— **这不是管线 bug，是运行环境的安全策略**。

### 3.2 CI（正式产物来源）

`.github/workflows/release.yml`，矩阵 **4 个平台 / 3 种 OS**：

| 平台 | runner | 规格 | 说明 |
|---|---|---|---|
| `win-x64` | `windows-latest` | 4 vCPU / 16 GB | Nuitka 自动拉 MinGW64，无需 MSVC |
| `linux-x64` | `ubuntu-latest` | 4 vCPU / 16 GB | 需 `patchelf` 修 rpath，否则换机找不到 `.so` |
| `mac-arm64` | `macos-15` | 3 vCPU / 7 GB | Apple Silicon |
| `mac-x64` | `macos-15-intel` | 4 vCPU / 14 GB | Intel |

```text
web job（构建 SPA 一次）→ compile job ×4（下载 dist → uv python install → Nuitka → smoke → 上传 artifact）
```

> **镜像标签会过期，别写老标签**：GitHub 只同时支持最新 2 个 GA 镜像。`macos-13` 已于 **2025-12-04 完全退役** —— 仍写它的任务会**直接失败**，不降级。macOS 两个架构**必须用不同标签**：arm64 是 `macos-15`，Intel 是 `macos-15-intel`，**没有通用标签**。`macos-15-large` / `-xlarge` 是 larger runner（私有仓库额外计费），不要误用。

> **计费**：公开仓库**免费且不限量**；私有仓库走账号额度，**macOS runner 按 10× 计费**（Free 计划 2000 分钟/月 → macOS 实际约 200 分钟；一次编译约 5–15 分钟，即消耗 50–150 分钟额度）。

> **不需要有 mac 电脑**：Nuitka 不支持交叉编译，mac 产物只能在 mac 上编 —— 但 GitHub 免费提供 macOS runner，本机（Windows）`git push` 即可产出。

触发：打 tag（`v0.1.0`）或手动 `workflow_dispatch`。**PR 不跑** —— 编译以十分钟计，不该拖慢日常 CI；日常校验仍由 `ci.yml` 的 pytest / web / docker 三 job 负责。

Linux 上额外装 `patchelf`（修正 rpath，否则产物换机器找不到 `.so`）。**每个平台各出一份产物** —— ABI 不同，`cp311` / `cpython-311` 不能跨平台。

## 4. D1 的三个坑（实测踩出来的，都已固化为自动处理）

### 4.1 `--mode=module` 编不出子模块，必须用 `--mode=package`

Nuitka 的 `--mode=module` 只编**单个模块**：包里的子模块完全不进去，运行时直接 `ModuleNotFoundError: No module named 'skillos.api'`。

官方为此提供了 `--mode=package`（`--help` 原文：*"package" compiles a whole package into an extension module*）。两者产物都是单个 `.pyd`，但只有 `package` 会把子模块按包路径编进去。管线再用 `--include-package=skillos` 叠一层保险：强制收全包内模块，防止包内「按字符串加载」的模块被静态分析漏掉（实测两者组合无冲突、无告警）。

### 4.2 扩展模块里 `__file__` 是**虚拟路径**，数据文件必须手工落位

`--include-data-files` 在 **module / package 模式下不落盘**（standalone 才生效）。而 `__file__` 在扩展模块里是**合成出来的**：

```
__file__ = <输出目录>/<包名>/<原相对路径>
```

实测 `skillos.d1/skillos.cp311-win_amd64.pyd` → `skillos.__file__ == ...\SK66B4~1\skillos\core\algorithm\discover.py`（该路径上并没有 `.py` 文件，是虚拟的；`SK66B4~1` 就是输出目录的短文件名）。

所以 `build.py` 在编译成功后**显式拷贝**数据文件到 `<输出目录>/<dest>`，`dest` 保持与包内相同的相对结构；装配时把整棵树搬到 `<dist>/skillos/skillos/...`。`discover.py` 用 `Path(__file__).parent` 就能读到（实测 `白名单.exists() == True`）。

> `.pyd` 与同名数据目录（`<dist>/skillos/skillos.cp311-win_amd64.pyd` 与 `<dist>/skillos/skillos/`）**可以安全共存** —— 扩展模块优先于 namespace package。实测 `import skillos` 加载的是 `.pyd`。

### 4.3 部署安全阀会硬失败

Nuitka 发现「代码 import 了一个被 `--nofollow-import-to` 排除的模块」时会直接失败，并给出逃生开关：

```text
ImportError: Module 'sqlalchemy' was actively excluded from Nuitka compilation.
Disable with '--no-deployment-flag=excluded-module-usage'
```

D1 的设计**恰恰就是**故意排除第三方、运行期从 venv 取，所以这个开关必须开。已写进管线。

### 4.4 其余：编译器选择与「下载提问永久挂起」

**编译器由构建机的 Python 版本决定**（实测）：

| 构建机 Python | 可用编译器 | 说明 |
|---|---|---|
| ≤ 3.12 | `mingw64` 或 `msvc` | MinGW64 由 Nuitka 自动下载，**不需要装 Visual Studio** |
| ≥ 3.13 | **只能 `msvc`** | 上游未提供 3.13 的 MinGW 构建；实测直接 `FATAL: cannot use '--mingw64' on Python version 3.13 or higher` |

D1 把构建机钉在 3.11，所以总是 MinGW64。`check_compiler()` 仍保留完整决策表 —— standalone 退路要用。

**下载提问会让构建永久挂起**（两道防线）。Nuitka 在需要下载辅助工具时会**交互式提问**：

```text
Is it OK to download and put it in local user cache.
Fully automatic, cached. Proceed and download? [Yes]/No :
```

源码位置 `nuitka/utils/Download.py::shouldDownload()` → `Tracing.py::queryUser()`，而 `queryUser()` **无条件阻塞在 `raw_input()` 上**：

```python
try:
    reply = raw_input() or default
except EOFError:
    reply = default_non_interactive     # = "no"
```

非交互环境里若 stdin 是「开着但不给数据」的管道，这里会**无限期阻塞**：实测一次构建**空转 18 分钟，零产物、零下载、零报错**，日志上看不出任何异常 —— 整套管线里最难定位的一类故障。

| 防线 | 内容 | 作用 |
|---|---|---|
| ① 命令行 | `--assume-yes-for-downloads` 写死在管线里 | 让 `shouldDownload()` 直接返回 yes，正常路径下**根本不出现提问** |
| ② stdin 兜底 | `build.py::run()` 用 `subprocess.run(..., input="yes\n" * 64)` | 万一上游漏传该开关而仍提问，**自动应答 yes**；即便无提问，多余输入也被忽略 —— **结构上不可能挂死** |

> `check_nuitka()` 也刻意**不用 `python -m nuitka --version`** —— 实测它在缺编译器时会顺带探测并触发下载提问。版本号改从 `importlib.metadata.version("nuitka")` 零副作用地读。

## 5. 「源码不可见」的能力边界（诚实记录）

**编译把逆向门槛从「5 分钟」抬到「几天」，不是 DRM。**

- Nuitka 产物理论上仍可逆向（反汇编、常量提取），只是成本完全不是一个量级。**别把它当授权保护手段**（授权防拷贝见 §8，明确不做）。
- **前端 JS 无法真正隐藏**：浏览器必须拿到可执行代码。唯一可行的一刀是**构建不发 sourcemap**（已做，且 `build.py::_copy_web()` 会在装配时检查 `runtime/web/**` 有没有 `.map`，有就中止构建）。
- **保护边界要说清**：`runtime/skillos/` 是机器码；`scripts/*.py` 是明文薄壳（只做编排，不含业务逻辑）。这是刻意的 —— 让客户能审计「启动器没干坏事」，同时业务逻辑不可见。
- 剥离 docstring（`--python-flag=no_docstrings`）是顺手的一刀，同时减小体积。
- **构建期有机械化的泄漏自检**：`BUILD-INFO.json.source_leak_check` 记录 `<dist>/runtime/skillos/**` 下 `.py` 的个数，`smoke.py` 再断言一次必须为 0。

**为什么编译在这里是「必要而非可选」**：产品架构决定 daemon 必须跑在用户机器上（真值在本地 git + 磁盘，见 `NFR-1`）。只要私有化部署，源码就必然落到客户手里 —— 要「看不到源码」，只有编译一条路。

## 7. 验证：四重自证

`build/smoke.py` 对**已编译产物**跑断言，不信任构建日志。它会把发行物**当成用户那样先装一遍**（用自带便携 CPython 建 venv → 装 `requirements.txt`），再跑起来。

> **2026-10-10 实测：44 项断言全绿**（`=== 全部通过 ✔（44 项断言，D1 发行物自证完成）===`；针对 `build/dist/skillos-win-x64/`）。

| # | 阶段 | 断言 |
|---|---|---|
| 0 | 发行形态与保密 | 包根有 `SKILL.md` 与 `scripts/start.py`（**证明这是个完整 skill**）；`manifest.mode=dist` 且 `frozen` 块在位、`frozen.dir` 指向包内 `runtime/`；`<dist>/runtime/skillos/**` **无 `.py`、无 `__pycache__`**；`runtime/web/**` **无 `.map`**；`runtime/requirements.txt` ≥8 条且**不含 skillos**；便携 CPython 与 `start.cmd`/`start.sh` 在位 |
| 1 | 运行时 | 包内便携 CPython 能建 venv、能装完 requirements；`import skillos` 成功且**由编译产物加载** —— 判据是 Nuitka 注入的标记：`__loader__ == nuitka_module_loader` 且 `__compiled__.extension_filename` 指向真实存在的 `.pyd`/`.so`。**不能拿 `__file__`/`__spec__.origin` 的后缀判断**（package 模式下它们是虚拟源码路径，见 §6 #13）；另断言 `__file__` 指向的路径上**没有真实 `.py` 文件** |
| 2 | CLI | `skillos --help` 退出码 0，且列出 `init` / `daemon` / `mcp` / `push` / `check` |
| 3 | MCP | 完整 JSON-RPC：`initialize` → `tools/list`（八工具白名单，`OUT-14`）→ `tools/call`（`push` 默认 `dry_run`、`upgrade` 显式 `NOT_IMPLEMENTED`） |
| 4 | 后端 | `/api/health` 通 → `/` 返回 HTML（证明 `web/` 随包且托管路径正确）→ 未知前端路由不 404、`/api/*` 未知路径返回 JSON 404（不被 SPA 吃掉） |

**依赖安装按 `requirements.txt` 哈希缓存在** `build/out/smoke/`，内容没变时不重装（首次约 4–5 分钟；实测 318s）。`--rebuild-venv` 强制重来。

> **缓存有自愈**：venv 的 `pyvenv.cfg` 把基座解释器路径写死，发行目录一改名/换位就失效（报 `No Python at '<旧路径>'`），而文件仍存在 → 会「假复用」。`smoke.py::_venv_python_works()` 先验证 venv 真的能跑，不行就删掉重建（批量删除被环境拦下时给出可读指引，不裸崩）。

**子进程环境必须是「沙盒化」的**：`build/smoke.py::run_env()` 同时注入 `SKILLOS_ROOT` **和** `SKILLOS_HOME`（都指向临时 home）。入口层现已收敛到 `resolve_home()`（`SKILLOS_ROOT` 优先，见 §6 #11），冒烟仍两个都设 —— 只设一个而恰好设错，就会退回 `Path.home()` 去扫开发机的真实 `~/.claude/skills`，结果是**脚本在别人机器上全绿、在你机器上撞 slug 冲突**。这类「测试环境污染」比产物缺陷更难查。

**为什么这一步不可省**：Nuitka 最典型的失败是**编译成功、运行期才炸**（漏 include、数据文件没随包）。那恰好是「构建脚本跑通了」和「产物能用」之间最大的落差。

## 8. 已知限制与后续

| 项 | 现状 | 后续 |
|---|---|---|
| **Python 版本被锁死在 3.11** | D1 产物只认 CPython 3.11 的 ABI（Windows 名 `cp311-*.pyd`，mac/linux 名 `cpython-311-*.so`） | launcher 的「系统有且达标即用系统」已收紧为「**系统有 3.11 才用系统**，否则一律回落随包的 3.11」；检测到 3.12/3.13 时会在 notes 里说明原因 |
| 每个平台各出一份产物 | ABI 不同，不能跨平台 | CI 矩阵四平台各编一份（`win-x64` / `linux-x64` / `mac-arm64` / `mac-x64`，见 §3.2） |
| 首次启动需要网络 | 要装第三方依赖 | `--offline` + 预置 venv 可免；或改走 standalone 退路 |
| `reload` / `workers` | 编译产物不支持 | 开发热更走源码形态 |
| 授权 / 防拷贝（license 码） | 明确不做 | 真值在客户内网，架构上无法强控；纯负担 |
| 前端 sourcemap | ✅ 已显式关闭 + 构建期机械检查 | 浏览器侧 JS 仍无法真正隐藏（见 §5） |
| `dulwich`（纯 Python git） | 未采纳 | 可彻底去掉 git 二进制依赖，但行为差异会咬人（见 `07` §6） |
| PyArmor（字节码加密） | **已评估淘汰** | 免费版在真实 skillos 的 **64/76 个文件处 `out of license`**；商用需授权（Basic $52 / Pro $89 / Group $158）；且公开评测指出其「加密字节码」只是减速带，弱于 Nuitka 机器码。引入第三方授权依赖且保护更弱 → 不采用 |
