## 5. 战略级影响（最重要 —— **已拍板**）

### 5.1 对方证明了一件事：多设备同步不需要自建云端

他们的做法：

```
多设备一致性 = Git remote
备份与历史   = Git remote
元数据一致性 = 元数据也进 Git（.skills-manager/ 目录）
SQLite       = 本地缓存，可重建，不进 Git

"远端始终是纯 Git 仓库——随时可以 git clone 走，没有锁定。"
```

对比我们的设计：云端后端（FastAPI + Postgres）+ daemon 出站 WebSocket + 18 张表 + 双向同步协议。

**我们的云端里，"同步/备份"这部分职责是可以被 git 完全替代的。**

### 5.2 但我们的云端不全是为了同步

必须先分清：我们的云端承载三件事——

| 职责             | 能否被 git 替代                             |
| -------------- | -------------------------------------- |
| 多设备同步 / 备份     | ✅ **能，且 git 更优**（免费 diff/历史/回滚，无服务端运维） |
| Web 控制台（浏览器访问） | ❌ 不能                                   |
| 评委可点开的在线沙盒     | ❌ 不能                                   |

### 5.3 建议的折中（**已拍板：不采纳**）

> **把云端的"数据面"职责全部删掉，只保留"表现层 + 沙盒"。**

具体：

- 多设备一致性 → **交给 git remote**（用户自己的 GitHub 私有仓或任意 git 地址）
- 云端**不存 skill 内容、不做 push 任务下发、不做冲突检测**（冲突在本地由 git 处理）
- 云端只保留：**Web 控制台（读元数据 + 展示漂移矩阵）+ 沙盒 Runtime + 任务触发**
- 相应地可以砍掉：`sync_records` 双写、云端冲突流程、daemon 的写任务（`file_write` / `push` 改为本地 CLI/MCP 路径）

**收益**：工作量显著下降，且"多设备"这个卖点从"我们要自建一套同步协议"变成"复用 git 成熟的分布式能力"——后者在评审面前更容易讲清楚，也更不容易出 bug。

**代价**：与已定稿的 `FR-3.x`（云端 API / 同步 API / 元数据存储）冲突，需要改需求编号；且 demo 剧本要调整（"一键分发"仍可演示，但"跨设备同步"改为演示 git 侧）。

**这是一个真正的取舍。**

> **拍板结果（2026-10-06）：不采纳，保留云端在写路径上的职责**（术语「数据面」的两个用法见 `04` §1.2 —— 此处指**云端保留写路径职责**：任务下发 + `sync_records` 双写，**不存文件内容、不判冲突**）。理由三条：
>
> | # | 理由                                                                  |
> | - | ------------------------------------------------------------------- |
> | 1 | **Demo 形态要求**：评委要能"打开浏览器就看见" —— 这是相对桌面应用的**唯一形态差异**，也是"线上可访问"硬约束的落点 |
> | 2 | **本地 daemon 已经设计好了**：云端数据面与本地 daemon 共用同一套任务表与锁，删掉它是**推倒重来**，不是省时间  |
> | 3 | **真正该收敛的是"云端不做冲突判定"**：冲突仍在本地三方比对解决，云端只转发结果 —— 这一条**与本提案无冲突，已落在设计中** |
>
> 换言之：**保留云端 ≠ 云端变重**。数据面职责保留，但"真值"始终在本地 git + 磁盘（`00` NFR-1 离线可用即此）。
>
> **保留的是职责，不是复杂度** —— 上表 5.1 里"多设备同步/备份可被 git 替代"这个观察**仍然成立且已被吸收**：仓库本身就是 `~/.skillos/repo` 的 git 仓库，用户可自行配 remote（FR-1.0.10）。云端不做同步也没有替它做同步，两者并存。
>
