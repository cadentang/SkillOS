## 1. 定位与叙事

**一句话定位**

> Skill OS —— Agent 能力的包管理器与分发层。写一次，四个 Runtime 都能用。

**对内的技术定义**

> Skill 的 canonical 仓库 + 跨 Runtime 适配层 + 漂移感知 + 版本可追溯 + 可被 Agent 自管。

**三级演进叙事（对应「商业价值」维度）**

| 层级 | 形态 | 价值 |
|---|---|---|
| L1 个人 | 单机 Skill 库、四端分发、版本回滚 | 当前 demo 展示的层级，赛后可立即自用 |
| L2 团队 | 共享 Skill 库、变更审查、权限 | 团队内部 Agent 能力复用与合规 |
| L3 企业 | Skill 治理：准入、安全扫描、审计、交付 | 企业 AI 能力交付（FDE 场景） |

**批判性提示**：个人工具本身商业模式弱。真实商业价值在 L3——企业需要知道「哪些 Agent 能力被允许使用、谁改的、过没过评审、有没有安全风险」。demo 只做 L1，但叙事必须把 L2/L3 讲清楚，否则「商业价值」维度会失分。

## 2. 核心架构矛盾（必须先解决）

**矛盾：要求「线上可访问」，但核心能力是操作本地文件系统。**

浏览器在云端碰不到 `~/.claude/skills`，因此不能做成纯 Web 应用。

**解法：双形态并存**

```text
┌────────────────────────────┐        ┌────────────────────────────┐
│  云端控制台 (Web)          │  出站  │  本地 Agent (daemon)       │
│  UI / 元数据 / 协作 / 权限 │◄──────►│  文件系统读写 / git / 扫描 │
└────────────────────────────┘  WS    └────────────────────────────┘
                                            
┌────────────────────────────┐
│  沙盒 Runtime (容器内)     │  ← 评委点开线上链接即可玩，无需本地安装
└────────────────────────────┘
```

三个要点：

1. **本地 daemon 主动出站连接云端**（WebSocket），不需要公网 IP、端口映射、内网穿透。
2. **云端控制台是产品本体**（自己长期用）。
3. **沙盒 Runtime 是 demo 门面**：容器内虚拟 `~/.claude/skills` 等四个目录，评委打开线上链接就能体验全流程。

这三者合起来同时满足「线上可访问」与「真实本地操作」，也是「技术创新」维度的主要得分点。

## 3. 功能域拆解

按**依赖关系**分层，不按重要度。下层是上层的必要条件。

### D0 引擎层（core，无 UI）

| 能力 | 说明 |
|---|---|
| scan | 扫描 runtime 目录树，识别 skill 包边界（含 `subskills/` 嵌套） |
| parse | 解析 SKILL.md frontmatter、文件树、`agents/openai.yaml` 等 sidecar |
| index | 建索引，落 DB（可随时重建的缓存） |
| hash | 内容指纹，用于漂移判定 |
| adapter | canonical → 目标 runtime 的结构映射 + frontmatter 字段策略 |
| distribute | 原子写入 + 备份 + 回滚 |
| diff | 三方比对（repo / 磁盘 / 上游） |
| version | git 封装（commit / log / diff / rollback / merge） |

### D1 存储层

| 数据 | 载体 | 理由 |
|---|---|---|
| 文件内容与版本 | **Git 仓库**（canonical，唯一真相源） | 白送 diff / commit / rollback / 三方合并 |
| 平台元数据（tags / source / 权限 / 评分 / 漂移状态） | **数据库**（只存 git 表达不了的东西） | 避免双写不一致 |
| 大文件 assets | 本地为主；团队版可上对象存储 | 先不做 |

### D2 漂移检测（产品核心）

```text
desired = repo 中 canonical skill 经 adapter 转换后「应当存在」的文件集合 + hash
actual  = 磁盘上实际存在的文件集合 + hash

漂移分类：
  MISSING    应装未装
  OUTDATED   已装，但 repo 版本更新
  MODIFIED   已装，但本地被改动
  EXTRA      磁盘上有，repo 里没有
  CONFLICT   本地改了 + repo 也改了  → 需三方合并，不可静默覆盖
```

`CONFLICT` 是唯一需要人工介入的状态，也是最能体现技术含量的部分。

### D3 来源与升级

| 能力 | 说明 |
|---|---|
| Source 抽象 | `local` / `git:<url>` / `marketplace` / `imported` |
| 上游跟踪 | 记录 upstream 地址、ref、基准版本、last_checked_at |
| 更新检测 | 定时比对 upstream hash（本机 `.runtime/update-status.json` 已有同款机制可参考） |
| 安全升级 | 保留本地改动的前提下升级；冲突则走三方合并 |
| fork 标记 | 本地修改即 fork，与上游关系显式化 |

### D4 质量检查（建议新增，卖点）

几乎不额外耗时，但同时在「技术创新」和「长期自用」两个维度产生价值：

- frontmatter 规范性（官方仅约定 `name` + `description`）
- description 长度与 token 占用（渐进披露依赖它，过长是真实成本）
- 结构完整性（SKILL.md / 引用文件是否存在）
- 依赖完整性（`skill_dependencies` 指向的 skill 是否存在）
- 相似 / 重复检测（已知案例：req-test-cases 与商城 test-case-generator 功能重叠）

### D5 入口层

| 入口 | 用途 | 对应评审维度 |
|---|---|---|
| MCP Server | Agent 自己调用（"帮我把这个 skill 升到上游最新"） | 技术创新 |
| HTTP API | Web 调用 | — |
| CLI | 日常与脚本 | 完成度 |

### D6 Web 功能（按用户指定全量纳入）

| 模块 | 说明 |
|---|---|
| 能力总览 | 六十二个 skill 的分类地图、状态、健康度 |
| 漂移告警 | 四端 × 每 skill 的状态矩阵，可下钻 |
| 一键分发 | 批量 push，带进度与结果 |
| CRUD 后台 | skill / 版本 / 标签 / 依赖 / runtime 的增删改查 |
| 编辑器 | 文件树 + Monaco + frontmatter 表单化（多文件包，非单文件） |
| Diff 视图 | 三种维度：版本间 / 端间 / 与上游 |
| 版本管理 | 时间轴、回滚、分支、tag |
| 协作 | 共享库、成员、权限、变更审查（Change Request） |

### D7 沙盒模式

容器内虚拟四个 runtime 目录，供线上访问者体验完整流程（scan → 漂移 → 分发 → 回滚）。

## 4. 关键设计决策（建议，待确认）

| # | 决策 | 建议 | 理由 |
|---|---|---|---|
| 1 | 唯一真相源 | **Git 仓库**；DB 只做索引与元数据 | 双写两套存储必然不一致 |
| 2 | canonical 格式 | **原生 SKILL.md 结构**，不自造 manifest | 不制造第二套规范，同步无需翻译层 |
| 3 | 平台元数据位置 | sidecar 文件或 DB，**不污染 SKILL.md** | SKILL.md 是给 agent 读的，塞平台字段烧 token |
| 4 | 版本粒度 | 包级版本（= git commit）+ 文件级历史（`git log -- <path>`） | 不引入两套版本概念 |
| 5 | 同步语义 | git 语义（三路合并），**不静默覆盖** | 避免丢改动 |
| 6 | 元数据主存 | 云端为主（存协作/权限），文件以 git 为准 | 本地索引可随时重建，无冲突 |
| 7 | 编辑粒度 | 第一版只编辑 text / markdown 类文件 | 二进制 assets 仅上传下载 |

## 5. 数据模型草案

```text
skills               id, slug, name, description, category, visibility, owner_id, timestamps
skill_versions       id, skill_id, version, git_commit, status, message, created_by, created_at
skill_files          id, version_id, path, hash, size          （内容在 git，这里只存索引）
skill_tags           skill_id, tag
skill_dependencies   skill_id, depends_on_skill_id, kind
skill_checks         id, skill_id, version_id, rule, level, message
skill_similarity     skill_a_id, skill_b_id, score

runtimes             id, name, adapter_key, root_path, scope(user/project), enabled
runtime_bindings     id, skill_id, runtime_id, status, installed_hash,
                     installed_version, last_synced_at      ← 漂移检测核心表
sync_records         id, skill_id, runtime_id, action, from_state, to_state, at, by

upstream_sources     id, skill_id, type, url, ref, base_version,
                     upstream_hash, last_checked_at

users / teams / team_members / team_skills / permissions
change_requests      id, skill_id, base_version, head_version, status, reviewer_id, comments
```

## 6. 阶段划分（每阶段必须有可演示产物）

单人项目最大的风险不是写不完，而是**没有中间可演示态**。因此排序原则：前两阶段就要能撑起完整 demo，后续皆为增量。

| 阶段 | 内容 | 可演示产物 |
|---|---|---|
| P1 | 引擎 + CLI：scan / parse / index / status / push | 终端里四个 runtime 状态矩阵 |
| P2 | 云端骨架 + daemon 通道 + Web 只读看板（总览 / 漂移 / 一键分发） | **完整 demo 主线已可用** |
| P3 | CRUD + 编辑器 + diff 视图 + 质量检查 | 可在 Web 里完整编辑一个 skill |
| P4 | 版本管理 UI（时间轴 / 回滚 / 分支） | 改坏 → 回滚的可视化 |
| P5 | MCP Server | Claude Code 里让 agent 自管 skill（demo 高潮） |
| P6 | 协作（共享库 / 权限 / change request） | 团队场景 |
| P7 | 沙盒 demo 模式 + 来源升级（上游跟踪） | 评委可点开的线上链接 |

> P5（MCP）也可提前到 P3 之后，取决于 demo 剧本的重心。

## 7. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 单人 + 全量 Web 功能 | 长期无可用中间态 | 严格按第 6 节阶段推进，每阶段可演示 |
| 线上 vs 本地文件系统 | 纯 Web 方案根本不成立 | 第 2 节 daemon + 沙盒双形态 |
| "多人协作"定义不清 | 若做成实时协同编辑（OT/CRDT），成本极高且价值低 | 见第 8 节待确认项 Q1 |
| 跨 runtime 字段策略复杂 | adapter 变成泥潭 | 第一版只做字段白名单 + 透传，转译留接口 |
| 商业价值叙事空泛 | 评审失分 | 用第 1 节三级演进叙事，并绑定 FDE 交付场景 |

## 9. Demo 剧本（双高潮）

> ⚠️ **本节已被 `03-开发排期.md` 第 7 节取代，仅作决策沿革保留。**
>
> 原因：这里的 2:15 片段写的是「把这个 skill 升到**上游最新**，冲突我来确认」—— 上游跟踪是 `FR-1.0.13`，排在砍单顺序第 6 位。**把 demo 高潮押在一个可砍功能上，是自找风险**。权威版已改为「本地 skill 分发」+「repo 改 + 磁盘改制造冲突」，不依赖任何外部来源。

```text
0:00  问题陈述
      一台机器 62 个 skill 散在 4 个目录；同名副本、不知谁新谁旧、上游更新不可知
      → 投屏展示 ~/.claude 与 ~/.agents 下两个字节完全一致的 brainstorming

0:30  skillos scan → 控制台刷出 62 个 skill / 四端状态 / 漂移告警

1:00  改一处 SKILL.md → 一键分发 → 四个终端同时生效          【高潮一】

1:45  故意改坏 → 版本时间轴回滚

2:15  切到 Claude Code，说「把这个 skill 升到上游最新，冲突我来确认」
      → agent 自己调 MCP 工具完成                              【高潮二】

2:45  收尾：真实数据 —— 「这不是编的 demo，是我每天在用的 62 个真实 skill」
```

**关键点**：全线跑在本机真实数据上，不切换到假数据。真实、可复现、无需编排，是相对其他参赛项目的最大优势。
