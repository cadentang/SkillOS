## 二、背景与目标

**背景**：黑客松 2026-10-18 交付后进入赛后演进期。产品定位已收敛为「Agent 能力治理的控制台」，功能骨架完整（D1/D2/D3 全线可用），短板集中在三处：

1. **口径缺口**：折旧阈值、引用计数、CR 状态机等定义不细，治理叙事的承重墙不牢；
2. **数据缺口**：僵尸 Skill 占比只能靠 staleness 推断，没有"实际被用过"的证据；
3. **扩展性缺口**：门禁规则不可扩展，安全扫描（L3 第一块砖）无从谈起。

**成功指标**（赛后 1 个月口径，估算）：

| 指标 | 口径 | 目标 |
|---|---|---|
| 僵尸占比口径升级 | 实测调用 + staleness 双条件命中的 skill 数 / 总数 | 管理者视图可用新口径，且能标出口径来源 |
| 门禁规则可扩展性 | 用户自定义规则成功拦截 push 的次数 | ≥1（自家 dogfood） |
| 安全扫描有效性 | 预置密钥规则在本机 62 个 skill 上的命中/误报比 | 有数据即可（先建基线） |
| 体检报告送达率 | 周报连续生成周数 | ≥4 |

## 三、名词与术语

| 术语 | 定义 |
|---|---|
| **使用事件（usage event）** | Skill 内容或元数据被**读取或修改**的一次经 skillos 通道的行为（定义见 N-01 §8.1）。Dashboard 总览页打开不逐 skill 计 |
| **僵尸 Skill（新口径，旧口径不保留）** | 近 90 天零调用 **且** staleness = degraded，双条件（Q-01 / Q-02 决议） |
| **token 归属** | 会话级 token 按「调用事件时间片」归到 skill 的估算口径（N-11.3），UI 强制标注，禁止当精确计量 |
| **规则集版本（ruleset hash）** | 一次 check 时生效的全部规则文件的聚合哈希，落 `skill_checks.ruleset_hash`，用于历史复现 |
| **deprecated（弃用）** | Skill 的软状态：保留记录与历史，bindings 停用，可随时恢复。≠ 删除 |
| **块内合并（block merge）** | 冲突整文件四选一之外的第五选项：按 diff3 块逐块选择，仅 Web 人工路径 |
| **pending 冲突传播** | 一台设备产生的未决策 CONFLICT，在其他设备上可见并可接手决策 |

## 七、功能细化需求（E-01 ~ E-08）

### E-01 健康度合成口径（基线：FR-1.0.24 / NFR-10.3 / T11）

**现状**：公式已在 `04` §2.1.7 并实现。本项把"算得出"固化为"可验收、不可漂移"。

**规则**：

| # | 规则 |
|---|---|
| E-01.1 | 公式维持 `score = 100 − 10×error_count − 3×warn_count − 8×degraded_decay_dimensions`，下限 0 |
| E-01.2 | 权重常量集中 `core/constants.py`（`HEALTH_WEIGHTS`）；**禁止做成 DB/配置可调** —— 健康度是缓存可重算值，运行时可配会让历史分数不可比（不知道是资产变了还是权重变了）。调权重 = 改代码 + 提交说明 |
| E-01.3 | unknown 维度不加减，但 UI 必须显示「未知 N 项」，且 N 与 `skill_checks(scope=decay, level=unknown)` 行数严格一致 |
| E-01.4 | 重算幂等：同一 SkillSnapshot + 同一 skill_checks 数据，两次计算同分 |
| E-01.5 | T11 落地约束验收：静态搜索 `health_score` 全部读取点，必须全在展示/排序路径（禁止 `if health_score < X: block`） |

**验收标准（GWT）**：

- Given 一个 skill 有 2 error + 1 warn + 1 个 degraded 折旧维度，When 重算健康度，Then score = 100−20−3−8 = **69**，且下钻面板逐条列出扣分明细与原始值（NFR-10.3）。
- Given 上游跟踪未启用（E-08 未开），When 算健康度，Then `upstream_divergence = unknown`，score 不含其扣分，UI 显示「未知 1 项」。
- Given error_count = 15，When 重算，Then score = 0（不下溢为负）。

**边界**：健康度重算与门禁判定解耦（门禁只看 `GateResult.has_error`，NFR-10.5）。

**优先级**：Must。

### E-02 折旧三维判定口径（基线：FR-1.0.23 / NFR-10.4）——本批最重缺口

**规则**：

| # | 维度 | 口径 |
|---|---|---|
| E-02.1 | `staleness` 输入 | ① `days_since_last_commit`（该 skill 在 canonical 的最近一次 commit 距今天数，UTC）；② 被引用次数 = `skill_dependencies` 反向入度 + 正文相对路径被其他 skill 引用次数 |
| E-02.2 | `staleness` 阈值（`core/constants.py`） | `STALENESS_DEGRADED_DAYS = 90`（**用户拍板 2026-10-24**）；**被引用次数 ≥1 时放宽一档至 180 天**（估算，常量可调）—— 被引用的资产不算僵尸。decay 状态集为 `ok/degraded/unknown`，无 warn 档 |
| E-02.3 | `dependency_broken` 判定 | 依赖声明格式定为 frontmatter `dependencies: [slug, ...]`（YAML list）。判定分两层：① 声明的 slug 在库内不存在 → degraded；② 库内存在但该 skill 的所有 binding 所在 Runtime 上依赖无有效 binding → degraded |
| E-02.4 | `dependency_broken` 容错 | 声明格式无法解析（非 list、slug 非字符串）→ `unknown`，同时在 gate 层出一条 info（`fm.dependencies.format`），**不猜**（NFR-10.4） |
| E-02.5 | `upstream_divergence` | 维持 `unknown` 直至 E-08 启用；启用后语义见 E-08.3 |
| E-02.6 | 落库 | 全部写入 `skill_checks(scope=decay)`，`value` JSON 存原始测量值 `{days_since, inbound_refs, declared_deps, missing_deps...}` 供 UI 下钻 |
| E-02.7 | 禁令 | 不读 DB `updated_at` 参与新鲜度判定（T16 既有禁令，重申） |

**验收标准（GWT）**：

- Given skill 最后 commit 距今 200 天且零被引用，When 跑折旧，Then `staleness = degraded`，`value.days_since = 200`。
- Given 同上但该 skill 被引用 2 次，When 跑折旧，Then 阈值放宽至 180 天；200 > 180 → `staleness = degraded` 仍成立，且 `value` 含 `relaxed_by_refs: true`，UI 呈现「陈旧，因被引用已放宽阈值」。

- Given 依赖声明 `dependencies: [api-automation]` 且库内无此 slug，When 跑折旧，Then `dependency_broken = degraded`，message 列出缺失 slug。
- Given 依赖声明是字符串 `"api-automation"` 而非 list，When 跑折旧，Then `dependency_broken = unknown` + gate 层 info 一条，UI 显示「未知 1 项」。

**边界**：时间源取 commit 的 UTC 时间；`days_since` 为负（时钟回拨）按 0 处理并记 warning 日志。

**优先级**：Must。

### E-03 门禁规则清单验收与 ID 稳定性（基线：FR-1.0.11 / 04 §2.1.4）

**规则**：

| # | 规则 |
|---|---|
| E-03.1 | 内置 11 条规则（`fm.name.required` … `asset.untracked`）逐条对照 `04` §2.1.4 表验收：每条有对应实现 + 至少 1 个单测 |
| E-03.2 | **规则 ID 是稳定契约**：Web 下钻、MCP 错误信封（`GATE_FAILED` 明细）、CLI `--json` 输出均引用它。重命名/删除规则 = 破坏性变更，须在 `00` 立项 |
| E-03.3 | 阈值常量归位：`DESC_MIN_CHARS=30`、description 上限 500、token 估算 150 → 集中 `core/constants.py`（`DESC_MIN_CHARS` 现散落在 `checks.py:67`） |

- Given 同一快照，When 分别跑 `check` 与 `push` 前置，Then 两处 findings 逐字段相等。
- Given `fm.description.required` 失败，When push（不带豁免开关），Then 中止，错误信封含 `rule: "fm.description.required"`。

**优先级**：Must（同时是 N-03 的地基）。

**规则**：

|---|---|

- Given 同一库跑两次 check 且无变更，When 比对结果，Then `skill_similarity` 无新增行（幂等）。

### E-05 Change Request 流程状态机（基线：FR-2.3.3）

**现状**：`change_requests.status` 仅 `open/merged/closed`；`cr_service.py` 8 行薄壳，无审查门槛、无合并门禁、无通知。

**状态机**（迁移：扩展 CHECK 约束）：

```
open ──审查通过──→ approved ──执行合并──→ merged（终态）
open ──审查拒绝──→ rejected（终态，可再评论）
open / approved ──撤回/关闭──→ closed（终态）
```

| # | 规则 |
|---|---|
| E-05.1 | 状态迁移表：`open→approved`（≥1 名有审查权者，owner/member；viewer 403）；`open→rejected`（必须填拒绝理由）；`approved→merged`（提交者或 owner 执行）；`→closed`（提交者撤回或 owner 关闭）。**merged / rejected / closed 均终态，禁止回跳** |
| E-05.2 | **合并前置门禁**：`approved→merged` 时对 CR 目标快照跑 `run_gate`（与 push 前置同一实现，NFR-10.5）；`has_error` → 拒绝合并，CR 退回 `open`，评论区附 `GATE_FAILED` 规则明细 |
| E-05.3 | 并发冲突：合并时 canonical 已前进（`base_hash` 不匹配）→ `409 STALE`，提示刷新重提交，**绝不静默覆盖**（NFR-3.1 同源） |
| E-05.4 | 通知（最小版）：WS 事件 `cr.updated`（type/status 变更），前端 `invalidateQueries`；**不做邮件/IM 推送**（记后续版本） |
| E-05.5 | 合并动作 = canonical commit（走既有 git 白名单路径），天然进溯源（FR-1.0.22）与可回滚 |
| E-05.6 | 指向的 skill 被删除 → CR 自动 `closed` + 系统评论说明 |

**验收标准（GWT)**：

- Given CR `open` 且目标快照 gate 有 error，When 尝试合并，Then 拒绝，CR 回 `open`，评论区出现 GATE_FAILED 明细。
- Given CR `rejected`，When 再次评论，Then 评论成功、状态不变。
- Given viewer 角色，When 执行审查，Then `403 FORBIDDEN`。
- Given CR `open` 且目标 skill 被删除，When 下次同步，Then CR 自动 `closed` 且有系统评论。

**边界**：评论内容长度截断（8000 字符，估算）；状态迁移全部落审计（复用不可变审计通道）。

**优先级**：Should。

### N-01 Skill 使用遥测（本地 + 云端一步到位）｜V2-FR-01｜Must

**目标**：让"僵尸 Skill 占比"从 staleness 推断变为实测调用 —— L2 管理者视图从"能看"到"可信"的关键一跳。

**方案对比（已拍板）**：

| 方案 | 取舍 | 结论 |
|---|---|---|
| A. 仅本地聚合 | 隐私面最小，但团队口径的僵尸占比做不出来 | 不选 |
| B. 本地 + 云端一步到位 | 多约一倍工作量（云端聚合 + 隐私开关 + 上报通道），换来团队级实测指标 | **选**（用户 2026-10-24 拍板） |

**需求规则**：

| # | 规则 |
|---|---|
| N-01.1 | **使用事件定义**（唯一定义处）：经 skillos 通道对某 Skill 的读取或修改——① MCP：`skillos_get_skill` / `skillos_status`（单 skill 级）/ `skillos_sync_push` / `skillos_sync_pull`；② Web：详情页打开（触发 file_read）/ 编辑保存（base_hash 写）/ push/pull；③ CLI：`status`（单 skill）/ `log` / `push` / `pull`。**Dashboard 总览打开、全库 scan、批量列表页不计** |
| N-01.2 | 采集位置：daemon 统一落事件（MCP/WS 任务/CLI 均经 daemon 或本地服务层挂钩）；**只记事件不记内容** |
| N-01.3 | 本地聚合：使用计数按日聚合成 `skill_usage_daily(skill_id, date, via, count)`，保留 180 天（估算），过期清理；**原始事件默认不落盘** —— N-11 启用后另存轻量事件表（30 天，见 §8.6） |
| N-01.4 | 云端聚合：`skill_usage_daily` 云端同构表；上报走 WS 任务通道新 op `usage_report`（**具名领域操作**，符合 OUT-14 白名单原则，非通用透传）；每日批量上报一次 |
| N-01.5 | **隐私开关**：设备侧 `usage_report_enabled`，**默认 off**；首次启用团队功能时引导开启并明示上报内容（skill 标识 + 计数 + 日期，无内容无路径）；关闭状态**零上报**（可测试断言，NFR-V2-03） |
| N-01.6 | 团队视图聚合口径 V1：只见「该 skill 全团队总调用次数」，**不看个人明细**（个人明细留后续版本且需再次确认） |
| N-01.7 | **僵尸口径（用户拍板 2026-10-24：旧口径不保留）**：V2 僵尸 = 近 90 天（复用 E-02.2 常量）零调用 **且** `staleness=degraded`，双条件；旧口径（仅 staleness）**不保留展示**，管理者视图口径唯一，UI 注明构成（调用数据 + 折旧） |
| N-01.8 | Dashboard 新增「近 30 天调用 Top / 零调用」两个列表；管理者视图僵尸占比按 N-01.7 新口径计算 |
| N-01.9 | 断连补偿：daemon 离线期间本地聚合照常累积，重连后按日补报（服务端按 skill+date 去重合并）；时钟回拨以服务端收到时间为准记当日 |

**数据模型**：新表 `skill_usage_daily`（本地 + 云端同构）：`id, device_id, skill_id, date, via(CHECK mcp/web/cli/daemon), count, UNIQUE(device_id, skill_id, date, via)`。

**验收标准（GWT）**：

- Given MCP 调用 `skillos_get_skill(A)` 3 次（当日），When 次日聚合，Then `skill_usage_daily[A] via=mcp count=3`。
- Given `usage_report_enabled=false`，When 聚合完成，Then 无任何 `usage_report` 任务产生（断言零上报）。
- Given 某 skill 90 天零调用且 staleness=degraded，When 管理者视图，Then 进入僵尸列表且口径标注「实测+折旧」。
- Given A 机离线 3 天累积聚合数据，When 重连，Then 3 天数据按日补报且云端无重复行。

**边界**：`count` 无上限（int）；单设备单日事件量异常（>10000，估算）告警不阻断。

### N-03 门禁规则自定义（YAML 声明式）｜V2-FR-02｜Should

**方案对比**：

| 方案 | 取舍 | 结论 |
|---|---|---|
| A. YAML 声明式（正则/存在性/字段校验） | 表达力有限，但**零任意代码执行面**、随 git 版本化、与元数据版本化（FR-1.0.30）同构 | **选** |
| B. 插件式（Python 钩子） | 表达力强，但引入任意代码执行 + 依赖隔离问题，与安全叙事冲突 | 不做（v1 明确排除） |

**需求规则**：

| # | 规则 |
|---|---|
| N-03.1 | 规则存放：仓库 `.skillos/rules/*.yaml`，随 commit 版本化；规则集变更 → 下次 check 生效 |
| N-03.2 | Schema：`rule_id`（**必须 `custom.` 前缀**，与内置 ID 冲突 → 仓库校验显式报错）/ `level`(error/warn/info，error 可拦 push，同内置语义) / `target`(description/frontmatter/file_content/file_list) / `match`(pattern + regex 开关 + flags) / `scope`(paths/exclude，可选) / `message`(必填，中文用户可读) |
| N-03.3 | 限额：单仓库 ≤200 条（估算）；单条正则匹配超时 100ms（估算）→ 该次匹配记 warn「正则超时」，不中断其他规则 |
| N-03.4 | 单规则失败隔离：正则编译失败 → 该规则落库 `invalid`（info 级 finding），**不静默跳过**，其余规则正常执行 |
| N-03.5 | 规则集版本：每次 check 将生效规则文件聚合 hash 落 `skill_checks.ruleset_hash`（新字段），历史结果可复现 |
| N-03.6 | **无代码执行**（架构断言，NFR-V2-05）：规则引擎禁止 import/eval 用户任何内容；测试断言规则文件中注入的 Python 片段不会被执行 |
| N-03.7 | MCP 路径同样受自定义 error 拦截，无绕过开关（NFR-10.2 扩展到自定义规则） |

**验收标准（GWT）**：

- Given `custom.no-secrets` level=error 命中 SKILL.md，When push，Then 拦截且信封 `rule=custom.no-secrets`。
- Given 某规则正则非法，When check，Then 该规则落库 invalid(info)，其余规则 findings 正常。
- Given 规则文件被改动并 commit，When 再跑 check，Then `ruleset_hash` 变化且历史行不变。

**优先级**：Should（N-08 的地基）。

### N-08 Skill 安全扫描｜V2-FR-03｜Should

**形态**：随包预置的安全规则集（复用 N-03 引擎）+ 规则类别标签 `category: security`。**L3 企业叙事的第一块砖**（对应 `08` §4"公司多一层：合规吗 + 有没有泄露密钥"，此前无 FR 承接）。

| 类别 | 示例规则 | 默认级别 |
|---|---|---|

| 通用凭证 | `ghp_` / `sk-` / `xoxb-` / `Bearer ` 模式 | **error** |
| 私钥块 | `-----BEGIN ... PRIVATE KEY-----` | **error** |
| 连接串 | `password=`、`postgres://user:pass@` | warn |
| 危险命令 | `rm -rf /`、`curl … \| sh`、`sudo` | warn（误报可能高） |
| 外发地址 | 明文 `http://` + 非常见域名 | info |

**需求规则**：

| # | 规则 |
|---|---|
| N-08.1 | 预置规则以 N-03 规则文件形式随包附带（`builtin-security` 规则集），用户可改级别、可删（自带 git 版本化） |
| N-08.2 | **白名单机制**：`.skillos/rules/ignore.yaml`（`rule_id + path 模式 + 理由`，随 git 版本化）；命中 ignore 的不产生 finding，但 ignore 记录本身落库可审计 |
| N-08.3 | **大文件例外**：`in_git=false` 的超阈值文件（FR-1.0.20）**仍参与安全扫描**（只读匹配、不进哈希）——这是 T2/FR-1.0.20 的显式例外，需回写 `00` 标注 |
| N-08.4 | 误报处理：不给硬性误报率指标（无基线）；误报通过 ignore.yaml + 调级别消化，命中数据进 N-02 报告 |
| N-08.5 | check 默认包含 security 类规则；`skillos check --security-only` 提供单独入口（CI 用） |

**验收标准（GWT）**：

- Given 某 skill 脚本含 `ghp_xxxx`，When check，Then error 级 finding，push 拦截。
- Given ignore.yaml 覆盖该路径，When check，Then 无该 finding，且 ignore 记录可在规则面板审计。
- Given 5MB 超阈值二进制旁路文件含密钥串，When check，Then 仍命中（E-08.3 例外生效）。

**优先级**：Should。

### N-11 调用可观测性：token 计量与执行路径｜V2-FR-05｜Must（用户 2026-10-24 评审追加）

**硬边界先说清**：Skill 的执行者是 Agent Runtime（Claude Code / Codex / WorkBuddy…），token 消耗发生在 LLM/Runtime 侧。skillos 的 MCP 通道**天然只能看见"自己被调了什么"**，看不见 Agent 的 token 与会话过程。所以本功能是**分层取数**，每层可靠性不同，UI 必须标明数据来源，禁止把估算呈现成精确计量。

**方案对比**：

| 方案 | 取舍 | 结论 |
|---|---|---|
| A. 全量接管执行（skillos 起 Agent 沙盒跑 Skill） | 数据最全，但等于自建 Agent 执行平台，与 OUT-2（运行时评测）/ OUT-4（编排）相邻，范围爆炸 | 不做 |
| B. 分层观测（通道内自记 + Runtime 会话日志适配器） | L1 精确但只有通道内事件；L2 靠解析 Runtime 本地留痕，覆盖率取决于 Runtime 是否留痕；工作量可控 | **选** |
| C. 要求 Runtime 上报（改造各 Runtime 埋点） | 不可行 —— Runtime 是第三方/上游产品，改不动 | 不做 |

**三层数据源**：

| 层 | 数据 | 来源 | 可靠性 | 期次 |
|---|---|---|---|---|
| L1 通道内观测 | 调用事件：skill_id / op / via / duration_ms / ok / session_id / 参数摘要 | skillos 自记（MCP 工具入口 + WS 任务处理 + CLI 服务层挂钩） | **精确** | 本期 |
| L2 Runtime 会话观测 | token 用量（input/output/cache）、会话内调用序列 | Runtime 本地会话日志适配器（如 Claude Code 的 session JSONL 自带 usage 字段） | 取决于 Runtime | 本期做 **Claude Code 适配器**，其余留接口 |
| L3 执行路径（trace） | 一次任务内的调用链（A→B→失败点） | L1 + L2 按 session_id 关联 | 估算级 | L1/L2 落地后 |

**需求规则**：

| # | 规则 |
|---|---|
| N-11.1 | L1 事件模型：新增本地表 `skill_usage_events(id, session_id, skill_id, op, via, duration_ms, ok, at)`，**保留 30 天**（估算，可配）；长期数据全在日聚合层（180 天） |
| N-11.2 | L1 覆盖点与 N-01.1 使用事件定义同源（多记字段、不改定义）：MCP 工具入口、WS 任务处理、CLI 服务层；Dashboard 浏览 / 全库 scan 不记 |
| N-11.3 | **token 归属口径（估算，唯一定义处）**：token 无法精确归属单个 skill（一次会话常有多 skill 参与）。归属规则 = **时间片归属**：会话内某 skill 调用事件之后的 usage 片段归该 skill，直到下一个不同 skill 的调用事件；无任何 skill 调用的会话 usage 归 `unattributed`。UI 一律标注「估算口径」，**禁止用于计费/考核类精确决策** |
| N-11.4 | L2 适配器契约：`skillos telemetry import claude-code`（手动）+ daemon 定时扫描（默认关，手动优先 —— 解析量与隐私面都可控）；解析对象为 Claude Code 本地会话 JSONL 的 usage 字段；**skill 关联**按「会话内工具参数/文件路径命中该 skill 部署目录」匹配，未命中不强行归属。**路径解析优先级：手动指定（N-11.9）> 自动探测** |
| N-11.5 | L2 扩展性：适配器按 Runtime 注册（路径即数据思想 —— 加 Runtime = 加一份解析配置，不加引擎代码）；Codex / WorkBuddy 留接口不实现（留痕格式待调研后按此模式扩展） |
| N-11.6 | 聚合扩展：`skill_usage_daily` 增列 `tokens_in / tokens_out / duration_ms_p50 / duration_ms_p95 / by_op(JSON)`；云端上报仍**只报聚合值**（事件级含参数摘要，隐私面大，不上云） |
| N-11.7 | 执行路径呈现：Skill 详情新增「调用记录」tab —— 近 100 次调用（时间 / op / 耗时 / 结果 / token）+ 按 session 的调用链视图（L3：session 内顺序 A→B→error）；均为本地数据 |
| N-11.8 | 隐私双开关：`usage_collect_enabled`（本地采集，**默认 on** —— 是用户自有数据）与 `usage_report_enabled`（云上报，**默认 off**，Q-04 决议）相互独立；L2 解析**不落盘会话正文**，只提取 usage 数字与 skill 关联所需字段；JSONL 损坏行跳过并计数 |
| N-11.9 | **Runtime 会话路径手动指定（用户 2026-10-24 评审追加）**：自动探测不可靠（自定义安装 / 便携版 / 非默认 HOME / 多实例），必须支持手动指定。① 配置键 `telemetry.runtime_paths`（map：runtime 名 → 目录列表，**支持多路径**，适配多实例/多 profile）；② 两个设置入口等价：Web 设置页「遥测 → Runtime 路径」表单 + CLI `skillos telemetry path set <runtime> <path...>` / `path show` / `path clear`；③ 手动路径存在时**跳过自动探测**，逐路径扫描且互不覆盖；④ 校验：路径不存在或目录内无匹配文件（如 `*.jsonl`）时 import **报错并列出已尝试的路径清单**，不静默产空结果；⑤ 路径配置**不参与云端上报**（本地路径属隐私面） |

**验收标准（GWT）**：

- Given MCP 调用 `skillos_get_skill(A)` 耗时 120ms 成功，When 查调用记录，Then 事件含 `op=get_skill, duration_ms=120, ok=true`。
- Given Claude Code 会话 JSONL 含 3 条 usage 且期间先后调用 skill A、B，When `telemetry import`，Then A、B 按时间片分得 token，余量归 `unattributed`，UI 标注「估算」。
- Given `usage_collect_enabled=false`，When 任意调用发生，Then `skill_usage_events` 零新增行。
- Given 事件表存在 31 天前的数据，When 日终清理，Then 过期事件删除、对应日聚合保留。
- Given JSONL 中间有 1 行损坏，When import，Then 跳过该行、其余正常解析，汇总报 `skipped_lines=1`。
- Given 手动配置了 `telemetry.runtime_paths["claude-code"] = [D:/custom/cc-projects]` 且目录含会话 JSONL，When `telemetry import claude-code`，Then **只扫描该路径**（跳过自动探测），正常解析出 usage。
- Given 自动探测目标目录不存在且未配置手动路径，When `telemetry import claude-code`，Then 报错并列出尝试过的路径清单与提示「可在设置中手动指定 Runtime 路径」，**不产出空聚合**。
- Given 配置了 2 个手动路径（多实例），When import，Then 两路径扫描结果合并去重（同一 session 文件只计一次），汇总报两路径各自的解析行数。

**边界**：duration 含锁等待（用户视角总耗时；拆分留后续）；多 Runtime session 键 = `runtime + session_id` 不冲突；一次调用触发多 skill 依赖时 token 归**发起调用**的 skill（被依赖方不重复计）。

## 九、方案级设计（N-06 / N-10，解冻 OUT-11 / OUT-17）

> 两项均为**方案级立项**（用户 2026-10-24 拍板）：本文档给方案与分阶段路径，**不写 FR 级验收**；解冻前置条件全部满足并经基线变更流程后再立 FR 细化。

### V2-DES-01 块内合并（解冻 OUT-11）

**定位**：冲突整文件四选一（FR-2.2.6）之上的第五选项「逐块合并」，**仅 Web 人工路径**；MCP 仍只有四选一（工程红线 12：MCP 参数不得出现新决策形态）。

**技术可行性前提（基线已具备）**：base = `render(canonical@installed_commit, installed_adapter_version)` 可精确重建（FR-1.0.18 + 纯函数 render，NFR-3.5）→ 三方 diff3 输入可靠，这是块内合并成立的前提，不需要新基建。

**算法思路**：`diff3(base, local, remote)` 纯函数（进 `core/algorithm/`，云端可复用，分层合规）→ 输出块序列 `unchanged / only-local / only-remote / conflict`；UI（MergeEditor，基于 Monaco diff 扩展）对 conflict 块左右对比逐块选择；写入仍是**整文件写回 + base_hash 乐观锁**（不引入新写入协议）。

**与既有安全机制的关系**：`keep_blocks` 作为冲突决策新增枚举值，决策前快照语义不变（FR-2.2.6）；快照可撤销继承。

**解冻前置条件**：① `docs/00` 移除 OUT-11 并立 FR；② L2 多人并发编辑真实出现（以 N-01 数据佐证）；③ Monaco diff 扩展技术评估通过。

**分阶段**：P1 diff3 引擎 + 只读块视图（2~3 人日）→ P2 逐块选择 + 整文件写回（4~5 人日）→ P3 与 CR 合并（E-05）整合（2~3 人日）。合计约 10~14 人日。

### V2-DES-02 对象级合并 + 跨设备冲突传播（解冻 OUT-17）

**定位**：以 Skill 为单位的合并对象化：A 机产生的未决策 CONFLICT（pending），在 B 机可见并可接手决策。

**技术思路**：pending 冲突作为**协作元数据**存入仓库 `.skillos/`（T19 已有元数据随仓库版本化通道，不新建同步机制）；云端 `sync_records` 已记录冲突事实 → 跨设备传播 = 云端下发 pending 列表 + 本地按 `skill_id` 关联展示；B 机决策结果经既有 `resolve-conflict` 路径回写。

**依赖**：强依赖 V2-DES-01（对象级视图需要块级展示能力）；依赖 E-05（CR 与冲突决策的统一入口）。

**解冻前置条件**：① `docs/00` 移除 OUT-17 并立 FR；② 多设备/多成员并发编辑成为常态；③ V2-DES-01 P2 落地。

**分阶段**：P1 pending 元数据结构 + 云端传播（3~4 人日）→ P2 跨设备决策接手 UI（3~4 人日）。
