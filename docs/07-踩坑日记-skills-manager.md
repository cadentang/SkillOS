## §1 六条直接改我们设计的结论

这六条不是"参考"，是**我们 00/04/05 三份文档里已经写错、或写得不够狠的地方**。对方用真实用户的数据丢失事故换来的，我们没有理由再踩一遍。

### 【D1】适配器路径不能当常量，必须当数据 + 带"验证依据"

**这是整份 CHANGELOG 里最尖锐的一处矛盾**：同一个 Codex 路径，对方在两个版本给出了**相反**的结论，两条都写得很肯定：

- `1.19.x`（#143 / #147）：*"Codex 按官方文档只从 `~/.agents/skills` 读取用户级技能，但 skills-manager 之前部署到 `~/.codex/skills`（codex 根本不读）且不扫 `~/.agents/skills`。现在部署和发现都改对。"*
- `1.22.2`（#182）：*"技能现在部署到 `~/.codex/skills/`，也就是 Codex CLI **实际读取**的位置。此前版本写到了 `~/.agents/skills/`，导致已安装的技能在 Codex 中根本不显示。"*

**同一个文件里，前一次说 A 对 B 错，后一次说 B 对 A 错。** 再看其余三个适配器的同类事故：

| 适配器        | 事故                                                                                                                       | 版本           |
| ---------- | ------------------------------------------------------------------------------------------------------------------------ | ------------ |
| Kimi Code  | 写到 `~/.config/agents/skills`（**上一个世代** kimi-cli 的位置），实际读 `$KIMI_CODE_HOME/skills/`。同步显示成功、Kimi 里什么都没有；装了 Kimi 还被显示为"未安装" | 1.35.0（#270） |
| GitLab Duo | 部署到 `~/.gitlab/duo/skills`，但 Windows 实际读 `%APPDATA%\GitLab\duo\skills`，**该版本尚不能自动识别**                                    | 1.39.0（#433） |
| OpenCode   | 项目级误装到 `<project>/.config/opencode/skills`，实际是 `<project>/.opencode/skills`                                              | 1.19.0       |
| 通用教训       | 路径**从对方源码读出来的**（`packages/util/home-paths`、`packages/skill/skill-filesystem`），**不是照搬 README**                            | 1.34.0       |

**根因**：Agent 的 skill 目录是**上游的私有实现细节**，无标准、随版本漂移、官方文档常年滞后。任何"写死的常量表"都会在某个上游版本后静默失效——而且失效形态是最坏的：**部署报成功，agent 里什么都没有**。

**他们的解**：`ToolAdapter` 结构体里同时持有 `relative_skills_dir`（部署）+ `additional_scan_dirs`（**仅发现、不部署**）+ `override_skills_dir`（用户覆盖）；`recursive_scan` 控制是否递归。

**→ 我们**（改 `04 §2.1` + `05`）：

1. **路径写进适配器数据，不写进代码常量**，且每条带 `verified_at`（日期）+ `evidence`（源码 / 实测 / 官方文档）+ `fallback_dirs[]`。
2. **部署根 ≠ 发现根**，必须分开建模。我们的 `runtime_bindings` 要加 `scan_only_dirs`（扫但不推），这是对方用 #143→#182 的反复换来的结构。
3. **部署后必须自证**：写完立刻回读目标路径并确认存在（对方 1.31.0 才补上"部署命令会核对数据库记录和文件系统状态后才报告成功"）。**"我写成功了"和"它在那"是两件事。**
4. **回答 06 里的待核实项**：Codex 到底读哪个——答案是**上游自己改过主意，所以两个都要扫，部署选一个 + 可覆盖**。这条不确定不该被"查清"消除，应该被"结构上容忍"消除。
5. 用户可覆盖路径是**必需功能不是 nice-to-have**（GitLab Duo 的 Windows 用户至今只能手改）。

### 【D2】禁止用"数据库写入时间"判断新鲜度

**事故（1.34.2）**：项目副本的同步状态，是拿**项目副本的文件时间戳**去&#x6BD4;**"中央库那行数据库记录的写入时间"**。而"在中央库里改文件"不推动那个字段，"只改元数据"的写入却会推动它。于是：**你刚改过的副本显示成"中央库更新"，照着这个状态点拉取，你的改动就被覆盖了。**

**根因**：把"记录的时间"当成了"内容的时间"。这两个是完全不同的东西，且在"内容没变但元数据变了"时必然分叉。

**他们的解**：`classify_sync_status` 只遍历中央目录一次，**实时 hash 比较和最新内容 mtime 都来自这次遍历**，取代了原来的"一次遍历 + 一次读库"——**没有新增开销，也不需要为此加缓存**。配套：1.25.1 重建索引时若内容未变化，**必须保留原时间戳**。

**→ 我们**（改 `04` 漂移模块）：我们的漂移 7 态里有 `OUTDATED`，判定依据必须写死为"**内容 hash 不等**"作为第一判据，mtime 只在内容已确定不同之后用于**提示方向**，绝不单独用于判定"谁更新"。并且要在 `04` 里明文禁止读 `updated_at` 之类的 DB 列参与漂移判定。

### 【D3】"状态分类"不能当"安全证明"——无法证明安全时一个字都不写

**事故（1.35.1，#322/#327）**：一个 skill 有 5 个 agent 副本，卡片亮起"更新到中心"。但只要**任意一份**被改过就会亮，而实际推上去的是 **agent 名称字母序排第一的那份**。于是：在配了 Claude Code 的项目里改 Codex 那份 → 推的是没动过的 Claude 副本 → **提示成功，改动一个字都没到中心**；而刚被写过的中心随后又显示"更新"→ 用户顺着卡片点"更新到项目" → **那份修改就没了**。

**根因（作者自己的复盘，值得逐字读）**：

> `classify_sync_status` 只有在内容 hash 已经不同之后才会走到 `center_newer`，然后按 mtime 分边——**它并不能证明项目副本是多余的**。而对齐逻辑把它当成了证明，拒绝的门槛又画在"被编辑过"而不是"能证明干净"上。  
> 推送会重建中心目录、把它的 mtime 变成当前时间，**这正是让每一份被丢下的副本变成 `center_newer` 的原因**——而处于该状态时，卡片上仅剩的操作会覆盖全部副本。

**他们的解**：**"无法证明安全时，一个字都不写。"** 一个 skill 若有超过一份副本不处于"已同步"状态，本次更新**整体拒绝**并说明冲突，而不是挑一份推、把其余悄悄丢下。**只有"已同步"能证明副本没有独有内容**——因为它是内容比对的结果。

**→ 我们**（改 `04` 分发模块 + MCP 契约）：

1. 我们的 `push` 要引入**同样的判据分层**：`SYNCED` = 内容 hash 相等（唯一可作证明的状态）；其余六态（MISSING / OUTDATED / MODIFIED / UNMANAGED / ORPHANED / CONFLICT）**一律不可作为"可安全覆盖"的依据**。
2. 多 binding 场景（一个 skill 推到四个 runtime）必须做**前置全量检查**：任一 binding 非 SYNCED → 拒绝整体操作，返回冲突详情。这条要进 `04` 的关键流程时序。
3. 这条对 MCP 尤其重要：我们的 MCP 写入类工具默认 `dry_run=true`，但**干跑的判据必须是真实判据**（见 D6/N17）。

### 【D4】文件夹级替换 = 静默销毁用户数据，必须有 removals 守卫

**事故（1.34.0，#256）**：更新是**整个文件夹替换**。报告者丢了 `ppt-master` 生成到自己 `templates/` 里的 PPT 模板，**事后才发现**。以复制模式部署的 agent 目录、重新导入本地技能、重新指向来源，**四条路径都同样危险**。

**他们的解（`core/removals.rs`，只回答一个问题：哪些路径存在于当前树而不存在于替换树）**，里面每条都是踩出来的：

| 设计点                                            | 理由（原文）                                                                 |
| ---------------------------------------------- | ---------------------------------------------------------------------- |
| **按路径比较，不按内容**                                 | "内容变了的文件更新后仍然存在，列出来只会淹没真正会消失的那些"                                       |
| **整个不存在的目录只上报一行**                              | 否则用户自建的嵌套 `.git` 会用几千个 object 文件淹掉弹窗                                   |
| **文件 / 目录 / 符号链接之间的形态变化一律计为移除**                | 形态变了就是数据形态变了                                                           |
| **对既不能确认存在、也不能确认不存在的路径返回错误而不是猜**               | "**一个错误的『什么都不会丢』正是这个模块要防的那种失败**"                                       |
| **比较对象是真正会被换进去的暂存树，不是原始 clone**                | `copy_skill_dir` 会跳过 `.git` 和符号链接，拿 clone 比会产生真实的假阴性                   |
| **无人值守的更新永不替用户做决定**                            | 启动批量更新、后台调度器、CLI **一律跳过**该技能（`held_back_removals`），角标保留，用户手动更新时才看到具体路径 |
| **批准绑定到「修订版 + 排序后的精确路径集合」的 SHA-256**           | 确认调用会重新 clone、重新暂存并重算；集合对不上就**再次询问**，而不是拿过期答案去动手                       |
| **`StagedPathGuard` 在 drop 中清理暂存目录，只在替换成功后释放** | 否则中间失败会留下 `.staged-<uuid>` 被元数据重建**当成一个新技能收编**                         |
| **审计日志把被拦下的更新如实记为 "held back"**                | 而不是记成一次成功的无变化                                                          |

**并且他们诚实标注了限制**：比较的是**路径不是内容**，你改过的、新版本也有的文件路径仍会被判为"幸存"，改动照样被静默覆盖 → **"请把个人改动放在技能文件夹之外"**。

**→ 我们**（改 `00` 需求 + `04`）：

1. 新增需求：**"会删文件的更新/分发必须停下并列出路径"**，且这条要覆盖我们的**四条写入路径**（push 到 runtime / import 纳管 / 换源 / 版本回滚），不只是 push。
2. `push` 的 dry-run 必须输出 `held_back_removals` 同构字段（路径 + 位置标注，因为我们的副本可能同时在 repo、runtime A、runtime B）。
3. **`dry_run` 与真实执行的判据必须是同一份代码**（对方 #483 专门修过：`--dry-run` 会报告真实运行时会遇到的冲突）。
4. 我们的原子写 9 步协议里，**第 3 步"写临时目录"必须带同样的守卫**，且暂存目录要有 drop 清理语义——否则 `.staged-*` 会被我们的 `scan` 误收编成新 skill。这条直接补进 `04 §2.2.0`。
5. 这条也是我们相对对方的**加分点**：他们只做路径比较且明说了局限，我们若在 hackathon 里做到"路径 + 内容双判"就是明确的差异化叙事。

### 【D5】锁归锁，网络归网络；热路径上禁止 fsync

**事故 A（#315）**：检查更新时"要向每个远端问最新版本号，被限流时能耗 30–57 秒"。**过去整个网络往返都握着中央仓库锁**，于是这期间用户做的任何操作——安装、更新、重新链接——等满 20 秒后直接失败，报 `skills repository is busy`。

**他们的解**：**两段式**。第一段在锁**外**：按 `(clone_url, branch)` 去重、最多 8 个并发 `git ls-remote`；第二段才逐技能取锁，只用来写状态列。**锁从 30 秒降到毫秒级。**

顺带踩出一个竞态：把"解析"和"写入"拆开后，重装会保留技能记录、只改写来源，于是**从旧远端读到的版本号可能被写到新来源上**。修法：每个预取结果带上**它被解析时的** `(clone_url, branch)`，写入侧从**重新读到的**记录重算这个键并比对，不匹配就丢弃。

**事故 B（1.40.0，macOS）**：每次获取中央仓库锁都会 **fsync 锁标记文件**。而 macOS 上这会**刷新整个卷的缓存**，把其中所有脏页（**包括其他进程的**）都算到本应用头上。约 75 个技能的库每轮就是 75 次全卷屏障，持续一小时被系统记为 **2.1 GB 的 "file backed memory dirtied"，超出磁盘写入上限 24 倍**。

而那个标记文件的用途只是"在『仓库忙』提示里说明是谁占着锁"——**互斥来自 `flock`，与文件内容无关**。

**→ 我们**（改 `02` 技术设计 + `04`）：

1. 我们的 daemon 有"每轮 scan + drift 计算 + 可选 check"的循环，必须明确：**网络 I/O 永不在锁内**；锁只保护"读/写 repo 与 bindings 的那一小段"。
2. 锁实现选 `filelock`（我们 05 已定），但要补一条**禁止在持锁期间做 fsync / 全量 rename / 目录 mtime 更新**的约束。
3. 我们的 `version_log`（从对方 MCP 危险工具改来的那个）如果要做提交/回滚，必须走**单锁事务命令**，而不是前端编排 commit/pull/push 三段——对方 1.28.0 专门加了 `git_backup_sync` 取代三段编排，并在 push 被拒时**锁内重试 fetch+merge ≤3 次**。
4. 预取键校验那条我们也要抄：任何"先算后写"的流程，写入前必须**重读记录重算键**。

### 【D6】哈希口径的单一事实源：枚举函数只有一份

**事故串**（这是他们修得最久的一类，横跨 5 个版本）：

| 版本     | 事故                                          | 根因                                                                                                        |
| ------ | ------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 1.22.4 | "有可用更新"徽标亮着，**Diff 标签页是空的**                 | 徽标对**整个目录**做哈希，Diff 只比 `SKILL.md`；`references/`、`scripts/` 的改动、文件增删、**可执行位变化**都会点亮徽标却显示空 diff             |
| 1.23.2 | 跑了 skill 的 Python 脚本后，副本**永久显示"中心有变更"**     | `__pycache__/*.pyc` 被算进内容哈希（symlink 模式不受影响，因为本来就是同一份文件）                                                   |
| 1.38.0 | 装第二个 skill 要重新下载整仓                          | 缓存无上限；**代理配置传给 `git fetch` 的位置是 git 直接拒绝的**，代理用户每次刷新都失败、每次装都从头 clone                                      |
| 1.39.0 | Windows + macOS **双端"永远可更新"**               | 逐字节比对，而 Git for Windows 默认检出时转换行尾 → 一台 CRLF 一台 LF → 永远不等；重新导入只是把中央库改成本地编码 → **两台机器来回推送，各自都看到对方刚"改"出来的更新** |
| 1.40.2 | 在本地导入源目录里跑 `npm install` 或建 venv → 被判为"有更新" | 依赖目录没排除                                                                                                   |

**他们的解（两条，都必须抄）**：

**(1) 枚举函数单一化**：抽出 `content_hash::list_content_files`，**哈希和 diff 共用**，确保"两者范围永不漂移"。

**(2) 行尾处理做成第二级比较，而不是直接进哈希**——这是最关键的设计取舍：

> 字节 hash `hash_entries` **未作改动，仍是每个技能的存储身份**。行尾比较是一个**独立且更严格的函数，只在两个字节 hash 已经不等时才被调用**，因此**不会作废任何已存 hash，也不需要迁移**。其余一切照旧：读不了的文件、进不去的目录、不是合法 UTF-8 的内容，都仍然按字节严格比较而**不是假定相同**。

**(3) 一处例外，必须记牢**：1.40.2 修"跳过依赖目录"时明确写了——「跳过依赖目录**只作用于更新检查的兜底比较，内容 hash 本身不变**」，因为「部分修复流程会在 hash 一致时替换目录，否则会**误删本地已安装的 `node_modules`**」。

**→ 我们**（改 `04 §2.1.3` 哈希口径 + `05`）：

1. **我们现在 05 里定的是"换行归一化 `\r\n`→`\n` 后进哈希"——这条要改。** 改成对方的两级结构：`hash_bytes`（字节级，存储身份，含路径 + 内容）→ 不等时再调 `compare_normalized_line_endings()` 作为第二判据。理由：**归一化进哈希会让"不可读文件 / 非法 UTF-8"的字节严格性被稀释**，而对方这条路径已经在生产上跑了一年多。
2. **枚举函数只有一份**，`scan`、`hash`、`diff`、`push` 的 removals 守卫**全部调用它**。
3. **排除集与"是否影响 hash"必须分开定义**，不能混成一个列表。至少三类：
   - 影响 hash（存储身份）：`.git`? → 不，`.git` 是 skip；
   - 不影响 hash 但影响更新检查（兜底比较用）：`node_modules` / `.venv` / `venv`；
   - 不影响 hash 也不影响比较（纯噪音）：`__pycache__` / `*.pyc` / `.DS_Store` / `Thumbs.db`。
4. 我们 04 里那张"超 5MB 文件不入漂移哈希但整个 skill 禁报 SYNCED"的设计，**方向和对方一致**（他们都是"宁可不算，也不给假 SYNCED"），可以互相印证。

## §2 适配器路径：这个赛道最脏的地方

D1 已覆盖核心。补充几条**结构性**教训：

| #  | 事故 / 设计                                                                                                                                                                                                                                                 | 版本                | → 我们                                                                                                          |
| -- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- | ------------------------------------------------------------------------------------------------------------- |
| N1 | **多个适配器共用同一目录**（Amp 与 Replit 都用 `~/.config/agents/skills`，Kimi 当时也在其中）。重定向某个工具时，清理陈旧目标的逻辑**直接删该路径，不检查还有谁指向它**                                                                                                                                           | 1.35.0            | 我们的"停用某个 runtime 时清理其目录"必须先做**引用计数**：还有别的 adapter 指向就不要删。`04` 适配器表要加 `shared_dirs` 检测                         |

**N25 展开——如果我们将来做"按需拉取单个 skill"，这四条一定会遇到**：

1. **窄检出必须拷贝缓存，不能用 `git clone --local`**：从 partial clone 克隆会让源仓库去提供它自己没有的对象，git 直接以 `could not fetch <oid> from promisor remote` 中止。
2. **`sparse-checkout set` 对仓库里不存在的路径是"成功"的**，只是那个路径不存在 → **结果必须先验证确实落到了一个 skill 才使用**。
3. **交给调用方的检出必须解除与 promisor 远端的关联**：git 从**三个设置中的任意一个**都会注册 promisor 远端，所以**三个都清掉**；否则调用方对这份检出直接跑 git 时，任何碰到未获取对象的命令都会**悄悄变成一次可能挂住的网络往返**。而且准确的说法是"不会有命令背着调用方去取对象"，**不是**"这个目录里跑什么都是本地的"。
4. **测试要断言结果而不是配置**：他们用真实的 `file://` partial clone 断言**结果**，"而不是断言设置的名字"。——这是很值钱的测试哲学，可写进我们的测试规范。

- **冲突永不阻塞同步、永不覆盖你的工作**：该技能保留本机版本，其余技能照常同步；三选一（保留本机 / 使用远端 / 两个都保留——远端版本以 `原名 (设备名)` 落地为普通技能）；**应用任一选择前都先建安全快照**。
- **元数据规范重建保证字节级收敛**（两侧合并同一对提交**产出相同树 OID**）——这是"可重复/可验证"的关键断言，值得我们借鉴为测试断言。
- **pending 冲突的真源是 commit trailer**（`Skills-Manager-Conflicts` / `Resolved`），随 push/pull 跨设备传播、**重克隆后可重建**；隐藏 refs 以 staging→promote 两段式钉住对端版本防 GC。
- **崩溃安全的应用序列**（pre-merge / applying 锚点）+ **启动恢复协议**（自动收敛工作区，用户改动**救援为快照 tag**，绝不静默覆盖）。

- **逃生舱**：`merge_engine=system` 作为退出开关；GUI 同步与 CLI `git pull` **共用同一门控路径**。
- **失败链路必须完整**：`classify_git_chain` 为所有错误保留完整 anyhow 链（`{:#}`）——因为"同步错误此前只显示最外层概要『object merge aborted』，**真正原因被吞掉**"。

### N30 · CHANGELOG 本身就是可借鉴的交付物

他们 1.22.2 专门重构了更新日志结构，从旧的 Added/Changed/Fixed/Removed 改成**按受众分三段**：

1. **发布概览** —— 一句话，用户能感知的
2. **用户可见更新** —— 每条都写"以前怎样 → 现在怎样 → 为什么"
3. **开发者与治理更新** —— 实现细节、为什么这么选、已知限制

并且**每条都带 `(#issue)` 编号**，且**诚实标注未修复/限制**（如 N9、N11、"路径比较不是内容比较"那条限制）。

**→ 我们**：这对黑客松是**直接可用**的素材：

- 我们的 README / Demo 叙事借用这个三段式；
- 尤其"**诚实标注限制**"这一条——在评审面前，**主动说出边界比假装完美更可信**；
- 我们的 `03-开发排期.md §7` 权威 Demo 剧本，可以按这个逻辑组织：先"能力总览"（用户能感知），再"漂移告警"（以前怎样→现在怎样），最后"底部能力"（为什么难）。

## §9 战略级观察

通读 19 个月的 500+ issue 修复史，有四个判断我认为可以直接用来校准我们的定位：

### 观察 1 · 这个赛道 90% 的难度在"本地状态一致性"，不在"分发"

数一下这 30 条编号项的分布：**路径/适配器 7 条、漂移/状态判定 7 条、删除安全 6 条、跨平台 19 条、git 底层 7 条**。真正关于"云端 / 协作 / 多人"的，**几乎是零**。

对方两年 5532 star，**全靠"本地文件系统 + 系统 git + 钥匙串 + 一个 GitHub 私有仓库"**，没有自建云端。

**→ 对 06 里那个待拍板项①的输入**：这强烈支持"**云端轻**"。数据面职责（谁持有真值、状态如何跨端收敛）是这个赛道公认最贵的地方，而对方用两年时间证明：**只做本地 + git remote 也能撑起成熟产品**。我们剩下的时间（12 天）里，把云端做成"重"的方案，风险不是"做不完"，而是"**做完了但状态收敛不可靠，Demo 翻车**"。

我的建议（待你拍板）：**云端保留"控制台 + 元数据 + 协作 UI"，但把"真值"这件事明确交给本地 git repo + git remote**——这正是对方验证过的形态，而我们比它多的价值在别处（见观察 3）。

### 观察 2 · "Agent 适配器"是**无限的运营负债**，不是一次性工程

对方从 v1.0 的少数几个 agent，一路加到 **54 个**，且每隔几个版本就有一次"路径其实一直是错的"修复。这不是他们做得差——**是这个领域本身没有标准**。

**→ 对我们的启示**：

- 不要把"支持 N 个 runtime"当卖点（**那是负债不是资产**，且对方已经 54 个了，我们追不上）；
- 要做的是**让适配器本身可声明、可探测、可覆盖、可在不重新发版的情况下修正**（D1 的五条）；
- 在 Demo 里，**"我们只做 4 个但每个都带验证依据 + 自证写入"比"我们支持 54 个"更有说服力**。

### 观察 3 · 他们唯一的功能空白是"质量"，而那正是我们 D4 的方向

06 里已经点出：对方**完全没有质量检查 / 评测**。而看它 1.40.0 那个 #267 事故——**两个内容相同的技能会让副本绑到错误的那一个，而"导回中央库"会覆盖掉另一个技能**——这已经不是"缺少功能"，而是**当 skill 数量上千、内容高度相似时，纯基于内容 hash 的身份判定会失效**。

**→ 我认为我们可以在 Demo 里立一个"第二幕"**：当 62 个 skill 涨到 620 个、有大量同源变体时，**光有漂移告警不够，你需要"这个 skill 到底是谁、它是好的吗"**。这就是我们做质量检查 / 评测的叙事支点——**不是加一个功能，而是回答对方答不了的问题**。

### 观察 4 · 对方没有云端，所以我们的"漂移告警"必须证明云端视角的独特价值

如果我们上云端控制台，它会立刻被问："这和我在本地跑个 CLI 有什么区别？"

从对方踩坑史里能提炼出**两个云端才有意义的问题**：

1. **N9**（同一物理 skill 被扫描成两份，因软链根目录）——**跨机器的"这其实是同一个 skill"**，需要跨端身份，云端天然有位置。
2. **多设备状态**（对方 1.28.0 花了整个版本做多设备同步，- 冲突三选一、按设备署名、pending 冲突跨设备传播）——**这些东西本地 CLI 表达不了"昨天 22:14 · 公司电脑 · 更新 3 个技能"**。

**→ 所以 Demo 第一幕应该是**：四端漂移告警里，**至少有一条告警是"只有云端视角才能看见"的**（例如"你 Mac 上改的这版，和你 Windows 上那份，其实是同一个 skill 的两个分支，而且它们已经分叉 3 天了"）。**这条如果立不住，云端就是多余的。**

> **拍板结果（2026-10-06）：保留云端数据面** —— `06` §5.3 的"云端收敛"提案**不采纳**。理由：Demo 形态要求（评委要能"打开浏览器就看见"）+ "线上可访问"硬约束；且云端数据面与本地 daemon 共用同一套任务表与锁，删掉是推倒重来，不是省时间。
>
> **但观察 1 与观察 4 的内核已被吸收**：
>
> | 观察                  | 吸收方式                                                                   |
> | ------------------- | ---------------------------------------------------------------------- |
> | 观察 1（难度在本地一致性，不在分发） | 「真值」始终在**本地 git + 磁盘**（`NFR-1` 离线可用）；云端**不做冲突判定**（冲突在本地三方比对解决，云端只转发结果） |
> | 观察 4（云端必须证明独特价值）    | **Demo 第一幕必须有一条"只有云端视角才能看见"的告警** —— 已写进 `03` §7 剧本设计                   |
>
> 完整拍板说明见 `06` §5.3。
