### 1.2 控制面 / 数据面划分

这是本系统的核心架构判断：

| 面       | 位置 | 职责                       | 为什么                          |
| ------- | -- | ------------------------ | ---------------------------- |
| **数据面** | 本地 | 文件系统读写、git 操作、扫描、漂移计算、分发 | 只有本地进程能访问 `~/.claude/skills` |
| **控制面** | 云端 | 元数据存储、协作、权限、UI 服务、任务下发   | 多端共享、可线上访问                   |

**推论**：

1. 云端**不跑** `drift` / `distribute` / `scan`——它碰不到磁盘。
2. 云端的漂移状态由 daemon 上报后落库。
3. CLI 与 MCP **完全不走云端**（`FR-2.4.3` / `NFR-1`），保证离线可用。
4. 一份代码两种部署：`core/algorithm` 云端复用，`core/fs` 仅本地使用。

> ⚠️ **术语消歧（重要 —— 「数据面」有两个用法，别混）**
>
> | 用法 | 含义 | 权威处 |
> |---|---|---|
> | ① **架构层**（本表） | 数据面 = **本地**文件系统 + git；云端是控制面 | **本节为权威定义** |
> | ② **决策语境**（`06` §5.3 的原提案） | 指"**云端是否承担写路径职责**"：存 Skill 内容 / 下发 `push` 任务 / 判冲突 | 已拍板 |
>
> **拍板结论（2026-10-06）**：云端**保留写路径职责**（任务下发 + `sync_records` 双写），但**不存文件内容**（`FR-3.12`）、**不判冲突**（冲突在本地三方比对，云端只转发结果）。
>
> 所以"**保留云端数据面**"这句话里的"数据面"是用法 ②，指的是**写路径参与度**，**不是**说云端变成了用法 ① 的数据面。两者不矛盾：**真值始终在本地 git + 磁盘**（`NFR-1`）。

### 1.3 代码分层约束

```text
入口层 (cli / mcp / daemon / api)
      ↓ 只做参数解析与协议转换，不含业务逻辑
服务层 (services)     ← 编排，事务边界在此
      ↓
引擎层 (core) + 数据层 (store)
      ↓ 不得反向依赖
```

**硬约束**：`core` 不得 import `services` / `store` / 任何入口层；`core/algorithm` 不得有 IO。

### 1.4 部署架构

```text
线上（1–2 个容器）
┌──────────────────────────────────┐    ┌──────────────────────────┐
│ 容器 A：skillos-cloud             │    │ 容器 B：skillos-sandbox   │
│   FastAPI (REST + WS Hub)        │    │   同一镜像                 │
│   托管 Web 静态文件               │    │   SKILLOS_SANDBOX=1       │
│   Postgres（外部或同容器）         │    │   预置演示数据             │
└──────────────────────────────────┘    └──────────────────────────┘
                    ▲
                    │ WS 出站
┌───────────────────┴──────────────┐
│ 你的机器：skillos daemon          │
│   + Git 仓库 + SQLite            │
└──────────────────────────────────┘
```

沙盒与云端**共用同一镜像**，仅通过环境变量切换：`SKILLOS_ROOT`（runtime 根路径）、`SKILLOS_SANDBOX`（**可写隔离**演示模式，见 2.7 —— 不限制写操作，隔离靠文件系统边界）。

#### 2.1.2 `adapters/` — 运行时适配器

| 项  | 内容                              |
| -- | ------------------------------- |
| 职责 | canonical → 目标 Runtime 的结构与字段转换 |
| 需求 | FR-1.0.8                        |

```python
class RuntimeAdapter(ABC):
    key: str                        # **带命名空间**："builtin:claude" / "custom:acme"（FR-1.0.25）
    version: str                    # 适配器版本，参与 base 重建（FR-1.0.18）
    category: str                   # 分类，用于分组展示（"coding" / "chat" / "review"…，FR-1.0.8）
    supports: frozenset[str]        # {"scripts","references","assets","subskills","sidecar"}
    field_policy: dict[str, str]    # canonical 字段 → "keep" | "drop"
    paths: RuntimePaths             # 路径即数据（FR-1.0.25）—— 不得写死成代码常量

    def resolve_root(self, scope: str, project_dir: Path | None) -> Path:
        """按 paths.deploy_dir → paths.fallback_dirs 顺序解析部署根；
        两个都不存在时返回 deploy_dir（首装），**不回退到任何硬编码默认值**"""

    def frontmatter_out(self, meta: SkillMeta) -> dict: ...
    def frontmatter_in(self, raw: dict) -> SkillMeta: ...
    def sidecar_specs(self, meta: SkillMeta) -> dict[str, str]: ...
    def render_layout(self, snapshot: SkillSnapshot) -> dict[str, bytes]: ...


@dataclass(frozen=True)
class RuntimePaths:
    """一个 Runtime 的路径事实。**部署根与发现根分开建模** —— 二者相同是巧合，不是定义。"""
    deploy_dir: PathSpec             # 部署根：我们往这里写
    scan_only_dirs: list[PathSpec]   # 发现根：只扫、不写（历史遗留目录 / 同源软链 / 第三方也在此扫）
    fallback_dirs: list[PathSpec]    # deploy_dir 不存在时的回退链（按序尝试）
    shared_dirs: list[PathSpec]      # 与其它 Runtime 共用的物理目录（停用前须引用计数归零）
    recursive_scan: bool             # 是否递归子目录（FR-1.0.8；不递归的 Runtime 只看一层）
    verified_at: date | None         # 本机实测确认日期；为空 = 未验证
    evidence: str                    # "official-doc" | "upstream-source" | "local-observed"


@dataclass(frozen=True)
class PathSpec:
    key: str          # "builtin:claude" / "custom:my-fork" —— 全局唯一（FR-1.0.25 命名空间隔离）
    scope: str        # "user" | "project"
    template: str     # 支持 {home} / {project} 占位符
    source: str       # "builtin" | "custom"
```

> **`category` / `recursive_scan` 与路径同源（`06` A1）**：上游 `ToolAdapter` 把这三类都当**数据**而不是代码分支，因此新增一个 Agent 不需要改渲染器。我们采纳这个原则 —— `adapters/` 目录里**不得出现 `if key == "xxx"` 之类的分支**。
>
> **项目级路径必须相对路径且不得含 `..`**（`06` B5）：项目级部署根随项目走，绝对路径会让同一份配置在别人机器上写进错误位置；含 `..` 则等于把部署目标放到了项目之外。

> **`render_layout()` 必须是纯函数**（FR-1.0.8）：同 `SkillSnapshot` + 同 `adapter.version` ⇒ 逐字节相同的输出。禁止依赖时间戳、随机数、环境变量、本机路径。
>
> 这是 **base 可重建**的前提（NFR-3.5）——历史 base 不落盘，靠 `render(canonical@installed_commit, installed_adapter_version)` 现算。一旦 render 不纯，base 就不可信，三方合并与漂移判定同时失效。
>
> `version` 是**适配器自身的版本**，与 Skill 版本无关。改变字段策略、sidecar 模板、目录布局都必须 bump 它。

**路径即数据（FR-1.0.25）**

Runtime 目录**不是代码常量，是数据**。依据：上游同一份 CHANGELOG 里，对 Codex 的 skill 目录给出过**两次相反结论**（1.19.x 说 `~/.agents/skills`、1.22.2 说 `~/.codex/skills`，两条都写得很肯定）。这说明"哪个目录对"无法靠一次性查证永久消除，**只能靠结构容忍**（`07` D1 / N1~N7）。

| 字段 | 语义 | 硬约束 |
|---|---|---|
| `deploy_dir` | **部署根** —— 我们往这里写 | 与发现根**分开建模** |
| `scan_only_dirs[]` | **发现根** —— 只扫、不写 | 只扫列出的目录，**未列出的一律不扫**，防止把无关目录收编成 Skill |
| `fallback_dirs[]` | 回退链 | 按序尝试，**不回退到硬编码默认值** |
| `shared_dirs[]` | 与其它 Runtime 共用的物理目录 | 停用某 Runtime / 清目录前**必须先查引用计数**，非零则禁止清理（`07` N1 / N5） |
| `verified_at` | 本机实测确认日期 | 为空表示**未验证**，UI 必须出"路径未验证"警告 |
| `evidence` | 依据来源 | 无依据的路径不得入库 |

**用户必须能覆盖路径**（必需功能，不是 nice-to-have）：上游多个 Agent（Kimi / OpenCode / GitLab Duo）路径一旦写错，用户只能等作者发版。覆盖值与内置定义用 **`builtin:` / `custom:` 命名空间隔离**，"按 key 查定义"的解析顺序必须统一（**先 `custom` 后 `builtin`，且只有一份实现**，`07` N3）。

> **Runtime key 迁移机制（`06` B4）**：Runtime 的 key 一旦改变（上游真实案例：`clawdbot` → `openclaw`；某 agent 从 custom 收录进 builtin），历史数据里的引用必须一并重映射。当前 4 端短期不变，但**入口必须预留**：`remap_runtime_key(old, new)` 需同时改写 `runtimes` / `runtime_bindings` / `sync_records` / `upstream_sources` 中的引用，且**改写前先备份、改写后回读自证**（FR-1.0.27 同源）。迁移是破坏性操作，走 §2.2.2 的移除守卫。
>
> **部署自证（FR-1.0.27）**：写完 runtime 目录后必须**回读目标路径**，确认存在、且内容哈希与期望一致，才允许上报成功。"我写成功了"与"它在那"是两件事 —— 上游多次出现"同步显示成功、Agent 里什么都没有"。

**字段策略（由本机 62 个真实 Skill 实测得出）**：

| canonical              | claude | agents | workbuddy | codex |
| ---------------------- | ------ | ------ | --------- | ----- |
| `name` / `description` | keep   | keep   | keep      | keep  |
| `allowed-tools`        | keep   | keep   | keep      | keep  |
| `version`              | drop   | drop   | **keep**  | drop  |
| `agent_created`        | drop   | drop   | **keep**  | drop  |
| `origin`               | drop   | drop   | drop      | drop  |

`agents` 适配器额外产出 `agents/openai.yaml`（本机 30 个 Skill 带此文件）：

```yaml
interface:
  display_name: "<name>"
  short_description: "<description 前 80 字>"
  default_prompt: "<description>"
policy:
  allow_implicit_invocation: true
```

#### 2.1.3 `drift.py` — 漂移检测

| 项  | 内容                  |
| -- | ------------------- |
| 需求 | FR-1.0.6 / FR-1.0.7 |

```python
class DriftState(StrEnum):
    SYNCED    = "synced"
    MISSING   = "missing"
    OUTDATED  = "outdated"
    MODIFIED  = "modified"
    CONFLICT  = "conflict"
    UNMANAGED = "unmanaged"     # 磁盘有目录，但从未纳管（原 EXTRA 并入此态）
    ORPHANED  = "orphaned"      # 曾被纳管，但 canonical 中已删除

@dataclass(frozen=True)
class DriftReport:
    skill_id: str
    runtime_key: str
    state: DriftState
    base_commit: str | None          # runtime_bindings.installed_commit
    base_adapter_version: str | None # runtime_bindings.adapter_version
    base_hash: str | None            # runtime_bindings.installed_hash（磁盘基线）
    local_hash: str | None           # 磁盘现状
    remote_hash: str | None          # 仓库经 adapter 渲染后应得
    adapter_outdated: bool           # 独立维度，见 FR-1.0.19
    has_untracked_assets: bool       # 含 >阈值文件，见 FR-1.0.20
    changed_files: list[str]
```

**判定算法**（先判归属，再三方比对）

**第 1 步：归属判定**（三事实 —— 磁盘是否有目录 / binding 是否有记录 / canonical 是否有该 skill）

| 磁盘有目录 | binding 有记录 | canonical 有该 skill | 状态                              |
| ----- | ----------- | ------------------ | ------------------------------- |
| ✗     | ✗           | ✓                  | 该 runtime 上**不适用**，不进矩阵         |
| ✓     | ✗           | 任意                 | `UNMANAGED` —— 装了但未纳管（含用户自建）    |
| ✓     | ✓           | ✗                  | `ORPHANED` —— canonical 已删，磁盘残留 |
| ✗     | ✓           | ✓                  | `MISSING` —— 应装未装               |
| ✓     | ✓           | ✓                  | 进入第 2 步内容比对                     |

**第 2 步：内容三方比对**（全部在**渲染后空间**；base 与 remote 必须使用**同一 adapter 版本**）

```text
base_disk    = render(canonical@installed_commit, installed_adapter_version)  # 当时写进磁盘的字节
base_current = render(canonical@installed_commit, 当前 adapter_version)        # 合并底线
remote       = render(canonical@HEAD,             当前 adapter_version)
local        = 磁盘现状

disk_dirty  = hash(local) != binding.installed_hash          # 磁盘是否被手改
content_new = canonical@HEAD != canonical@installed_commit    # canonical 是否前进
adapter_new = 当前 adapter.version != binding.adapter_version # 渲染器是否升级
```

| `adapter_new` | `disk_dirty` | `content_new` | 状态                                   | 说明                       |
| ------------- | ------------ | ------------- | ------------------------------------ | ------------------------ |
| ✗             | ✗            | ✗             | `SYNCED`                             | 全一致，无徽标                  |
| ✗             | ✗            | ✓             | `OUTDATED`                           | 仓库领先，可直接 push            |
| ✗             | ✓            | ✗             | `MODIFIED`                           | 磁盘被手改，可 pull 回收或 push 覆盖 |
| ✗             | ✓            | ✓             | `CONFLICT`                           | 两边都改，需人工**四选一**（含「两个都保留」） |
| **✓**         | ✗            | 任意            | `OUTDATED` + `adapter_outdated=true` | 只提供「应用新模板」动作             |
| **✓**         | ✓            | 任意            | `MODIFIED` + `adapter_outdated=true` | 分发前对用户改动过的文件走整文件**四选一** |

> 六行覆盖全部 8 种组合（`adapter_new = ✗` 的 4 种 + `= ✓` 的 2×2），无遗漏、无重叠。

> **为什么 `adapter_new` 时不得判 `CONFLICT`（FR-1.0.19）**：磁盘上的 `local` 是**旧 adapter 渲染 + 用户改动**的混合体，与 `base_current`（新 adapter 渲染）的差异里既有模板差异也有人改差异，无法分离。此时走三方合并必然产生假冲突。规则：**先应用新模板，再单独处理用户改动**（整文件粒度），两步分开。

> **`adapter_outdated` 不是漂移状态，是独立维度**：它不进入状态枚举，也不改变状态取值的语义，只在 UI 显示「模板已升级」徽标（FR-2.4.6）。这样矩阵规模不膨胀，同时不会漏报。

**`SYNCED*` 与 `has_untracked_assets`（FR-1.0.20）**

含 >阈值文件的 Skill，其漂移哈希**不覆盖这些文件**。为避免「用户改了 8MB 资产、UI 却显示 SYNCED」的假同步：

- `has_untracked_assets = true` 时，即使状态为 `SYNCED`，**UI 必须显示 `SYNCED*`** 并附「含未纳管资产」徽标；
- 徽标 tooltip 需列出具体文件与大小，说明「该文件不参与版本管理与漂移检测」；
- 该字段为真时，`push` 需提示「未纳管资产不会被分发」。

**哈希口径（两级结构，FR-1.0.5）**

"存储身份"与"看起来是否一样"是两件事，必须分两级 —— 混作一级会同时毁掉两边：

| 级 | 名称 | 计算 | 用途 |
|---|---|---|---|
| **第一级** | `hash_bytes` | `sha256(path + "\0" + sha256(content))` 排序聚合；路径用 POSIX 分隔符；**字节级，不做任何归一化** | 判定"是不是同一个内容"。**写入 `installed_hash` 的就是它** |
| **第二级** | `compare_normalized()` | **仅当 `hash_bytes` 已判定不等时**才调用：统一换行符（`\r\n` → `\n`）、Unicode NFC、尾随空白 | 报告"差异是否仅风格差异"，供 UI 提示；**不改变状态判定** |

> **第二级折叠的三条边界（`06` B1）**：① **只折叠文本** —— 靠 `is_foldable_text()` 判定；② **孤立 `\r` 不动**（`\r` 后面不跟 `\n` 时不视为行尾，它可能是脚本里有意义的字节）；③ **二进制一律不折叠**。折叠**只用于"解释差异"这一个用途**，不得回流去影响任何身份判定。

> **为什么不把归一化做进哈希**：一旦归一化，就再也无法表达"这两个文件**字节不同**"—— 而跨平台同步恰恰需要知道这一点（Windows 的 CRLF 与仓库的 LF 语义相同但字节不同）。旧写法"归一化后进哈希"会让"永远可更新、两端来回互推"成为常态（`07` D6）。
>
> **历史兼容**：本设计**不作废任何已存 `installed_hash`** —— 第一级从来就是字节级，归一化只是新增的第二级，无需迁移。
>
> **枚举单一化**：参与哈希的文件集合必须由**同一个 `list_content_files()`** 产出，`scan` / `hash` / `diff` / `removals` 四处共用，禁止各自 filter —— 范围漂移会让"该比的没比、不该比的比了"，是上游多处误报的根因。
>
> **排除集分三类**（不得混为一个 `ignore` 列表）：① 影响哈希的排除（`__pycache__/`、`*.pyc`、`.DS_Store`、`.skillos/`）；② 只影响兜底比较的排除（行尾、BOM）；③ 纯噪音（日志、临时文件）。
>
> **`*.pyc` / `__pycache__/` 必须进第一类（`06` A3，实锤坑）**：Skill 里的 Python 脚本一运行就生成 pyc。不排除的话，**每次使用后部署副本都会永久显示"已变更"**，漂移矩阵长期飘红。本机已有 54 个 `.pyc` 可证。

**仓库协议版本协商（FR-1.0.29 / `06` A4）**

`adapter_version`（FR-1.0.18）只解决**单机内**的模板漂移；**跨客户端**（多台机器、不同 `skillos` 版本）的协议差异必须另有机制：

#### 2.2.0 `safe_path()` — 路径安全（强制统一入口）

| 项  | 内容                |
| -- | ----------------- |
| 需求 | FR-1.0.14、NFR-7.4 |

**所有**接受外部传入 `path` 的入口 —— REST `?path=`、WS `file_read` / `file_write`、MCP 工具参数、CLI 参数 —— **必须先过这一个函数**，不得各自拼接路径后直接开文件。

```python
def safe_path(root: Path, rel: str) -> Path:
    """把外部传入的相对路径解析为受限于 root 的绝对路径。
    绝对路径、含 .. 逃逸、经 symlink 逃逸、命中保留名 —— 一律抛 PATH_TRAVERSAL。
    """
    if Path(rel).is_absolute():
        raise PathTraversalError(rel)
    base = root.resolve()
    target = (base / rel).resolve()      # resolve() 展开 symlink 与 Windows 8.3 短名
    if not target.is_relative_to(base):  # Python 3.9+
        raise PathTraversalError(rel)
    return target
```

| # | 约束                                                                                                 |
| - | -------------------------------------------------------------------------------------------------- |
| 1 | **先 `resolve()` 再比较** —— 否则 `root/link/../../etc` 这类经符号链接的逃逸检测不出来                                  |
| 2 | **禁止用字符串前缀匹配判越界**（`str(target).startswith(str(root))`）：`/data/skills-evil` 会误通过 `/data/skills` 的检查 |
| 3 | Windows 上 `resolve()` 会展开 8.3 短名与 UNC 前缀（`\\?\`），比较必须在同一形态下进行                                      |
| 4 | Windows 保留名（`CON` / `PRN` / `AUX` / `NUL` / `COM1-9` / `LPT1-9`）与非法字符在此一并拒绝                        |
| 5 | 错误码固定 `PATH_TRAVERSAL`，HTTP 400；**错误信息不回显解析后的绝对路径**（避免泄露目录结构）                                      |
| 6 | 与 T1 的「根路径参数化」是同一条约束的两面：`root` 由调用方注入，越界校验也在此统一完成                                                  || 7 | **符号链接形态差异**：Windows 上 `symlink` 需管理员权限，能力不足时降级为 **junction**（只支持目录、必须绝对路径）。`resolve()` 对二者处理不同（部分 Python 版本不把 junction 识别为 link），越界判定必须同时检查 `Path.is_symlink()` 与 Windows reparse point 属性（`05` P1-2 / `07` W1） |
| 8 | **防符号链接环**：`resolve()` 遇自引用软链会抛 `RuntimeError` 或死循环，必须捕获并转为 `PATH_TRAVERSAL`，**禁止异常穿透到调用方** |
| 9 | **不做路径整理**：不自动去除多余分隔符 / 不大小写归一化 / 不展开 `~`。路径整理只在 `safe_path` 一处发生（`07` W9 / NFR-7.8） |
| 10 | **路径键归一化（FR-1.0.31 / `06` A7）**：判定"两个路径是否同一个"必须走统一路径键 —— 按分隔符**分段**，逐段做 `unicodedata.normalize("NFC", part)` + `str.casefold()`，再校验唯一性。**只比大小写不够**：中文、组合字符、全角/半角场景下 `NFC` 差异会让**同一路径被判成两个**（本机 62 个 Skill 全中文名，这是常态）。注意 `path_key` 是**比较用**的键，**不得用来替换用户可见的真实路径**（与第 9 条一致） |

#### 2.2.1 `scan.py` — 扫描器

| 项  | 内容                  |
| -- | ------------------- |
| 需求 | FR-1.0.1 / FR-1.0.3 |

```python
@dataclass(frozen=True)
class ScannedSkill:
    root: Path
    rel_path: str
    runtime_key: str
    scope: str                # "user" | "project"
    meta: SkillMeta | None
    pack_hash: str
    is_nested: bool           # 位于 subskills/ 下

def scan_roots(roots: list[RootSpec], ignore: list[str]) -> list[ScannedSkill]: ...
```

**包边界规则**：

1. **Skill 检测规范（FR-1.0.1 / `06` A2）**：含 `SKILL.md`（大写）的目录即包根，**这是唯一 canonical 标记**；`skill.md`（全小写）作 **legacy 兼容**识别（接受、但不作为新建标准，导入时可提示归一化）；**`README.md` / `CLAUDE.md` 绝不算 Skill 标记**。理由：递归扫描时分类目录（本机 `skills/research/` 这类）里的 README 会被误判成 Skill，而**父目录一旦误判，其下的真 Skill 会被短路跳过** —— 一次误判损失整棵子树，且表现为"扫不到"，不是"扫错了"。
2. 包根下的 `subskills/<name>/SKILL.md` 识别为**子技能**（本机 `test-automation` 即此结构），计入清单但标记 `is_nested=True`。
3. 跳过 `.runtime/`（商城安装产物，已隔离存储）、`node_modules/`、`.git/`、**`.skillos/`（仓库内元数据目录，见 §2.3）**。跳过集由 §2.1.3 的 `list_content_files()` 统一给出，**不在此另立一份**。
4. 符号链接**不跟随**（防环），记录为警告。但**扫描根本身如果是软链，必须按 canonical path 去重**（见下）。
5. **按 canonical path 合并扫描根（`07` N9 —— 上游已知未修复，我们的超越点）**：两个 Runtime 的根目录若是指向同一物理目录的软链（本机 `.claude` 与 `.agents` 存在此形态），`resolve()` 后会得到同一路径。`scan_roots()` 出口必须对 `Path.resolve()` 去重，否则**同一个物理 Skill 被扫成两条**，进而产生假 `UNMANAGED` 与重复纳管。
6. 扫描只发生在 `RuntimePaths` 显式列出的 `deploy_dir` / `scan_only_dirs` / `fallback_dirs` 内（FR-1.0.25），**不遍历 home 目录去猜**。

```python
def scan_roots(roots: list[RootSpec], ignore: list[str]) -> list[ScannedSkill]:
    seen: set[Path] = set()
    out: list[ScannedSkill] = []
    for r in roots:
        canon = r.path.resolve()          # 合并软链指向同一物理目录的根
        if canon in seen:
            continue                       # 记 warning：根被合并，不重复产出
        seen.add(canon)
        out.extend(_walk(canon, r, ignore))
    return out
```

#### 2.2.2 `distribute.py` — 分发器

| 项  | 内容                       |
| -- | ------------------------ |
| 需求 | FR-1.0.9、`NFR-3`、`NFR-5` |

**写入协议（Windows 安全）**

先明确**四个写入调用点** —— 每个都必须**显式声明自己被授权销毁什么**，不存在"默认就安全"的调用点（FR-1.0.26）：

| 调用点 | 场景 | 默认 `ReplacePolicy` |
|---|---|---|
| `push` | 一键分发 / 批量分发 | `RECORDED` |
| `import` 换源 | 纳管时选定主副本、覆盖其它副本 | `NO_CLOBBER` |
| `rollback` | 版本回退覆盖磁盘 | `RECORDED` |
| 导出 / 落盘 | 导出 Skill 到任意目录 | `NO_CLOBBER` |

```python
class ReplacePolicy(StrEnum):
    """替换授权三态。**无默认值** —— 每个调用点必须显式传参。"""
    NO_CLOBBER     = "no_clobber"      # 目标已存在且无法证明属于我们 → 拒绝，逐字节保留
    RECORDED       = "recorded"        # 仅当目标内容 == runtime_bindings.installed_hash 时才替换
    USER_CONFIRMED = "user_confirmed"  # 已由人类显式确认可销毁
```

```text
1. 解析目标路径 target
2. 【归属判定】读取 target 现状，按调用点的 ReplacePolicy 决定是否继续
   - NO_CLOBBER 且 target 非空        → 立即返回 TARGET_CONFLICT，不做任何写入
   - RECORDED   且 target != installed_hash → 立即返回 TARGET_CONFLICT
   - 无法判断"某路径是否会被删"        → **报错，不许猜**（NFR-11.3）
3. 备份：复制 target → .skillos/backups/<skill_slug>/<timestamp>/
4. 渲染：adapter.render_layout() → {rel_path: bytes}      （只含纳管文件）
5. 写临时目录 target.parent/.<name>.tmp-<rand>/          （落盘清理见下）
6. 【removals 守卫】逐条列出「本次替换后将从 target 永久消失的路径」
   - 比较对象是**即将换进去的暂存树**，不是 canonical 快照（两者可能不同）
   - 目录只上报一行（`templates/`，而非其中每个文件）
   - 未纳管资产（>阈值）在此**回收进 tmp**，不计入 removals（FR-1.0.20）
   - removals 非空 → **停下**，人确认后才继续；无人值守路径一律跳过并保留角标（NFR-11.4）
7. 校验：比对临时目录中纳管文件哈希 == 期望哈希
8. 交换：
   - target 不存在 → rename(tmp, target)
   - target 存在   → rename(target, target.old) ; rename(tmp, target) ; 删 target.old
     （Windows 下 rename 不可覆盖非空目录，必须两步）
9. 【部署自证】回读 target，逐文件核对清单与哈希 —— 不一致按失败处理（FR-1.0.27）
10. 更新 runtime_bindings：
    installed_commit = canonical HEAD
    adapter_version  = 当前 adapter.version
    installed_hash   = 本次渲染内容哈希（只算纳管文件）
    installed_version= 展示用版本号（不作基线）
11. 写 sync_records（含 removals 明细、skipped / preserved 的未纳管资产）
12. 任一步失败 → 从备份还原，返回失败明细
```

> **为什么 removals 在第 6 步、且比较对象是暂存树**：上游 1.34.0 用户丢了 `templates/` 里的 PPT 模板 —— 文件夹级替换把用户自建内容整体换掉，**事后才发现**。只比较 canonical 快照会漏报（快照没有、磁盘有、新版本也没有 → 该报不报）；比较暂存树才得到"真正会消失的文件"（`07` D4 / N15）。
>
> **`held_back_removals` 不给 CLI 覆盖开关**：只有人能说"这些文件可以丢"（`07` A9）。MCP 与启动批量一律不可覆盖（FR-1.0.26 ④ / NFR-11.4）。

**幂等性**：第 5–8 步以内容哈希为判据，纳管文件内容一致时跳过写入（`NFR-5`）。未纳管资产始终保留，不参与判据。

**暂存目录生命周期**：`.staged-*/` 与 `.<name>.tmp-*/` 必须在**每次 commit 之前**清理（`07` N16f）。否则残留目录会被下一次 `scan` 收编成一个新 Skill —— 一次中断演变成持续污染。

**残留自检与恢复（FR-1.0.15）**：

第 10 步「失败 → 从备份还原」**只在进程正常存活时有效**。若进程在第 7 步的两步交换之间被 kill / 崩溃，第 10 步根本不会执行，目标目录会停在中间态。

```text
第 7 步中断的三种残留形态：
  ① 只有 target.old，无 target   → 交换未完成
  ② 有 target.old 且有 target    → 交换已完成，仅剩清理
  ③ 只有 .<name>.tmp-<rand>/     → 写临时目录中断

恢复规则（幂等，可重复执行）：
  ① → 把 target.old 改回 target（回退到分发前状态）
  ② → 删除 target.old（分发已成功，只补清理）
  ③ → 删除 tmp 残留
```

执行时机：`skillos doctor` 显式检查 · daemon 启动时 · **每次 `push` 前对该 target 的定向检查**。

**为什么必须做**：不做的话，残留的 `target.old` / `tmp-*` 目录会被 `scan` 当成"多出来的目录"，污染漂移判定 —— 从一次崩溃演变成持续误报。

#### 2.2.3 `version.py` — Git 封装

| 项  | 内容        |
| -- | --------- |
| 需求 | FR-1.0.10 |

全部通过 `subprocess` 调用 `git`，**不自研 VCS**：

```python
class GitRepo:
    def init(self, initial_branch: str = "main", ref_format: str = "files") -> None:
        """**必须显式指定初始分支与 ref 存储格式**（`07` G1 / G2）：
        - 不指定初始分支 → 依赖用户全局 `init.defaultBranch`，不同机器仓库结构不同
        - 不指定 ref 格式 → 新版 git 可能默认 reftable，与旧版工具链不互通
        实现：`git init -b <initial_branch> --ref-format=<ref_format>`（不支持时降级并记 warning）"""

    def commit(self, paths: list[str], message: str, author: str) -> str: ...
    def log(self, path: str | None, limit: int) -> list[Commit]: ...
    def show(self, commit: str, path: str) -> bytes: ...
    def snapshot_at(self, commit: str) -> SkillSnapshot:
        """取某一 commit 的完整 canonical 快照 —— base 重建的唯一入口（NFR-3.5）"""
    def diff(self, base: str, head: str, path: str | None) -> str: ...
    def rollback(self, commit: str, paths: list[str]) -> str:
        """**先自动建一次安全快照，再** `git checkout <commit> -- <paths>` 并提交新 commit。
        快照对用户可见、可再回滚（`07` N23）—— 回滚本身也是破坏性操作"""
```

**回滚策略**：`checkout` + 新建 commit，**不 rewrite history** —— 避免用户已推送的远端历史被破坏。

> **锁文件位置（`07` G6）**：git 的锁文件（`.git/index.lock` 等）**不得放在会被 rename 的目录内** —— 原子写会整目录 rename，锁文件跟着搬家 → 并发方拿到的是失效锁。我们的仓库锁是 `~/.skillos/.lock`（在 repo 之外），git 自身的锁由 git 管理。
>
> **首次 push 必须 `-u`（`07` G4）**：`git push -u origin <branch>` 建立上游关联，否则后续 `ls-remote` / `status` 拿不到 tracking 信息，只能靠猜。
>
> **调 git 一律显式传 `-c`**：`-c core.autocrlf=false -c core.quotepath=false -c core.longpaths=true`，**不读用户全局 config**（`05` P0-1）。

> **接口收紧（OUT-14）**：`GitRepo` 只暴露上面这些**具名方法**，**不提供 `run(cmd, args)` 之类的通用透传**。
>
> 原因：daemon 接受的参数来自云端，若存在通用 git 透传，等于把「云端触发 → 本地任意 git 执行」开成一条通道。同理，daemon 的 WS 任务表里也不得出现 `git {cmd, args}`（见 4.2）。
>
> 块内三方合并（`git merge-file --diff3`）**本期不实现**（OUT-11），冲突走整文件粒度**四选一**。该方法待 P4 之后需要时再加，且仍只以具名方法形式暴露。

#### 2.2.4 `upstream.py` — 上游跟踪

| 项  | 内容        |
| -- | --------- |
| 需求 | FR-1.0.13 |

```python
def check_upstream(source: UpstreamSource) -> UpstreamStatus:
    """git: git ls-remote 取 ref 的 commit；marketplace: 查版本号；url: HEAD 请求取 ETag"""
```

状态：`current` / `outdated` / `error` / `unknown`。  
本地改动标记 `is_fork=True`，升级时走三方合并而非覆盖。

**ref 解析优先级（`07` G3）**：`git ls-remote` 返回的是一个自由文本表，同一 commit 可能以多种形式出现（分支 / 轻量 tag / annotated tag 对象 / peeled tag）。解析必须按固定优先级：**分支 → peeled tag（`^{}`）→ annotated tag 对象 → 轻量 tag**，且**只认第一个匹配**，不合并多个结果。

**网络与锁分离（`07` D5 / N18）**：`ls-remote` 是网络往返，**永不在锁内执行**。顺序为「锁外并发解析（结果去重、最多 8 并发）→ 锁内只写状态列」。上游曾因整个 `ls-remote` 持锁，导致用户操作 20 秒后报 `repository is busy`（#315）。

**预取结果必须带键（`07` N18）**：缓存条目要连同解析时的 `(clone_url, branch)` 一起存；写入前**重读记录并重算键**，键不一致则丢弃缓存重算。否则远端改了地址，会拿旧结果覆盖新结论。

**缓存 LRU（`07` N22）**：上游状态缓存设容量上限（建议 200 条 / 无引用即驱逐）。无上限会在长期运行后吃掉内存 —— daemon 是长驻进程，这类泄漏不会自愈。

#### 2.2.5 `import.py` — 纳管器

| 项  | 内容                   |
| -- | -------------------- |
| 需求 | FR-1.0.16 / FR-1.1.3 |

**核心前提**：同一 slug 出现在多个 Runtime 是**常态，不是异常**。本机实测：`brainstorming` 在 `.claude` 与 `.agents` 下字节完全一致；34 个 skill 带 `origin: ECC`。若把"多副本"当错误处理，62 个 skill 的首次纳管会当场失败一半。

**纳管决策表**：

| 情形                                  | 处理                                                     |
| ----------------------------------- | ------------------------------------------------------ |
| 同 slug 多副本，**内容一致**（`pack_hash` 相同） | **合并为一条 Skill + 挂多个 binding**，不报错、不询问                  |
| 同 slug 多副本，**内容不一致**                | 报 `NAME_CONFLICT`，列出各副本差异摘要，由用户选**主副本**；其余仍保留为 binding |
| slug 仅大小写不同（`Foo` / `foo`）          | 报 `NAME_COLLISION`（NFR-7.4），拒绝纳管                       |
| 目录无 `SKILL.md`                      | 跳过，记 warning                                           |
| 同一 slug 已纳管                         | 幂等更新 binding，不新建记录                                     |

**主副本建议顺序**（用户可在 import 时覆盖）：`~/.claude` > `~/.agents` > `~/.workbuddy` > `~/.codex` > 项目级。

> **"同一 slug 多副本"的识别由 2.1.5 `identity.py` 承担**，**不以 slug 字符串相等为唯一依据** —— 按 `source_ref` → 唯一内容哈希 → `dir/name` 分层判定，**任一层出现多个候选就报冲突，禁止自行挑一个**。上表用 slug 描述只是为了可读性；若真按 slug 相等合并，`Code Review` 与 `code-review` 会被误并成一条（`07` N8 的触发条件）。

**产出**：1 条 `skills` 记录 + N 条 `runtime_bindings`（各副本的 `installed_hash` 分别记录，这是后续漂移判定的基线）。

**基线来源与 `baseline_source`（关键）**

binding 的 base 有两种来源，语义不同，必须区分：

| `baseline_source` | 何时产生                | base 能否重建                                                         | 漂移判定                     |
| ----------------- | ------------------- | ----------------------------------------------------------------- | ------------------------ |
| `distributed`     | 由本系统 `push` 写入      | ✅ `render(canonical@installed_commit, installed_adapter_version)` | 完整三方比对（§2.1.3 第 2 步）     |
| `imported`        | 由 `import` 纳管用户已有目录 | ❌ 磁盘内容是用户写的，不是我们渲染的                                               | **只做两方比对**，不进 `CONFLICT` |

`imported` 基线的判定降级规则：

```text
local == remote  → SYNCED
local != remote  → MODIFIED（无法区分"仓库超前"还是"磁盘超前"，UI 标注「待确认」）
```

**首次 `push` 成功后**，该 binding 自动转为 `baseline_source = distributed`，并写入 `installed_commit` / `adapter_version` —— 从这一刻起三方比对才完整可用。

> **不自动 push**：纳管过程会做字段归一化（如 `origin` 字段被 drop），自动写回等于在用户没确认的情况下改动他的 skill。差异只列出、只提示，由用户决定何时 `push` 建立基线。

### 2.3 `store` — 数据访问

```python
class IndexStore(Protocol):
    # skills
    def upsert_skill(self, skill: SkillRecord) -> None: ...
    def list_skills(self, q: SkillQuery) -> list[SkillRecord]: ...
    def get_skill(self, skill_id: str) -> SkillRecord | None: ...
    # bindings
    def upsert_binding(self, b: RuntimeBinding) -> None: ...
    def list_bindings(self, skill_id: str | None) -> list[RuntimeBinding]: ...
    # ...
```

两个实现：`SqliteIndexStore`（本地）、`PostgresIndexStore`（云端）。**表结构同构**（见第 3 节）。

**元数据随仓库版本化，索引可重建（FR-1.0.30 / `06` A8）**

本地 SQLite **不是事实源，是缓存**。真正的事实有两份：

| 事实 | 存放位置 | 谁权威 |
|---|---|---|
| Skill 内容 | 仓库工作副本（git 管理） | 磁盘 + git |
| **协作元数据**（标签 / Profile 归属 / 启用状态） | 仓库内 `.skillos/` 目录，**随 git 版本化** | 仓库 |
| 索引与判定缓存（`status` / `health_score` / FTS） | 本地 SQLite | **不权威，可随时重建** |

> **为什么元数据也要进仓库**：只进本地库的话，"我在这台机器上打的标签"永远到不了另一台机器。而 `.skillos/` 随 git push 自然同步 —— 与「跨机器」目标是同一件事，且不需要任何云端参与。
>
> **两个 `.skillos` 不是同一个，别混**：**`<repo>/.skillos/`** 是**仓库内**的元数据目录（进 git、会同步、被 `scan` 排除）；**`~/.skillos/`** 是**本机**状态目录（锁文件、备份、日志、SQLite —— 不进 git、不同步）。前者是资产的一部分，后者是这台机器的私事。

> **重建守卫（关键保护，`06` A8）**：`rebuild_index()` 前必须比对「元数据里的 Skill 数」与「仓库里的 Skill 目录数」。**若元数据说 0 个、而仓库里确有 Skill 目录 → 拒绝重建**，抛**类型化错误** `META_INDEX_MISMATCH`。理由：元数据损坏或首次克隆时，"照元数据重建"会**把整库清空**（元数据是空的 → 重建出空库 → 再写回覆盖）。做成类型化错误的好处是启动流程可以**只在这一种情况下**自愈（重新全量扫描重建元数据），而不是把所有异常都当"重建一下就好了"。

#### 2.5.2 daemon（`FR-1.2.x`）

```text
启动
 ├─ 读配置 ~/.skillos/config.toml
 ├─ 残留自检（FR-1.0.15）+ 环境校验（WSL 边界 / 云同步目录 / 编码）
 ├─ 加载 token（OS 凭据库优先，回退到 0600 权限文件）
 ├─ 建立 WS 连接（指数退避：1s,2s,4s,8s,…,60s 上限）
 ├─ 发送 hello（agent_id / version / runtimes）
 ├─ 启动 watchdog 监听四个 runtime 目录
 └─ 任务循环
      ├─ 单任务串行执行（避免并发写同一目录）
      ├─ 写操作获取全局写锁（与 CLI / MCP 共用，FR-1.0.17）
      └─ 结果回传 + 更新本地 SQLite
```

**并发控制**：任务队列串行 + 进程级文件锁。**不做并发写**——单人场景下并发带来的复杂度远大于收益。

> **锁的作用域是三个入口共享的，不是 daemon 独有（FR-1.0.17）**
>
> CLI、daemon、MCP 三个模式都能写同一批 Runtime 目录。只在 daemon 内加锁，等于"daemon 正在 push 时你在终端敲 `skillos push` 会互踩"。
>
> **实现方式**：锁下沉到 `services` 层的写操作入口（`core/fs` 写函数的第一道关），三种模式自动继承，**不在各模式里各写一遍**。
>
> 锁文件 `~/.skillos/.lock`；持有时长覆盖整个写事务；用 `filelock`（纯 Python、跨平台），超时 30s，超时报错退出不静默跳过。**禁用 `fcntl` / `msvcrt`** —— 前者 Unix-only，Windows 上 import 即崩（`05` P0-3）。
>
> **前后台语义分级 + Windows 抢锁语义（`06` A6）**
>
> | 场景 | 行为 |
> |---|---|
> | 后台任务（daemon 批量 push） | 可能持锁 10–15s（含 git 操作），**允许长持锁**，但锁内**不得有网络 I/O**（见下方四条禁令） |
> | 前台交互（CLI 敲命令 / Web 点击） | **等待**而不是立即失败；等待上限 20s，超时才报 `BUSY`。立即失败会让"后台正在批量分发"变成"你现在什么都干不了" |
>
> **抢锁失败必须按"任何错误都重试"实现**：Windows 的 `LockFileEx` 冲突返回的是 `ERROR_LOCK_VIOLATION`，**不会映射成 `WouldBlock`** —— 若代码写成 `except WouldBlock: retry`，在 Windows 上会**直接抛出**，且只在并发时才复现。规则：抢锁循环里**不对异常类型做分支**，统一退避重试直到超时。
>
> **锁诊断 stamp（`06` B7）**：持锁时把 `pid` / `hostname` / `operation` / `start_time` 写进锁文件旁的可读 stamp（**该 stamp 不 fsync**，见禁令第 2 条）。抢占失败时把这四项报给用户（`FR-2.4.9`），让"repository is busy"可追责到具体操作 —— 而不是让用户干等 30 秒凭空猜。

> **持锁期间的四条禁令（`07` D5 / M4）**
>
> 锁的持有时间直接等于用户看到 `repository is busy` 的等待时间。持锁段内**禁止**：
>
> 1. **任何网络 I/O** —— `git ls-remote` / 上游检查 / 云端回传一律在锁外完成（判据见 2.2.4）；
> 2. **`fsync`（尤其 fsync 目录）** —— macOS 的 `F_FULLFSYNC` 会 flush **整个卷**，一次锁内 fsync 能让整机卡顿；
> 3. **全量目录 rename**（批量分发时尤其）—— 拆成 per-Skill 事务，每个事务短锁；
> 4. **改目录 mtime** —— 会触发 watchdog 自己的事件（见下）。
>
> 这些约束要写进 `services` 层**契约表**，不只靠自觉 —— 上游正是因为"没人记得 `ls-remote` 在锁里"才踩了 20 秒卡死（#315）。

> **自写静音窗（`07` N19 / N20 / N21）**
>
> daemon 的 watchdog 监听 runtime 目录，而我们自己 `push` 正是在改这些目录 —— 不处理就是**自己触发自己**（事件风暴 + 重复 scan）。
>
> | 机制 | 做法 |
> |---|---|
> | 静音窗 | 写入前登记 `(路径集, 1.2s 单调时钟窗口)`，窗口内同名路径事件直接丢弃 |
> | 目录指纹 | 静音判定用**内容哈希**而非 mtime（mtime 被上面禁令第 4 条影响） |
> | 启动扫描后置 | 启动时先建连接、加载状态，**最后**才起 watchdog —— 否则启动期全量扫描事件灌满任务队列 |
> | 候选集门闩 | 事件入队前先与"我们正在写的候选集"比对，命中即静音 |

> **WSL 文件系统边界（NFR-7.7）**
>
> daemon 操作的是**它自己所在文件系统命名空间**里的路径。若 daemon 跑在 WSL，它看到的是 `/home/x/.claude/skills`；而 Windows 侧的 Claude Code 读的是 `C:\Users\x\.claude\skills` —— **两个不同的目录**。结果是分发"成功"了，但 Agent 完全看不到。
>
> 约束：daemon 必须与它要操作的 Runtime **处于同一命名空间**。
>
> - 全部在 Windows：daemon 装 Windows 侧，操作 `C:\Users\x\.claude\skills` ✅
> - 全部在 WSL：daemon 装 WSL 侧，Agent 也跑在 WSL ✅
> - 混用（daemon 在 WSL、Agent 在 Windows）❌ 明确不支持
>
> 由 `doctor` 检查项 6 与 daemon 启动校验拦截。

#### 2.5.3 MCP（`FR-1.3.x`）

stdio 传输，工具清单见 4.3。**写入类工具默认 `dry_run=true`**（`FR-1.3.3`），避免 Agent 误操作本地目录。

> **两条对 MCP 的额外收紧**
>
> 1. **不暴露 `force`（FR-1.3.5）**：MCP 工具的参数里没有 `on_conflict`，冲突只能中止（`abort`）或跳过（`skip`）。`force` 只存在于 REST / Web 人工链路 —— **危险决策留给人**。
> 2. **不暴露通用 git / shell（OUT-14）**：工具集只有领域操作（`list_skills` / `get_skill` / `status` / `check` / `version_log` / `sync_push` / `sync_pull` / `upgrade`），没有 `git(cmd, args)`。Agent 走的是 **SkillOS 领域 API**，不是 Git API。

**云端文件读写必须经 daemon，且云端不缓存文件内容（FR-3.12）**：

| 数据                                | 是否进云端      | 说明                                                  |
| --------------------------------- | ---------- | --------------------------------------------------- |
| 文件树（path / size / hash / is_text） | ✅ 缓存       | **Dashboard 漂移矩阵的数据源**，随 `scan` 上报，不可砍              |
| **文件内容**                          | ❌ **不进云端** | `GET /api/skills/{id}/file` 一律下发 `file_read` 任务实时取回 |

**为什么内容不进云端**：内容缓存需要一整套失效机制（谁改了、何时失效、多端如何对齐），单人项目维护它极易出 Bug —— Web 端读到旧内容，基于旧内容编辑保存就会覆盖新改动。

**但真正的防覆盖靠乐观锁，不是靠"不缓存"** —— 没有缓存照样会覆盖（两个客户端基于同一份内容编辑）。所有写接口强制校验 `base_hash`，不匹配返回 `409 STALE`（见 4.1 与 NFR-3.1）。

#### 2.7.1 前端技术选型

> **本节是前端选型在 SDD 中的落地口径。** 选型的论证与决策记录在 `02-技术设计.md` §9（技术选型确认）与 §10.1（决策 T1–T8），本节不重复论证，只补齐 04 需要的落地约定。  
> **冲突时的裁决顺序**：选型以 `02` 为准，落地细节以本节为准。

| 层      | 选型                                       | 落地约定                                            |
| ------ | ---------------------------------------- | ----------------------------------------------- |
| 框架     | **React + TypeScript**（SPA）              | **不用 Next.js** —— 控制面 / 数据面分离下 SSR 无收益（`02` §9） |
| 构建     | **Vite**                                 | Monaco 的 worker 必须显式注册，见 2.7.5                  |
| 样式     | **Tailwind + shadcn 风格组件**               | 设计令牌唯一来源见下表下方说明                                 |
| 编辑器    | **Monaco**（动态 `import()` 异步加载）           | 不进主 bundle；demo 主线不得依赖它                         |
| 服务端状态  | **TanStack Query**                       | WS 事件驱动缓存失效，不自行维护平行状态（2.7.3）                    |
| 实时     | **WebSocket `/ws/ui`**                   | 自研轻量 hub（4.2），不引入第三方实时服务                        |
| API 类型 | **`openapi-typescript` → `schema.d.ts`** | 提交进 git、禁止手改；请求代码手写于 `client.ts`（决策 T3）         |
| 目录     | `web/src/{pages,components,api,ws}`      | 页面与组件树见 2.7.2                                   |

**设计令牌**：唯一来源是 `app/index.html` 的 `:root` Design Tokens 段与 `Skill OS 设计系统.pdf`。漂移 7 态是产品视觉语言的主体，采用**色 + 形双编码**，令牌名 `--drift-*` 已在原型中落定 —— 前端实现须直接沿用，**不得另起命名或另调色值**。

**前端选型红线**（架构约束，不是风格偏好）：

1. **浏览器不得直连数据库**（含任何 BaaS / SDK 形式的库直连）。所有数据访问一律走 D3 云端后端的 REST / WS；**文件内容必须经 daemon 代理实时取回**（1.2 控制面 / 数据面划分、`FR-3.12`）。绕开 API 层就是绕开 daemon 任务链路，会同时破坏离线态降级与 `base_hash` 乐观锁。
2. **不引入 SSR / Serverless 运行时**：daemon 依赖常驻 WebSocket 长连接（`/ws/agent`，见 4.2 与 5.1）。Serverless / Edge 环境无法承载持久连接，云端后端与 WS Hub 必须同进程常驻（1.4 部署架构）。
3. **不引入第二套校验体系**：请求 / 响应的类型真源是 `schema.d.ts`。后端契约变更靠 TS 编译报错暴露，而不是靠运行时 schema 兜底（决策 T3）。

> 结论：前端技术栈**只在 SPA 内部演进**，不触及控制面 / 数据面的边界。任何需要"前端直接拿数据"的需求，先检查是否已有对应的 REST / WS 接口。

```
#### 2.7.3 状态管理

服务端状态用 TanStack Query（缓存 + 失效）；实时状态用 WS 事件驱动失效，不自行维护平行状态。

#### 2.7.4 daemon 离线态（`FR-2.4.4`）

全局维护一个极简 `DaemonStatus`（只存 `connected` / `last_seen`），所有写操作按钮的 `disabled` 都由它派生，而不是各页面各判一次。

| 状态 | 写操作 | 读操作 |
|---|---|---|
| daemon 在线 | 正常 | 正常 |
| **daemon 离线** | **全部禁用 + 遮罩提示「本地 daemon 已离线」** | **保留**（继续用已有数据），但顶部标注「数据可能过期」 |

> 注意不要"离线就清空页面"—— 读缓存仍然有价值，只有写操作必须被拦住。收到 `daemon_status{connected:false}` 时立刻切换，不等待下一个轮询周期。

#### 2.7.5 编辑器加载（`FR-2.2.3`）

Monaco 必须**异步加载**（动态 `import()`，不进主 bundle），保证 Dashboard 首屏不被它拖慢。

> **vite 下 Monaco 的 worker 配置是必做项**，不配就是白屏：用 `vite-plugin-monaco-editor` 或 `?worker` 导入显式注册 editor / json / ts worker。
>
> **设计约束**：demo 主线（Dashboard + 漂移 + 一键分发）**不得依赖 Monaco** —— 即使编辑器加载失败，demo 仍要能完整跑通。

#### 2.7.6 API 层（决策 T3）

```

web/src/api/  
├─ schema.d.ts    ← openapi-typescript 生成，提交进 git，禁止手改  
└─ client.ts      ← 手写 fetch 薄封装（统一 baseURL / 错误码 / 事件失效触发）

````

- 生成命令：`npm run gen:api`（读 `http://localhost:8000/openapi.json`）。
- 请求代码**手写**，类型从 `schema.d.ts` 取；调用 `paths['/api/skills']['get']` 这类索引类型，后端改契约前端即编译报错。
- 后端改接口后的固定动作：跑 `gen:api` → 看 TS 报错 → 修调用点。

#### 2.7.7 沙盒模式（`FR-2.4.3` / `FR-3.10`）

`SKILLOS_SANDBOX=1` 时，前端**不隐藏写操作**。

> **这是本轮修正的关键一处。** 原设计写的是「隐藏写入类操作」，与 demo 需求直接冲突 —— 演示高潮就是「改坏 → 回滚」，禁用写等于把产品最核心的能力从评委眼前拿掉。

沙盒下只改三件事：

| # | 变化 | 实现 |
|---|---|---|
| 1 | 顶部常驻「演示模式」横幅 | 前端读 `SKILLOS_SANDBOX` 标志 |
| 2 | 侧栏出现「重置沙盒数据」按钮 | 调 `POST /api/sandbox/reset`，恢复预置数据（评委可反复体验） |
| 3 | 所有 Runtime 根路径指向容器内虚拟目录 | `SKILLOS_ROOT`，前端无感 |

**隔离靠文件系统边界，不靠 UI 禁用**：沙盒进程的 `root` 全部落在容器内（`/runtime/.claude` 等），物理上触达不到宿主 `~/.claude`。`scan` / `push` / `pull` / 编辑 / 回滚全部可用。
````

### 4.2 WebSocket 协议

**`WS /ws/agent`**（daemon 出站）

```json
// daemon → cloud：握手
{"type":"hello","agent_id":"win-01","version":"0.1.0",
 "runtimes":["claude","agents","workbuddy","codex"],"token":"<token>"}

// cloud → daemon：任务下发
{"type":"task","task_id":"t_123","op":"push","params":{"skill_id":"...","runtime_key":"claude"}}

// daemon → cloud：结果
{"type":"result","task_id":"t_123","ok":true,
 "data":{"from_state":"outdated","to_state":"synced","files":12}}
{"type":"result","task_id":"t_123","ok":false,
 "error":{"code":"PERMISSION","message":"..."}}

// daemon → cloud：事件
{"type":"event","event":"drift_changed","payload":{"skill_id":"...","matrix":{...}}}

// 心跳
{"type":"ping"} / {"type":"pong"}
```

| op            | params                                            | data                           |
| ------------- | ------------------------------------------------- | ------------------------------ |
| `scan`        | `{roots?, ignore?}`                               | `{items: [ScannedSkill]}`      |
| `status`      | `{skill_id?}`                                     | `{matrix, summary}`            |
| `push`        | `{skill_ids, runtime_keys, on_conflict, dry_run}` | `{results, held_back_removals[], skipped_assets}`    |
| `pull`        | `{skill_id, runtime_key}`                         | `{new_version, changed_files}` |
| `file_read`   | `{skill_id, path, ref}`                           | `{content, hash}`              |
| `file_write`  | `{skill_id, path, content, message, base_hash}`   | `{hash, commit}`               |
| `version_log` | `{skill_id, limit?}`                              | `{items: [Commit]}`            |
| `diff`        | `{skill_id, base?, head?, path?}`                 | `{unified, files}`             |
| `rollback`    | `{skill_id, ref, paths?}`                         | `{commit}`                     |

> **原 `git {skill_id, cmd, args}` 已删除（OUT-14，这是本轮的安全修正）**
>
> 通用 git 透传等于给云端开了一条「触发 → 本地执行任意 git」的通道，间接成为命令执行入口。改为三个**具名领域操作**（`version_log` / `diff` / `rollback`），参数是结构化的，没有 `cmd`、没有 `args`。
>
> 原则：**任务表即白名单**。新增能力必须加具名 op，不得引入通用透传。

> **`file_write` 的 `base_hash` 为必填**（NFR-3.1）：daemon 侧同样校验乐观锁，不因为"是云端下发的"就跳过。缺少或过期一律拒绝。

> **`request_id` 守卫（`07` N12）**
>
> 每个 task 从云端下发时必须带 **`request_id`**（云端生成、全局唯一），daemon 的 `result` 原样回带。云端按 `request_id` 去重，**不按 `task_id`** —— 重连补发与网络重试都可能让同一任务被处理两次。
>
> 三个守卫点：① 云端收到 `result` 时先查 `request_id` 是否已消费；② daemon 执行写操作前先查该 `request_id` 是否执行过（近窗口 LRU）；③ **无 `request_id` 的任务直接拒绝**，不做宽容处理。

> **结构化冲突信封（`07` N6 / D4）**：所有写类 op 的错误响应统一为
> `{"ok":false,"error":{"code":"TARGET_CONFLICT","path":"...","held_back_removals":[...],"detail":"..."}}`。
> `held_back_removals` 是**结构化路径列表**，不是一句提示文案 —— 前端要拿它渲染确认弹窗，CLI 要拿它逐行打印，**两边必须同源**（FR-3.19）。

**`WS /ws/ui`**（前端订阅）

```json
{"type":"task_progress","task_id":"t_123","done":7,"total":12,"current":"code-review"}
{"type":"task_done","task_id":"t_123","summary":{"ok":11,"failed":1}}
{"type":"drift_changed","summary":{"synced":48,"outdated":8,"conflict":1}}
{"type":"daemon_status","connected":true,"last_seen":"..."}
```

前端收到事件后**失效对应 Query 缓存并重新拉取**，不直接改本地状态。

**`daemon_status` 的语义（FR-2.4.4）**：

| 字段                 | 含义                                          |
| ------------------ | ------------------------------------------- |
| `connected: false` | 前端**立即**进入受限态：所有写操作禁用 + 遮罩；读操作保留但标注"数据可能过期" |

**daemon 断开时，未完成任务的收尾**：

| 情形                     | 处理                                                            |
| ---------------------- | ------------------------------------------------------------- |
| 任务在 daemon 侧已完成，结果回传丢失 | daemon 重连后**主动补发未 ack 的 `result`**（云端按 `task_id` 去重）          |
| 任务未执行完，连接断开            | 云端将任务标记 `unknown`（**不是 failed**）；重连后由前端发起一次 `status` 刷新确认真实状态 |
| 前端本地有进行中的进度条           | 断开时**冻结**并提示"连接中断，正在重连"，不伪造成功或失败                              |

> 原则：**断连不等于失败**。状态未知时必须落到 `unknown` + 重新查证，而不是乐观判定成功或失败。

3. **不暴露通用 git / shell**（OUT-14）：工具集只有领域操作，没有 `git(cmd, args)`。
4. **无设备管理工具**：token 撤销属安全敏感操作，只存在于 Web 人工路径（`DELETE /api/devices/{id}`）。
5. **`dry_run` 与真跑共用同一份判据**（`FR-1.3.7` / `07` N17）：干跑返回的 `held_back_removals` / 冲突清单必须**与真跑完全一致**（同一函数、同一代码路径）。禁止为预览另写一套判断 —— 那会让"预览说没事、真跑删了文件"成为可能。
6. **写类工具默认 `ReplacePolicy = NO_CLOBBER`**（`FR-1.0.26`）：MCP 参数里**不暴露 `replace_policy`**，Agent 只能触发"不覆盖"的写入；需要覆盖时由 Web 人工路径显式确认。

> **Agent 的边界是清晰的：能执行能力，不能执行危险决策。**

## 5. 关键流程时序

### 5.1 daemon 配对

```text
用户            云端                     本地 daemon
 │                │                          │
 │─ 登录 ─────────►│                          │
 │◄─ 显示 6 位码 ──│                          │
 │                │                          │
 │─ skillos daemon --pair ABC123 ────────────►│
 │                                           │─ 建立 WS 连接
 │                                           │─ hello + code
 │                │◄──────────────────────────│
 │                │─ 校验码有效且未用
 │                │─ 限流检查：scope(user/ip) 未处于锁定期
 │                │─ 签发 token（只存 hash）
 │                │──────── token ───────────►│
 │                                           │─ 存 OS 凭据库
 │                │◄──── hello + token ───────│
 │                │─ 注册 agent_id
 │◄─ 控制台显示设备在线 ───────────────────────│

失败路径（FR-3.15）：
 │                │─ 校验失败 → pairing_attempts[scope].failed_count += 1
 │                │─ 连续 5 次 → locked_until = now()+60s，期间一律拒绝
 │                │─ 校验成功 → 清零该 scope 计数
```

**安全要求**

1. `NFR-2`：token 只存哈希；daemon 侧优先存 OS 凭据库（Windows Credential Manager / macOS Keychain），回退到权限 0600 的文件；**禁止写入项目目录**。
2. `FR-3.15`：**配对必须限流**。6 位码 = 10⁶ 空间、10 分钟窗口，不限流理论上可枚举。限流按 `user` 与 `ip` 双维度计数，任一命中锁定即拒绝。
3. `FR-1.2.8`：设备可撤销（`revoked_at`），撤销即断连；**不物理删除**，保留撤销痕迹。

### 5.2 分发（push）

```text
入口(CLI/Web/MCP)
  │
  ├─1 校验参数 + 权限
  ├─2 从 Git 读 canonical 快照
  ├─3 【门禁】run_gate(snapshot) ← FR-1.0.11 / NFR-10.1
  │     ├─ has_error → CLI: 需显式 --allow-gate-failure 才继续
  │     │              MCP: 直接返回 GATE_FAILED + 规则明细（无开关，FR-1.3.6）
  │     │              Web: 返回拦截原因，由用户在 UI 显式确认后重试
  │     └─ 结果落库 skill_checks（无论通过与失败，NFR-10.1）
  ├─4 【跨目标前置全检】所有目标的 drift + 归属判定，**在写任何一个之前全部完成**
  │     ├─ 任一 binding 非 SYNCED（六态之一）→ **整体拒绝**，返回逐目标明细（FR-1.0.28）
  │     │     · 唯一例外：目标「不适用」（磁盘无目录 且 binding 无记录）→ 视为首装，允许
  │     │     · baseline_source = imported 的 binding 只做两方比对（§2.2.5）；
  │     │       两方不等同样**拒绝** —— 无法区分"谁超前"就不动手
  │     └─ 任一目标命中 removals → **整体拒绝**，返回 held_back_removals（FR-1.0.26）
  ├─5 对每个 runtime：adapter.render_layout() → desired
  ├─6 drift 复核（至此才允许 per-runtime 分支）
  │     ├─ adapter_outdated → 先应用新模板（不判 CONFLICT，FR-1.0.19）
  │     └─ SYNCED / 首装 → 继续
  ├─7 逐目标事务：备份 → 写临时目录 → removals 复核 → 哈希校验 → 原子交换 → **回读自证**
  ├─8 更新 runtime_bindings
  │     installed_commit / adapter_version / installed_hash / installed_version
  │     baseline_source → distributed
  ├─9 写 sync_records（含操作者 FR-1.0.22 / removals 明细）
  └─10 触发 WS 事件 → UI 刷新
```

> **为什么门禁在步骤 3 而不是循环内**：① 门禁只依赖 Skill 内容，与目标 Runtime 无关，放在循环里会重复计算；② **必须在任何写入之前完成全部判定** —— 否则会出现"前两个 Runtime 写完了、门禁在第三个才发现不过"的半成品状态。这与 `distribute` 的原子性要求同源（NFR-3）。

> **为什么前置全检在步骤 4（`07` D3 / FR-1.0.28）**：不做就是上游 1.35.1 的形状 —— per-runtime 循环写到第三个才发现冲突，前两个已落盘，而**用户被告知"成功"**，顺着后续提示操作即数据丢失。铁律：**无法证明安全时一个字都不写**（NFR-11）。`SYNCED`（内容 hash 相等）是**唯一**可作"可安全覆盖"证明的状态。

### 5.3 冲突解决

```text
前置条件：adapter_new = false
  （adapter 版本变更时不进 CONFLICT，见 §2.1.3 判定表末两行 / FR-1.0.19）

检测到 CONFLICT（disk_dirty = true 且 content_new = true）
  │
  ├─1 取三方内容（base 由 commit 现算，不用版本号反查）：
  │      base   = render(canonical@installed_commit, 当前 adapter_version)
  │      local  = 磁盘文件
  │      remote = render(canonical@HEAD, 当前 adapter_version)
  ├─2 判定粒度：整文件级（本期不做块内合并，见 OUT-11）
  │      └─ 文本文件附带 diff 摘要供人判断；二进制只显示"已变更"
  ├─3 【决策前快照】无论后续选哪项，先把 local 与 remote 各存一份安全快照
  │      → 快照对用户可见、可再回滚（回滚本身也是破坏性操作，FR-2.2.6）
  ├─4 UI / MCP 呈现四个选项：
  │      A. 保留本地    → 以 local 覆盖 repo（记为新版本）
  │      B. 保留仓库    → 以 remote 覆盖本地磁盘
  │      C. 两个都保留  → local 以冲突副本名（如 SKILL.local-conflict.md）落库，
  │                       remote 同时进库；两份都在，由人后续合并
  │      D. 暂不处理    → 标记待办，drift 维持 CONFLICT，不写任何文件
  ├─5 选 A / B / C → 写回（带 base_hash）→ 新 commit → 重新 push → drift 应为 SYNCED
  ├─6 选 D         → 只写 sync_records(action=defer)
  └─7 写 sync_records(action=resolve|defer)
```

> **「两个都保留」为什么值得加（`06` B2）**：三选一的隐含前提是"我比较得出哪个对"。但真实场景里，本地那版是刚调的、远端那版是同事删了半页 —— **人当下就是分不清**。这时最安全的动作是"两份都留着、回头再合"，而不是被迫在信息不足时丢掉一份。它是**唯一不丢内容**的解法，与 NFR-11 同源。
>
> **MCP 路径不提供 C 选项**：Agent 不得自行创建"冲突副本"（等于替人决定保留两份，会把仓库搞乱）。C 只存在于 Web 人工路径。

**批量场景：单个 Skill 的冲突不阻塞整批（FR-2.1.4 / `06` B3）**

| 层级 | 规则 | 依据 |
|---|---|---|
| **同一 Skill → 多个 Runtime** | 任一 binding 非 `SYNCED` → **整体拒绝**，不写任何目标 | FR-1.0.28 / NFR-11.2 |
| **多个 Skill 之间** | 某个 Skill 冲突 / 被拒 → 该 Skill 进「需要处理」列表，**其余 Skill 照常分发** | FR-2.1.4 / `06` B3 |

> **两者不矛盾，是两个层级**：前者保护"一个 Skill 的多份副本不许部分更新"（同一份内容落到 N 个地方必须一致）；后者避免"一个坏 Skill 拖垮整批"（批量 20 个，1 个冲突不该让 19 个停下）。**混淆这两层会走向两个极端** —— 要么半成品分发，要么一个坏 Skill 让整批无法进行。

> **`base` 必须是同一 adapter 版本下渲染出来的**：若 `base` 与 `remote` 用了不同 adapter 版本，两侧的模板差异会被当成内容差异，产生假冲突。这正是 FR-1.0.19 要把 adapter 变更单独拎出去的原因。

**为什么不做块内合并**：

- diff3 冲突块解析 + 前端逐块交互组件，成本 2–3 天，而**单人场景冲突率极低**（同一 skill 要既在本地改又在 repo 改才会冲突）。
- 为低频场景做重 UI 不划算。块内合并**本期不实现**，`core/version.py` 也不再保留 `merge_file`（OUT-11 / OUT-14：只暴露具名方法），待 P4 之后确实需要时再加。

**明确不做（OUT-12）**：让 Agent 自动生成合并结果并直接落盘。Agent 可以**给建议**，但落盘必须走同一套写接口（带 `base_hash`）—— 否则绕过乐观锁，且演示时结果不可控。

**兜底**：`on_conflict` 默认 `abort`（见 4.1 的 push 接口），批量分发时遇到冲突整体停下，不会部分成功部分跳过。

### 5.4 Agent 经 MCP 分发（Demo 高潮二）

```text
用户 → Claude Code：「把 code-review 同步到 Codex」
  │
  ├─ Agent 调 skillos_status{slug:"code-review"}
  │    → { codex: { state: "outdated", ... } }
  ├─ Agent 调 skillos_sync_push{slug, targets:["codex"]}   ← dry_run 默认 true

  ├─ Agent 向用户确认
  ├─ 用户确认

  └─ Agent 汇报结果
```

## 6. 错误处理与日志

### 6.1 错误分级

| 级别                                 | 处理                                                                        |
| ---------------------------------- | ------------------------------------------------------------------------- |
| 单文件解析失败                            | 降级继续，记录 warning，不中断全量扫描                                                   |
| 单 Skill 分发失败                       | 记录失败明细，继续其余 Skill                                                         |
| 原子写失败                              | 从备份还原，返回 `restore_ok`                                                     |
| 分发中断残留                             | 启动 / `doctor` / push 前检出并恢复（FR-1.0.15）                                    |
| daemon 离线                          | 云端返回 `503 DAEMON_OFFLINE`，前端进入离线态（禁写、读保留）                                 |
| CONFLICT                           | 返回 `409 CONFLICT`，附三方内容，等待人工决策                                            |
| **STALE**                          | 返回 `409 STALE`（`base_hash` 不匹配），前端提示重新加载，**不覆盖**                          |
| **PATH_TRAVERSAL**                 | 返回 `400 PATH_TRAVERSAL`，不回显解析后的绝对路径                                       |
| **NAME_CONFLICT / NAME_COLLISION** | import 时报出，列出各副本摘要，等用户指定主副本                                               |
| **RATE_LIMITED**                   | 配对校验连续失败 5 次 → `429 RATE_LIMITED`，附 `retry_after`；不泄露"码是否存在"              |
| **REMOVALS_REQUIRE_CONFIRM**       | 本次写入将删除目标已有内容 → `409`，响应含 `held_back_removals[]` 路径清单；**无人值守路径不报错而是跳过**并记 `skipped_removals`（FR-1.0.26） |
| **TARGET_CONFLICT**                | 归属判定失败（`NO_CLOBBER` 遇非空目标 / `RECORDED` 内容不匹配）→ `409`，**不做任何写入**（FR-1.0.26） |
| **GATE_FAILED**                    | 质量门禁 `error` 级拦截 → `422` + 规则明细；CLI 需 `--allow-gate-failure` 才继续，**MCP 无开关**（FR-1.0.11 / FR-1.3.6） |
| **PARTIAL_REJECT**                 | 多目标分发中任一目标非 `SYNCED` → 整体拒绝，返回逐目标明细；**没有任何目标被写入**（FR-1.0.28） |
| **adapter_outdated**               | **不是错误、不是状态**：作为 `DriftReport` 的独立布尔返回，UI 显示「模板已升级」徽标（FR-1.0.19）          |
| **has_untracked_assets**           | 同上，独立布尔；为真时 `state` 即使为 `synced` 也**必须显示 `SYNCED*`**（FR-1.0.20 / NFR-3.4） |
| **UNMANAGED / ORPHANED**           | 正常状态，非错误。`UNMANAGED` 引导 import；`ORPHANED` 引导清理磁盘副本或恢复 canonical           |
| **PROTOCOL_MISMATCH**              | 仓库协议版本与本机不符（树里有 `protocol.json` 但 commit 无对应 trailer，或 trailer 版本更高）→ 拒绝混用并提示升级，**不得静默继续**（FR-1.0.29） |
| **META_INDEX_MISMATCH**            | 元数据说 0 个 Skill 但仓库里确有 Skill 目录 → **拒绝重建索引**（否则清空整库），抛类型化错误供启动流程定向自愈（FR-1.0.30） |
| **BUSY**                           | 抢锁等待超时（前台 20s）→ `409 BUSY`，响应**必须含持锁者诊断**（`pid` / `hostname` / `operation` / `start_time`，FR-2.4.9）。实现约束：**抢锁循环不得按异常类型分支** —— Windows 返回 `ERROR_LOCK_VIOLATION`，不会映射成 `WouldBlock`（`06` A6） |

- **禁止记录**：token、凭据、完整文件内容（只记 path 与 hash）

## 7. 安全设计

| 项         | 措施                                                                                  | 需求                           |
| --------- | ----------------------------------------------------------------------------------- | ---------------------------- |
| 凭据        | token 只存哈希；本地存 OS 凭据库；禁止入项目文件                                                       | NFR-2                        |
| 传输        | 全链路 HTTPS / WSS                                                                     | —                            |

> **T1 落地约束**：`core/fs` 全部文件操作显式接收 `root: Path`，禁止隐式读取全局根；路径穿越校验在此层统一实现。  
> **T2 落地约束**：超阈值文件标记 `skill_files.in_git = false`，**不参与漂移哈希**，前端显示「含未纳管资产」徽标（不是"警告标签"就完事 —— 状态本身必须降级为 `SYNCED*`）。  
> **T3 落地约束**：生成命令 `npm run gen:api`；后端改接口后必跑，靠 TS 编译报错定位调用点（详见第 2 节 API 层）。  
> **T6 落地约束**：`runtime_bindings` 的 `status` 为**判定结果缓存**，不是事实源；事实源是磁盘 + commit + adapter 版本，任何时候都应可重算。  
> **T7 落地约束**：adapter 修改字段策略 / sidecar 模板 / 目录布局 ⇒ **必须 bump `version`**，否则历史 base 会静默算错。  
> **T9 落地约束**：`resolve_identity()` 返回 `None` 时，**调用方唯一允许的动作是报冲突**，禁止 fallback 到"取第一个"或"取最像的"。`import`、`scan`、`drift` 三处都要遵守 —— 这三处任一处偷偷兜底，都会重新打开误覆盖的路径。  
> **T10 落地约束**：门禁判定与 `check` 命令**调用同一个 `run_gate()`**（NFR-10.5）。实现时若为 `push` 单独写一遍判断逻辑，等于埋一颗"两处判定漂移"的雷。  
> **T11 落地约束**：`health_score` 只读、只用于排序与展示。代码层面**不得**出现 `if health_score < X: block` —— 放行判定只有 `GateResult.has_error` 一个入口。  
> **T12 落地约束**：`scan` 只遍历 `RuntimePaths` **显式列出的**目录；扫描根必须**按 canonical path 去重**（软链指向同一物理目录时不得扫成两份）。  
> **T13 落地约束**：`ReplacePolicy` **不得有默认值** —— 代码层面用关键字强制传参（`*, policy: ReplacePolicy`），漏传即 `TypeError`，不允许"忘传就默认安全"。  
> **T14 落地约束**：removals 的**判定与执行必须用同一份路径集合**（算出 → 展示 → 确认 → 用同一集合执行）；两次计算之间目标被改动则**重新询问**（NFR-11.5）。  
> **T15 落地约束**：`push` 的 per-runtime 分支只能出现在**前置全检通过之后**（§5.2 步骤 6）；循环内**不得**再有"发现冲突就 abort"的分支。  
> **T16 落地约束**：写入 `installed_hash` 的只能是 `hash_bytes`；`compare_normalized()` 的返回值**不得**参与任何状态判定。  
> **T17 落地约束**：`with lock:` 块内**不得出现网络 I/O / `fsync` / 目录整体 rename**（单测 mock 网络与 `os.fsync`，断言持锁期间未被调用）；抢锁循环**不得按异常类型分支**（写 `except WouldBlock` 会在 Windows 上失效）。  
> **T18 落地约束**：`protocol.json` 与 commit trailer 的一致性检查**必须双向**（有文件无 trailer = 旧客户端；有 trailer 无文件 = 需补写 sticky 文件）。commit 版本**高于**本机支持版本时进入**只读模式**，不得写入。  
> **T19 落地约束**：`rebuild_index()` 的两道前置 —— ① 读元数据；② 数仓库 Skill 目录。**元数据为空而目录非空 → 抛 `META_INDEX_MISMATCH`，不得继续**。注意区分路径：**首次克隆**（元数据本就应该为空）走**全量扫描重建**，不走 `rebuild_index()`。  
> **T20 落地约束**：`sync_service` 里两个循环层级必须显式分开 —— 外层「Skill 迭代」允许 `continue`（跳过该 Skill），内层「Runtime 迭代」**不允许** `continue`（必须整体拒绝）。代码评审项：内层循环体内不得出现 `break` / `continue`。  
> **T21 落地约束**：提供 `path_key(p: Path) -> str` **单一实现**，所有路径去重 / 冲突检测 / 大小写校验都调它；`Path.resolve()` 返回的仍是真实路径，**两者不可互换**。  
> **T22 落地约束**：快照必须**在任何写入之前**完成，且在 `sync_records` 里记下快照 id（可回滚到决策前）。MCP 工具参数中**没有** `keep_both` 之类的选项。

**已知风险**：

1. **Windows 原子写**：`os.rename` 无法覆盖非空目录，必须两步交换（见 2.2.2）。**已缓解**——进程被杀导致的中间态由启动残留自检恢复（FR-1.0.15）。注意：崩溃时数据并未丢失（`target.old` 仍在），属于"不一致状态"而非"数据丢失"。
2. **daemon 单点**：云端所有文件操作依赖 daemon 在线，离线时仅本地 CLI / MCP 可用（这是设计取舍，非缺陷）。缓解：前端离线态只禁写、保留读（FR-2.4.4）；断连任务落 `unknown` 而非 `failed`。
3. **哈希口径（已改写为两级，`07` D6）**：`hash_bytes` **字节级、不归一化**；行尾 / NFC / 尾随空白只在**第二级兜底比较**里处理（§2.1.3）。旧写法"归一化后进哈希"会让两端"永远可更新、来回互推"。
4. **git 层与哈希层口径**：两层都以**字节**为准 —— `hash_bytes` 不归一化，git 侧靠 `.gitattributes * -text` + 显式 `-c core.autocrlf=false` 关掉换行转换（`05` P0-1）。
5. **中文 Windows 控制台编码（P0）**：默认 cp936，CLI 输出中文 skill 名必抛 `UnicodeEncodeError`。入口强制 UTF-8 解决（详见 `05` P0-2）。
6. **云同步目录**：repo 若落在 OneDrive / iCloud / Dropbox 内，文件变按需下载占位符，哈希随机漂移。启动时检测并**警告 + 要求显式确认**（详见 `05` P0-5）。
7. **WSL 文件系统边界**：daemon 若运行在 WSL 而 Agent Runtime 在 Windows，二者文件系统命名空间不同源，同步会"成功"但 Agent 看不到效果。由 `doctor` 检查项 6 拦截（NFR-7.7）。
8. **多入口并发写**：CLI / daemon / MCP 三个写入者若各自加锁会互踩。已通过**锁下沉到 `services` 层**解决（FR-1.0.17），实现时需确认无绕过路径（如直接调用 `core/fs` 写函数）。
9. **基线依赖 adapter 的纯函数性（新增，P0）**：base 不落盘、靠 `render(canonical@installed_commit, adapter_version)` 现算。若 `render_layout()` 掺入时间戳 / 随机数 / 环境变量，历史 base 会静默算错，且**三方合并与漂移判定同时失效**。缓解：`render_layout()` 必须有纯函数单测（同输入两次调用逐字节相同），并纳入 P1 的基线工作。
10. **分发是整体替换目录（新增）**：`push` 的两步交换会整目录替换，**未纳管资产（>阈值文件）若不回收就会被静默删除**。缓解：已写入分发协议第 5 步（回收未纳管资产，同名冲突以 canonical 为准并备份）。
11. **纳管来的 binding 无有效 base（新增）**：`import` 的目录内容是用户写的，不是我们渲染的，因此 `baseline_source = imported` 时**只有两方比对**，无法区分"仓库超前"与"磁盘超前"。缓解：首次 `push` 成功后自动转为 `distributed`，三方比对才完整（见 2.2.5）。
12. **身份匹配误认导致覆盖（新增，P0）**：分层匹配若在其中任一层"兜底挑一个"，副本会绑到**错误的** Skill 上，而「导回仓库」正是写入匹配到的那一条 —— 结果是覆盖另一个 Skill（上游 1.40.0 真实事故，触发条件：库中同时存在 `Code Review` 与 `code-review`，见 `07` N8）。**缓解：`resolve_identity()` 返回 `None` 时只允许报冲突**（T9 落地约束）；`import` / `scan` / `drift` 三处都要遵守，测试需覆盖"并列候选"与"大小写近名"两个用例。
13. **健康度被误用为门禁（新增）**：`health_score` 一旦进入放行判断，就变成"调权重即可放行"，治理叙事当场失效。缓解：T11 落地约束 + 代码审查项 —— 搜 `health_score` 的所有读取点，必须全部在展示与排序路径上。
14. **`unknown` 被消化成 `ok`（新增）**：折旧维度无法判定时若悄悄落成 `ok` 或不写记录，健康度会**虚高**，决策者据此得出的结论是反的。缓解：`skill_checks.level` 枚举包含 `unknown`（表结构已约束）；UI 必须单独显示"未知 N 项"；测试断言"上游跟踪未启用时 `upstream_divergence` 必须为 `unknown` 而非 `ok`"。
15. **删除守卫被绕过（新增，P0）**：`push` / `import` / `rollback` / 导出四条写入路径中，任一未接 `ReplacePolicy` 与 removals 检查，就会重现上游"静默删除用户 `templates/`"的事故。缓解：`ReplacePolicy` **无默认值**（T13 落地约束）+ **变异验证**（删掉守卫后测试必须变红，见 `03` §8）。
16. **适配器路径未验证（新增）**：`verified_at` 为空的路径可能指向错误目录，分发"成功"但 Agent 读不到（上游对 Codex 路径给过两次相反结论）。缓解：UI 出"路径未验证"警告 + `doctor` 检查项 + **部署后回读自证**（FR-1.0.27）。
17. **锁内网络 I/O 回归（新增）**：`ls-remote` / 上游检查极易被顺手写进锁内，一次网络抖动就变成几十秒 `repository is busy`（上游 #315）。缓解：锁与网络分离写进 `services` 契约表（§2.5.2）+ 代码评审项。
18. **自写事件风暴（新增）**：watchdog 监听我们正在写的目录 → 自己触发自己（重复 scan + 队列积压）。缓解：静音窗（1.2s 单调时钟）+ 内容哈希目录指纹 + 启动扫描后置 + 候选集门闩（§2.5.2）。
19. **暂存目录被 scan 收编（新增）**：`.staged-*` / `.<name>.tmp-*` 残留会被下一次 `scan` 当成新 Skill。缓解：每次 commit 前清理（§2.2.2）；`scan` 显式排除这两类前缀。
20. **父目录误判导致整棵子树短路（新增，`06` A2）**：扫描器若把 `README.md` / `CLAUDE.md` 当作 Skill 标记，分类目录会被误判，**其下的真 Skill 全部被短路跳过** —— 表现为"扫不到"而不是"扫错了"，极难发现。缓解：检测标记白名单只有 `SKILL.md`（+ `skill.md` legacy）；单测断言"分类目录含 README 时，其下 Skill 仍被扫出"。
21. **Python 脚本把部署副本标记为已变更（新增，`06` A3）**：Skill 里的脚本一运行即生成 `*.pyc` / `__pycache__/`，不排除则漂移矩阵长期飘红。缓解：`list_content_files()` 第一类排除集必须含二者；单测断言"运行脚本后 `pack_hash` 不变"。
22. **抢锁按异常类型分支（新增，`06` A6）**：Windows `LockFileEx` 冲突返回 `ERROR_LOCK_VIOLATION`，**不映射 `WouldBlock`**。"`except WouldBlock` 才重试"的写法在 Windows 上直接抛出，且**只在并发时复现** —— 单人开发最难撞见。缓解：抢锁循环**不对异常类型分支**（`06` A6）；CI 需在 Windows 列跑并发用例。
23. **元数据为空触发清库（新增，`06` A8）**：`rebuild_index()` 若照"元数据"重建，元数据损坏 / 首次克隆时会重建出空库并写回。缓解：**元数据为空而仓库非空 → 拒绝重建**（T18 落地约束）；集成测试要覆盖"删掉元数据文件后再启动"。
24. **`path_key` 被当成写盘路径（新增，`06` A7）**：归一化键**只可用于比较**；若被当成写路径，会出现"看起来一样、其实写到别处"。缓解：类型层面区分（`PathKey` 与 `Path` 两个类型，不互相隐式转换）+ 代码评审项。
