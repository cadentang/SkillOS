## 1. 总体架构

```text
┌─────────────────────────── 云端 (Cloud) ───────────────────────────┐
│  ┌──────────────┐   ┌──────────────┐   ┌────────────────────┐     │
│  │ Web 控制台    │   │ HTTP API     │   │ WS Hub             │     │
│  │ React + Vite │   │ FastAPI      │   │ (agent + ui)       │     │
│  └──────┬───────┘   └──────┬───────┘   └─────────▲──────────┘     │
│         └──────────────────┴─────────────────────┘                 │
│                            │                                       │
│                   ┌────────▼────────┐                              │
│                   │  Postgres       │  元数据 / 协作 / 权限         │
│                   └─────────────────┘                              │
└────────────────────────────┬───────────────────────────────────────┘

┌────────────────────────────▼──────────── 本地 (Local) ─────────────┐
│  ┌────────────┐    ┌──────────────┐    ┌───────────────┐          │
│  │ daemon     │───►│ core engine  │───►│ SQLite 索引    │          │
│  │ (WS client)│    │ (无状态)      │    │ (可重建缓存)   │          │
│  └────────────┘    └──────┬───────┘    └───────────────┘          │
│                           │                                        │

│              └────────────┬────────────┘                           │

│      ▼          ▼                ▼              ▼                 │
│  ~/.claude  ~/.agents      ~/.workbuddy     ~/.codex              │
└────────────────────────────────────────────────────────────────────┘
```

### 架构要点

1. **core engine 无状态**——不持有 UI、不持有网络。CLI / HTTP / MCP / daemon 四个入口都调用它，逻辑只写一遍。
2. **daemon 主动出站**连接云端，无需公网 IP / 端口映射 / 内网穿透。
3. **Git 是唯一真相源**；SQLite（本地）与 Postgres（云端）都只是索引与元数据，可随时重建。
4. **沙盒模式**复用同一份 core，只把 runtime 根路径参数换成容器内虚拟目录 —— **不引入 VFS / Storage Provider 抽象层**（T1）。沙盒是**可写隔离**环境，`scan` / `push` / `pull` / 编辑 / 回滚全部可用。

## 1.1 交付物与部署形态

**关键结论：真正的交付物只有 3 个，不是 5 个。**

| # | 交付物 | 形态 | 运行位置 | 技术 | 阶段 |
|---|---|---|---|---|---|
| 1 | **`skillos` Python 包** | pip / pipx 包 | 本地 | Python | P0 |
| 1a | ├ CLI 模式 | 命令行进程 | 本地 | Typer | P1 |
| 1b | ├ daemon 模式 | 常驻进程 | 本地 | WS client | P2 |
| 1c | └ MCP 模式 | stdio server | 本地 | MCP SDK | P5 |
| 2 | **Web 控制台** | SPA | 浏览器 | React + Vite | P2 / P3 |
| 3 | **云端后端** | 容器服务 | 云 | FastAPI + Postgres | P2 |
| 3a | └ 沙盒变体 | 同一镜像，不同配置 | 云 | 同上 | P7 |

> **CLI / daemon / MCP 是同一个包（`skillos`）的三种运行模式，不是三个产品。**
> 三者共用 `core` 引擎与 `services` 编排层，各自只是薄封装。因此工作量不是三倍。
>
> `core` 引擎是内部库，不单独交付。

### 两条独立路径

```text
路径 A（真实） 你的浏览器 → 云端后端 ←WS← 本地 daemon → 文件系统
路径 B（本地） CLI / MCP 直连本地 repo 与 SQLite，不经云端
路径 C（演示） 评委浏览器 → 沙盒镜像（容器内虚拟根路径）
```

**路径 B 是刻意设计**：CLI 与 MCP 不依赖云端，保证离线可用、低延迟。
代价是本地需要 SQLite 索引——这正是「本地 SQLite + 云端 Postgres」双库存在的原因，而非冗余。

### 同步形态：拷贝为主，软链可选（NFR-7.9 / `06` B6）

| 模式 | 行为 | 默认 | 适用 |
|---|---|---|---|
| **拷贝** | 把渲染结果写成真实文件 | ✅ **默认** | 所有平台；跨平台稳定、不依赖权限 |
| **软链** | 在 runtime 目录放一个指向 canonical 的链接 | ⬜ 可选（按 Runtime 开启） | Linux / macOS 本地开发，**改一处全生效** |

> **为什么两种都留**：上游 README 明确"支持软链接和复制两种模式"，证明两者可共存。我们此前纠结"二选一"，但两者服务的是**不同语义** —— 拷贝是**分发**语义（快照隔离、可回滚、可漂移检测），软链是**开发**语义（实时联动）。丢掉任一个都会少一类真实用法。
>
> **Windows 上软链需管理员权限或开发者模式**，能力不足时降级 **junction**（仅目录）或直接隐藏该模式（`05` P1-2）。
>
> **不得混用**：同一 Runtime 的同一 Skill 只能处于一种模式 —— 否则漂移判定里的"磁盘现状"会有两种互斥语义，`installed_hash` 无法表达。

### 部署形态

- 线上只需 **1–2 个容器**：云端后端（顺带托管前端静态文件）+ 沙盒容器。
- 沙盒与云端后端**共用同一镜像**，仅通过环境变量切换 runtime 根路径。

### 仓库结构

**单仓（monorepo）**：`skillos/`（Python 包）+ `web/`（前端）+ `sandbox/`（沙盒配置）。单人维护不拆仓。

## 3. Adapter 设计（技术核心之一）

### 抽象接口

```python
@dataclass(frozen=True)
class RuntimePaths:
    """**路径是数据，不是代码常量**（FR-1.0.25）。上游在同一份 CHANGELOG 里
    对 Codex 路径给出过两次相反结论（07 D1）—— 靠结构容忍，不靠查清。"""
    deploy_dir: Path                   # 部署根（我们往这里写）
    scan_only_dirs: tuple[Path, ...]   # 只发现、不部署（共享发现根，如 ~/.agents/skills）
    fallback_dirs: tuple[Path, ...]    # deploy_dir 不可用时的回退顺序
    recursive_scan: bool               # 是否递归子目录（FR-1.0.8 / 06 A1）
    verified_at: str                   # 验证日期
    evidence: str                      # 依据：源码路径 / 本机实测 / 官方文档
    source: str                        # "builtin" | "custom"（用户覆盖）

class RuntimeAdapter(ABC):
    key: str                            # **带命名空间**：builtin:claude / custom:acme
    version: str                        # 适配器版本，参与 base 重建（FR-1.0.18）
    category: str                       # 分类，用于分组展示（FR-1.0.8 / 06 A1）
    supports: set[str]                  # scripts / references / assets / subskills / sidecar
    paths: RuntimePaths                 # 路径即数据

    def scan_roots(self, scope, project_dir) -> list[Path]:
        """发现集合 = deploy_dir + scan_only_dirs；**部署集合 ⊊ 发现集合**"""
    def resolve_root(self, scope: str, project_dir: Path | None) -> Path:
        """用户 override > deploy_dir > fallback_dirs"""
    def frontmatter_out(self, meta: SkillMeta) -> dict: ...      # canonical → 目标
    def frontmatter_in(self, raw: dict) -> SkillMeta: ...        # 反向
    def sidecar_specs(self, meta: SkillMeta) -> dict[str, str]: ...  # 如 agents/openai.yaml
    def render_layout(self, skill: SkillSnapshot) -> dict[str, bytes]: ...
```

> **`runtime_bindings` 不再承载路径**：路径是 **Runtime 级配置**（`runtimes.scan_only_paths` / `runtime.base_path`），不是 Skill 级事实。放 binding 会导致每个 Skill 冗余一份、用户改路径时要更新所有行（决策 T12）。
>
> **关键约束**：`adapters/` 目录中**不得出现字面量路径**（`.claude` / `.codex` 之类）。新增 Runtime 只加数据、不加代码 —— 单测可直接遍历适配器源码断言这一点。

> **字段设计取齐上游（`06` A1）**：上游 `ToolAdapter` 把 `key` / `display_name` / `relative_skills_dir` / `relative_detect_dir` / `additional_scan_dirs`（**仅发现、不部署**）/ `project_relative_skills_dir` / `recursive_scan` / `override_skills_dir` / `category` **全部当作数据**，因此新增一个 Agent 不需要改渲染器。我们按同一原则取齐 —— 其中 `additional_scan_dirs`（= `scan_only_dirs`）、`relative_detect_dir`（= 发现根）、`override_skills_dir`（= 用户覆盖）**本设计已有**，本轮补 `recursive_scan` 与 `category`。
>
> **项目级路径必须相对且不得含 `..`**（`06` B5）：项目级部署根随项目走 —— 绝对路径会让同一份配置在别人机器上写进错误位置；含 `..` 则等于把部署目标放到了项目之外。

### 字段策略（从本机实测得出）

本机现状佐证：

- `.claude/skills/brainstorming/SKILL.md` → 仅 `name` + `description`
- `.workbuddy/skills/requirement-analyst/SKILL.md` → `name` + `description` + `version: 1.0.0` + `agent_created: true`
- 30 个 skill 带 `agents/openai.yaml`（`interface.display_name` / `short_description` / `brand_color` / `default_prompt` / `policy.allow_implicit_invocation`）

因此 canonical 保存**全量字段**，各 adapter 声明 keep / drop / map：

| canonical 字段 | claude | agents | workbuddy | codex |
|---|---|---|---|---|
| name | keep | keep | keep | keep |
| description | keep | keep | keep | keep |
| version | drop | drop | keep | drop |
| agent_created | drop | drop | keep | drop |
| origin | drop | drop | drop | drop |
| allowed-tools | keep | keep | keep | keep |

> 第一版只做字段白名单 + 透传，**不做语义转译**（如工具名映射），转译留接口。

## 4. 漂移检测（技术核心之二）

> **本节的完整版在 `04-系统设计.md` §2.1.3**（含 7 态判定表与三事实归属判定）。此处只保留结论。

### 三方基线（已修正 base 的定义）

```text
base   = render(canonical@installed_commit, installed_adapter_version)   ← 「当时写进磁盘的字节」
local  = 磁盘当前内容
remote = render(canonical@HEAD, 当前 adapter_version)
```

> **`base` 不能再用 `installed_version` 反查**。原设计写的是 `git show <installed_version>:<path>`，但版本号（`v1.2.0`）**不对应唯一 commit**（`skill_versions` 自己都有 `version` 与 `git_commit` 两列）。三方合并要求 base 是精确快照，因此改为由 `installed_commit` + `adapter_version` **现算**（`FR-1.0.18` / NFR-3.5），前提是 `render_layout()` 为纯函数（`FR-1.0.8`）。
>
> 副作用：不再需要 `runtime_binding_files` 表（OUT-15）—— 能重渲染就能算出 `changed_files`。

### 状态分类（7 态）

| 状态 | 判定 | 处理 |
|---|---|---|
| `MISSING` | canonical 有、有 binding、磁盘无 | 可直接 push |
| `OUTDATED` | 磁盘未被手改，但 canonical 或 adapter 前进 | 可直接 push |
| `MODIFIED` | 磁盘被手改，canonical 与 adapter 均未变 | 可 pull 回 repo 或覆盖 |
| `CONFLICT` | 磁盘被手改 **且** canonical 前进 | **必须人工介入，整文件粒度选择** |
| `UNMANAGED` | 磁盘有目录，但无 binding（含用户自建） | 提示 import 纳管或忽略 |
| `ORPHANED` | 有 binding，但 canonical 中已删除 | 清理磁盘副本或恢复 canonical |

**判定用的三个事实**（不是直接比哈希）：`disk_dirty`（磁盘是否被手改）· `content_new`（canonical 是否前进）· `adapter_new`（渲染器是否升级）。

**判据分层（`FR-1.0.28` / `NFR-11.1`，v1.3 新增）**

| 状态 | 能否作为"目标可被安全覆盖"的依据 |
|---|---|
| **`SYNCED`** | ✅ **唯一可以** —— 它是**内容比对的结果**，能证明该副本没有独有内容 |
| 其余六态 | ❌ 一律不可以 |

> 上游 `1.35.1` 的真实事故：多副本 skill 推的是"agent 名排序第一份"，**提示成功而改动一字未到中心**，顺着后续提示操作即**数据丢失**。铁律：**无法证明安全时，一个字都不写。**

**新鲜度判据（v1.3 新增，`FR-1.0.6`）**

- **第一判据只能是「内容 hash 不等」**；`mtime` 只在内容已确定不同之后用于**提示方向**，绝不单独用于判定"谁更新"。
- **明文禁止读取 `updated_at` 之类的 DB 列参与判定**：上游 `1.34.2` 用"数据库行写入时间"当新鲜度 → 刚改过的副本显示成"中心更新"，顺着操作就覆盖了。
- **索引重建时内容未变必须保留原时间戳**（上游 `1.25.1` 重启后状态翻转）。

**哈希口径：两级结构（v1.3 修正，`FR-1.0.5` / 决策 T13）**

| 层 | 函数 | 作用 | 是否进存储身份 |
|---|---|---|---|
| ① | `hash_bytes`（字节级，`sha256(path + "\0" + sha256(content))` 排序聚合） | 判定"是不是同一份内容" | ✅ **是** |
| ② | `compare_normalized_line_endings` | 仅在字节 hash 已不等时，判断差异是否只来自行尾 | ❌ 仅提示 |

> **修正说明**：早先写法是"行尾归一化**后**进哈希"。改为两级之后，**已存 hash 不作废、无需迁移**，同时避免"不可读文件 / 非法 UTF-8"的字节严格性被稀释（`07` D6）。
>
> **枚举函数只有一份**：`list_content_files()` 供 `scan` / `hash` / `diff` / removals 守卫共用 —— 上游为此修了 5 个版本（徽标说变了、Diff 说没变）。排除集分三类：影响 hash / 只影响兜底比较（`node_modules` / `.venv`）/ 纯噪音（`__pycache__` / `*.pyc` / `.DS_Store`）。

> **`adapter_new = true` 时不判 `CONFLICT`（`FR-1.0.19`）**：磁盘上的 `local` 是「旧 adapter 渲染 + 用户改动」的混合体，与「新 adapter 渲染」的 base 之间的差异混了两种来源，无法分离。此时先应用新模板，再单独处理用户改动。
>
> `adapter_outdated` 与 `has_untracked_assets` 都是**独立维度**（不进状态枚举），只体现为徽标。

### 冲突处理实现

**第一版不做块内合并**：冲突走**整文件粒度四选一**（保留本地 / 保留仓库 / 两个都保留 / 暂不处理），不做 diff3 标记解析与前端逐块交互。详见 `00-需求定稿.md` 的 FR-2.2.6 与 OUT-11，流程见 `04-系统设计.md` §5.3。

因此 `core/version.py` **不提供 `merge_file()`** —— 只暴露 `init / commit / log / show / snapshot_at / diff / rollback` 这些**具名方法**，不提供任何 `run(cmd, args)` 通用透传（OUT-14）。daemon 的任务表同理。

## 5. Daemon ↔ Cloud 协议

出站 WebSocket，任务式 RPC。

```json
{"type":"hello","agent_id":"...","version":"0.1.0",
 "runtimes":["claude","agents","workbuddy","codex"]}

{"type":"task","task_id":"t_123","request_id":"r_9f3a","op":"scan","params":{}}

{"type":"result","task_id":"t_123","request_id":"r_9f3a","ok":true,"data":{...}}

{"type":"event","request_id":"r_9f3a","event":"drift_changed","payload":{...}}
```

| op | 参数 | 返回 |
|---|---|---|
| `scan` | `{roots: [...]}` | skill 列表 + 来源 + hash |
| `status` | `{}` | 四端漂移矩阵（7 态 + 两个徽标位） |
| `push` | `{skill_ids, runtime_keys, on_conflict, dry_run}` | 逐项结果 + 跳过的未纳管资产 + **`held_back_removals`** |
| `pull` | `{skill_id, runtime_key}` | 新版本草稿 |
| `file_read` / `file_write` | `{skill_id, path, base_hash}` | 文件内容 |
| `version_log` | `{skill_id, limit?}` | commit 列表 |
| `diff` | `{skill_id, base?, head?, path?}` | unified diff |
| `rollback` | `{skill_id, ref, paths?}` | 新 commit |

> **原来的 `git {skill_id, cmd, args}` 已删除（OUT-14）**：通用 git 透传 = 云端可触发本地任意 git 命令，等价于一个命令执行入口。改为 `version_log` / `diff` / `rollback` 三个具名领域操作 —— **任务表即白名单**。
>
> **`rollback` 前必须自动快照当前状态**（含未保存改动），快照用户可见、可再回滚（`FR-1.0.10` / 上游 `1.26.0`）。

**`request_id` 守卫（v1.3 新增，`07` N12）**

`task_id` 与 `request_id` **并存但语义不同**：

| 字段 | 语义 | 用途 |
|---|---|---|
| `task_id` | 标识任务本身 | 去重、断线后补发未 ack 的结果 |
| `request_id` | 标识**这一次请求的上下文** | 上下文已切换（用户换了 Skill / 项目 / 设备）时，**结果丢弃** |

> 上游 `1.28.5`：一次慢扫描的响应在用户已切到另一个项目后才返回，**把上一个项目的技能塞进了当前页面**。前端侧同理 —— 切换上下文时**必须显式取消订阅**，不能只靠"结果回来对不上就忽略"。

**锁与网络分离（v1.3 新增，`07` D5）**

daemon 的"每轮 scan + drift + 可选 upstream"循环里**只有 upstream 涉及网络**：网络往返一律在锁外（按 `(clone_url, branch)` 去重、最多 8 并发预取），锁只用来"读 / 写 repo 与 bindings"。**禁止持锁 `fsync` / 全量 rename / 更新目录 mtime**（macOS 上 `fsync` 会刷新整卷缓存）。上游实测：改两段式后**锁从 30 秒降到毫秒级**。

特性：心跳保活、断线指数退避重连、任务超时、连接唯一性（同 agent_id 踢旧连接）。

## 8. MCP Server 工具集

```text
skillos_list_skills      列出 skill（支持分类 / 标签过滤）

skillos_version_log      查询版本历史
skillos_upgrade          从上游升级
```

设计原则

1. **只读工具先做，写入工具必须带 `dry_run` 参数** —— 避免 agent 误操作本地目录。
2. **不暴露 `force`**（`FR-1.3.5`）：冲突只能 `abort` / `skip`，危险决策留给人工路径。
3. **不暴露通用 git / shell**（OUT-14）：只有领域操作，没有 `git(cmd, args)`。
4. **无设备管理工具**：token 撤销只在 Web 人工路径（`DELETE /api/devices/{id}`）。

> 划清边界：**Agent 能执行能力，不能执行危险决策。**

**T1 的实现约束**（决策即约束，必须写进代码规范）：

- 所有 `core/fs` 的文件操作**必须显式接收 `root: Path` 参数**，不得从全局配置 / 单例 / 环境变量隐式读取。
- 运行时根路径由调用方决定：CLI / daemon 传真实用户目录，沙盒进程传容器内虚拟目录。
- 分层硬约束不变：`core` 不得 import `services` / `store`（见 `04-系统设计.md` 1.3）。
- 代价：路径校验（`resolved_path` 必须落在 `root` 内）要在这层统一实现，不能散落各处。
- 沙盒下 **`scan` / `push` / `pull` / 编辑 / 回滚全部可用** —— 隔离靠文件系统边界（root 全在容器内），**不靠 UI 禁用写操作**。

**T2 的实现约束**：

- 阈值常量集中在 `core/constants.py`，便于后续调整。
- 超阈值文件在 `skill_files` 表标记 `in_git = false`。
- 超阈值文件**不参与漂移哈希**（否则会把"本地独有的大文件"误判为漂移）。
- **但必须补一条**：`has_untracked_assets = true` 的 Skill，其漂移状态**禁止显示 `SYNCED`**，改显示 `SYNCED*` + 徽标。否则「用户改了 8MB 资产、UI 说同步正常」就是假同步（`NFR-3.4`）。
- **分发时须回收未纳管资产**：`push` 是整体替换目录，若不回收就会静默删掉用户的资产（见 `04` §2.2.2 第 5 步）。
- MVP **不做** Git LFS / 对象存储（OUT-13）。

**T3 的实现约束**：

- 生成命令固定在 `web/package.json`：
  ```json
  "gen:api": "openapi-typescript http://localhost:9080/openapi.json -o src/api/schema.d.ts"
  ```
  前提是后端在跑（或预先导出 `openapi.json` 到本地再生成）。
- 产物路径 `web/src/api/schema.d.ts`，**提交进 git** —— 否则新环境 / 沙盒镜像必须先跑起后端才能编译前端。
- **禁止手改生成物**：文件头保留工具注释；手写部分只放 `web/src/api/client.ts`（fetch 薄封装）与业务 hook，类型从 `schema.d.ts` 取。
- 后端改接口后的动作固定为：跑 `npm run gen:api` → 看 TS 报错 → 修调用点。

**T6 / T7 / T8 的实现约束**：

- `render_layout()` 必须有**纯函数单测**：同一 `SkillSnapshot` + 同一 `adapter.version` 调用两次，输出逐字节相同。这是 base 可重建的前提，不纯则漂移与合并同时失效。
- 修改 adapter 的字段策略 / sidecar 模板 / 目录布局 ⇒ **必须 bump `adapter.version`**，否则历史 base 会静默算错。
- adapter 变更后，受影响 binding 只走「应用新模板」，**不进入 `CONFLICT` 判定**（`FR-1.0.19`）。
- `runtime_bindings.status` 是**判定结果缓存**，任何时候都必须能由「磁盘 + canonical commit + adapter 版本」重算。
