### P1（10/2 – 10/5）
- **`core/fs/safe_path.py`：统一路径校验 + `path_key()` —— 第一个写，后面所有模块都依赖它**（FR-1.0.14 / FR-1.0.31）
  - `path_key()`：按分隔符**分段** + `Unicode NFC` 归一化 + `casefold`，**所有路径去重 / 冲突检测都走它**；`path_key` **只用于比较**，不替换真实路径
  - 理由：macOS 写盘即 NFD 化、Windows 大小写不敏感 —— **只比大小写会漏掉中文名场景**（本机 62 个 Skill 全中文名）
- **全局写锁下沉到 `services` 层**（FR-1.0.17，三入口共享，先立规矩再加功能）
- **★ 基线模型先行（FR-1.0.18 / FR-1.0.8 / NFR-3.5）—— 必须排在 `drift.py` 之前**
  - `runtime_bindings` 落 `installed_commit` + `adapter_version` + `baseline_source`
  - `adapter.render_layout()` 定成**纯函数**并补纯函数单测（同输入两次调用逐字节相同）
  - `GitRepo.snapshot_at(commit)`：base 重建的唯一入口
  - 理由：base 若不可精确重建，drift 与三方合并都会算错 —— **模型不定就写 drift，一定返工**
- **★ `core/adapters/*`：路径即数据（FR-1.0.25）—— 与字段策略同期落地**
  - `RuntimePaths`：`deploy_dir` + `scan_only_dirs` + `fallback_dirs` + `verified_at` + `evidence`
  - **部署根 ≠ 发现根**：`scan_roots()` 返回发现集合，`resolve_root()` 返回部署根
  - `key` 带命名空间（`builtin:` / `custom:`），解析顺序统一在一处
  - 理由：上游在同一份 CHANGELOG 里对 Codex 路径给出过**两次相反结论** —— 靠结构容忍，不靠查清
- `core/parse.py`：SKILL.md frontmatter + 文件树 + sidecar 解析
- `core/adapters/*`：四个 runtime 的字段策略与 layout 渲染（**每个 adapter 带 `version`**）
- **★ `core/hash.py`：哈希两级结构（FR-1.0.5）**
  - `hash_bytes`（字节级，**不做归一化**）+ `compare_normalized_line_endings`（**只在字节 hash 已不等时调用**）
  - `list_content_files()` 是**唯一**的文件枚举入口，供 `scan` / `hash` / `diff` / removals 守卫共用
  - 排除集分三类：影响 hash / 只影响兜底比较（`node_modules` / `.venv`）/ 纯噪音（`__pycache__` / `*.pyc` / `.DS_Store`）
  - 理由：本机已有 54 个 `.pyc`，不排除必踩；且"徽标说变了、Diff 说没变"是最伤信任的一类 bug
- `core/scan.py`：目录扫描、包边界识别（含 `subskills/` 嵌套）+ **超阈值文件标记 `in_git=false`**（FR-1.0.20）
- **`core/import.py`：纳管 + 同名多副本合并 + `baseline_source=imported`**（FR-1.0.16 —— 本机 62 个 skill 有这个常态，不是边角）
- **★ `core/identity.py`：稳定身份与分层匹配（FR-1.0.21）—— 必须与 `import.py` 同期落地。** 匹配分层：`source_ref` → 唯一内容哈希 → `dir/name`；**任一层多候选即不认**。排在 import 之前：匹配错了，合并就会把两个不同 Skill 绑成一条，且「导回仓库」会写入错误的记录
- **`core/provenance.py`：溯源记录（FR-1.0.22）** —— 纳管 / 分发 / 编辑 / 回滚写 `author + commit + at`。**数据源直接用 git，不另建表**（这是它成本低的原因）
- `core/version.py`：git 封装（init / commit / log / show / snapshot_at / diff / rollback，**无通用透传**）
  - `init` **显式 `-b main --ref-format=files`**（不吃用户全局配置，防 reftable 格式导致库"看起来坏了"）
  - 首次 push 走 `push -u`；`resolve_ref()` 按 分支 → peeled tag → tag 对象的优先级
  - `rollback` **前自动快照当前状态**（含未保存改动），快照用户可见、可再回滚
  - 锁文件**不放**在会被克隆 / 整体替换的目录内
- **★ `core/distribute.py`：原子写 + 备份 + 回滚 + 残留自检（FR-1.0.15）+ 未纳管资产回收 + 三道安全机制**
  - **`ReplacePolicy` 三态**（FR-1.0.26）：`NO_CLOBBER` / `RECORDED` / `USER_CONFIRMED`，**无默认值**，每个调用点显式声明
  - **removals 守卫**（FR-1.0.26）：按路径比较、目录只报一行、**形态变化计为移除**、无法判断时报错不猜；无人值守路径一律跳过并记 `held_back_removals`
  - **部署自证**（FR-1.0.27）：写后回读目标，清单 + 哈希一致才上报成功
  - 暂存目录（`.staged-<uuid>`）由 `try/finally` 负责清理，**每次提交前也清一遍**
  - 理由：这是"一键分发"这个门面功能**唯一能一次删掉用户数据的地方**，也是上游多起真实数据丢失事故的来源
- `core/drift.py`：**七态判定**（先做 SYNCED / MISSING / OUTDATED / MODIFIED / UNMANAGED / ORPHANED，CONFLICT 留到 P3）
  - **跨目标前置全检**（FR-1.0.28）：任一 binding 非 `SYNCED` → 整体拒绝。**必须在任何写入之前跑完**，不能放进 per-target 循环
  - 判据分层：`SYNCED` 是唯一可作"可安全覆盖"证明的状态；**明文禁止读 `updated_at` 判新鲜度**
  - 扫描根**按 canonical path 合并**（`07` N9 —— 上游已知未修复，我们的低成本超越点）
- `core/checks.py`：门禁规则骨架 + **三级分级**（FR-1.0.11），新增 `asset.untracked`（warn）规则。**判定函数一次写好、供 `check` 与 `push` 共用**（NFR-10.5 —— 两套判定必然漂移）
- **`core/meta.py`：协作元数据随仓库版本化（FR-1.0.30）** —— 标签 / Profile 归属 / 启用状态写入 `<repo>/.skillos/`，**SQLite 仅缓存、可重建**
  - **重建守卫**：元数据说 0 个 Skill 而仓库里有 Skill 目录 → **拒绝重建**并抛 `META_INDEX_MISMATCH`（否则一次失误清空整库）；**首次克隆**走全量扫描，不走 `rebuild_index()`
  - 两个 `.skillos` 别混：`<repo>/.skillos/`（**进 git**、会同步）vs `~/.skillos/`（本机状态：锁 / 备份 / 日志 / SQLite，**不进 git**）
  - `scan` 必须排除 `<repo>/.skillos/`，否则元数据目录会被当成 Skill
- **`core/protocol.py`：仓库协议版本协商（FR-1.0.29）** —— commit trailer `Skillos-Protocol: N` + sticky `protocol.json`（**只升不降**）
  - **"有 `protocol.json` 但 commit 无 trailer" = 旧客户端写入** → 拒绝混用；本机支持版本低于仓库版本 → **只读模式**
  - 单机 demo 不触发，但**数据结构必须现在定** —— 否则 V2 加第二个客户端时要迁移历史
- `cli/main.py`：`skillos scan | status | push | import | log | versions | diff | rollback | doctor`
- **产出**：终端里打印四端状态矩阵；`doctor` 全绿

- **锁实战三条（`06` A6 / FR-2.4.9）**：① 抢锁**不按异常类型分支**（Windows `ERROR_LOCK_VIOLATION` 不映射 `WouldBlock`，写成 `except WouldBlock` 会在 Windows 上直接抛，且只在并发时复现）；② **前后台锁分级**（后台可长持锁，**前台等待 20s** 超时才报 `BUSY`）；③ **锁诊断 stamp**（`pid` / `hostname` / `operation` / `start_time`）—— `repository is busy` 必须能追责到具体操作
- **批量分发「单 Skill 冲突不阻塞其余」（FR-2.1.4）**：批量 20 个、1 个冲突时其余 19 个照常分发，冲突项进「需要处理」列表。**注意与 FR-1.0.28 分属两个层级**（后者是"同一 Skill → 多 Runtime"必须整体拒绝）

### 不可退让的六项

1. **P1 引擎**——没有它产品不成立
2. **P2 云端 + daemon + 看板**——demo 本体（含「双读者」总览）
3. **P3 编辑器 + diff**——"完成度"维度的主要背书
4. **P5 MCP**——"技术创新"与 demo 高潮
5. **质量门禁的 `error` 级拦截**（FR-1.0.11）—— 「资产」定位的技术支点，且成本极低（复用 P1 的 checks 骨架），是 demo 高潮一里最有力的一击
6. **一键分发的删除守卫**（FR-1.0.26 + FR-1.0.27）—— **v1.3 新增**。理由见 `00` §8：**"一键分发"是这个产品的门面，也是唯一能一次删掉用户数据的地方**。它与第 5 项共用同一批前置判定代码，增量成本几乎为零

> **第 8 / 9 / 11 项都不是"砍功能"而是"降级"**：门禁、守卫、身份、哈希口径全部保留，只是评分退化为计数、回退链退化为单路径、双判退化为路径判。
>
> 这是刻意留的退路，**三条线不可越**：
>
> | 不可越的线 | 为什么 |
> |---|---|
> | **门禁不可砍，评分可退化** | 门禁是「资产」定位的当场证明 |
> | **守卫不可砍，双判可退化** | 守卫是数据安全的底线；双判只是比上游做得好一点 |
> | **哈希两级不可退，排除集可简化** | 两级是正确性（跨平台），排除集是性能 |
> | **重建守卫不可砍，元数据范围可窄** | 守卫防的是"一次失误清空整库"，属数据安全 |

**注意**：占比最高的是**引擎**，其次才是前端。若进度落后，**优先压缩前端页面数量，不要压缩引擎质量** —— 引擎是产品本体，页面是包装。

> 前端占比从"8 个页面"收敛到"3 页面 + 标签页"后，虽然新增了乐观锁与离线态，总占比仍从 30% 降到 26% —— 冲突解决简化为整文件粒度省下的量最大。
>
> 本轮新增的**基线模型修正**（`installed_commit` / `adapter_version` / 纯函数单测）计入引擎，占比 32% → 34%。这笔投入**不能省**：base 不可重建的话，drift 与三方合并都算错，返工量比省下的时间大得多。
>
> **本轮（v1.2 战略定位）的预算操作**：质量从 4% 提到 8%（门禁 + 折旧 + 健康度），引擎 +1%（identity + provenance）。这 5 个点全部从 Web（−2）、云端（−1）、MCP/CLI（−1）、部署（−1）挤出来。
>
> 能做到的原因是**不新增页面**：溯源进 `Versions` tab、门禁与健康度进 `Checks` tab，新增成本几乎全在"算"上（纯 Python 函数，且 checks 骨架 P1 已有）。
>
> **时间不够时的二选一**：保门禁，砍折旧。门禁是叙事支点且成本最低；折旧可退到只留 `staleness` 一个维度。
>
> **本轮（v1.3 吸收 `07` 踩坑日记）的预算操作**：引擎 35% → **38%**（+3），来源是 Web（−1）、MCP/CLI（−1）、部署（−1）。云端占比不变，因为它拿到的是"换实现方式"（锁与网络分离、自写静音窗）而非新增功能。
>
> 引擎这 3 个点的去向都可以一句话说明：**路径即数据**（改结构不改逻辑）、**哈希两级**（拆函数）、**删除守卫 + 部署自证 + 跨目标全检**（三者共用同一批前置判定代码）。
>
> **为什么这 3 个点不能省**：它是上游两年、500+ issue 里**最贵的一类事故**（数据丢失与静默失效），而我们此刻**只花 12 天**就能把它们都躲开。相对地，砍掉的 3 个点（Web 一个组件级优化、CLI 一个子命令的打磨、部署脚本的自动化）都是**可以靠手工补的**。
>
> **本轮（v1.4 采纳 `06` A/B 清单）的预算操作**：引擎 38% → **39%**（+1），来源是 Web（−1）。三个新增模块成本都很低：`path_key()` 是纯函数、`meta.py` 是读写 JSON、`protocol.py` 只在入口校验一次。
>
> **云端占比不变 —— 这是一个明确决策**：`06` §5.3 曾建议"删掉云端数据面职责，多设备同步交给 git remote"。**我们选择保留云端的写路径职责**（`sync_records` 双写与 daemon 写任务；术语消歧见 `04` §1.2），理由有三：
>
> | # | 理由 |
> |---|---|
> | 1 | **Demo 形态要求**：评委要能"打开浏览器就看见" —— 这是相对桌面应用（skills-manager）的**唯一形态差异**，也是"线上可访问"这条硬约束的落点 |
> | 2 | **本地 daemon 已经设计好了**：云端数据面与本地 daemon 共用同一套任务表与锁，删掉它是**推倒重来**，不是省时间 |
> | 3 | **真正该收敛的是"云端不做冲突判定"**：冲突仍在本地由三方比对解决，云端只转发结果 —— 这一条**与本轮无冲突，已经落在设计里** |
>
> 换言之：**保留云端 ≠ 云端变重**。写路径职责保留（术语「数据面」的两个用法见 `04` §1.2 —— 此处指**云端保留写路径职责**：任务下发 + `sync_records` 双写，**不存文件内容、不判冲突**），但"真值"始终在本地 git + 磁盘（`NFR-1` 离线可用即此）。`06` §5.3 的取舍**不采纳**，`06` §6.3 的叙事调整**采纳** —— 两者是独立的决策。

6. `skillos doctor` 全绿
7. 录屏一份作为终极备份

> **收尾是杀手锏，且现在是两句**：先强调"这不是编的 demo，是我每天在用的 62 个真实 skill" —— 数据真实、可复现、不用造场景，这是绝大多数参赛项目给不出的东西。紧跟一句切到公司侧：**"要是团队 20 个人呢？人走了，skill 还在 —— 这是账本，不是网盘。"** 两句之间不要停顿解释，让最后一句停在观众脑子里。

## 7. Demo 剧本（双高潮）

> 本节为**剧本权威版**（`00-需求定稿.md` 第 7 节引用此处）。原 `01-需求讨论稿.md` 第 9 节的版本已作废——那版把高潮二挂在「升到上游最新」上，而**上游跟踪是可砍项**，等于让高潮依赖一个可能不存在的功能。

```text
0:00  问题陈述（**治理视角**，不是"同步工具"视角）
      一台机器 62 个 skill 散在 4 个目录：同名副本、不知谁新谁旧、改了哪边不知道
      → 投屏：~/.claude 与 ~/.agents 下两个字节完全一致的 brainstorming
      → 一句话：「四个 Agent 各装了什么、谁改的、过没过检查 —— 现在一个都答不上来」
      → 定位句：「我要的是一个治理控制台，不是又一个同步工具」

0:30  skillos scan → 控制台刷出 62 个 skill / 四端状态 / 漂移告警        （视觉冲击）
      → 顺手滑到总览下半部：「这半页是给不写 skill 的人看的 ——
         覆盖度、僵尸 skill 占比、N 个有 error」                      （新增·双读者）

1:00  改一处 SKILL.md → 故意删掉 description → push 被门禁拦下
      → 补回 → 一键分发 → 四个终端同时生效                            【高潮一】
      ⚠️ 高潮一现在是两步：先说不行，再说行

1:45  版本时间轴：这条是谁改的、什么时候 → 回滚到上一版                （安全感 + 溯源）

2:15  制造冲突：repo 里改一处 + 磁盘上手改一处 → 矩阵亮 CONFLICT
      → 整文件粒度四选一解决（含「两个都保留」）
      ⚠️ 只用「repo 改 + 磁盘改」，不碰上游跟踪

2:30  切到 Claude Code：「把 code-review 同步到 Codex」
      → agent 调 skillos_status → 发现 outdated → dry_run 预览 → 用户确认 → push   【高潮二】

2:50  收尾：真实数据 + 一句话切公司侧
      「这不是编的 demo，是我每天在用的 62 个真实 skill」
      「要是团队 20 个人呢？人走了，skill 还在 —— 这是账本，不是网盘」
```

**五处刻意的设计**

| # | 设计 | 理由 |
|---|---|---|
| 1 | 高潮二用**本地 skill 分发**，不用上游升级 | 上游跟踪排在砍单第 7 位，押它是自找风险 |
| 2 | 冲突用 **repo 改 + 磁盘改** 制造 | 三方基线（base/local/remote）里 local 与 remote 都动即可，不需要任何外部依赖 |
| 3 | 全线**本机真实数据** | NFR-6 硬要求。真实可复现是相对其他参赛项目的最大优势 |
| 4 | 高潮一改为**两步**：先被拦、再通过 | 门禁是「资产」定位**唯一的当场证明**。当场拦一次，比讲十句"我们做治理"有用 |
| 5 | 公司侧**只用一句话**，放在最后一句 | Q1=C 要求两个支点都讲，但主线只讲「团队复用」（有实物、本就在看板里），「人走资产留」靠 1:45 的时间轴背书 + 收尾一句话。**不新增任何 P2 工作量** |
| 6 | **删除守卫不单独占时间**，并入 1:45 或 2:15 的自然停顿 | `FR-1.0.26` 是**保险丝而不是表演项目** —— 正常演示路径上它不该触发。只有时间富余时，才在 2:15 之后加一句"如果这次会删掉你目标目录里的东西，它会先停下并把这些路径列给你看"。**不要为了演它去制造删除场景**（那会挤掉高潮二） |
| 7 | 叙事重心放在**治理与验证**，不是"跨 Agent 分发" | 后者已被成熟产品占位（skills-manager，5532★、54 个 Agent）。而"分发 → 漂移 → **门禁**"这条链的终点（**过没过检查**）正是它唯一的空白，也是高潮一（push 被拦下）的落点 —— `06` §6.3 |

## 8. 工程治理纪律（v1.3 新增，源自 `07` §8）

上游在 19 个月的 500+ issue 修复史里沉淀了四条流程纪律，**成本极低但对"完成度"维度有直接背书**。

### 8.1 破坏性改动前跑一轮只读对抗评审（`07` N26）

上游的原话密度很高：*"共做了三轮跨厂商复核，实质缺陷在第二轮之后不再出现"*、*"发版前复核发现两处缺陷"*、*"该缺陷在发布前经跨厂商复核发现；去掉这道守卫，回归测试即变红"*。使用的评审方是**跨厂商**（codex / grok），含"只读沙箱对抗性评审"与"设计阶段四轮评审"。

**→ 我们怎么做**：用户手上已有 4 个 runtime 与多个评审 agent。约定：

| 触发 | 动作 |
|---|---|
| 任何**破坏性改动**前（分发协议、漂移判定、哈希口径、删除路径） | 跑一轮**只读**对抗评审（不给写权限） |
| 评审意见的**拒绝** | **必须记录理由** —— 上游把这当成习惯；我们这两轮评审已在实践 |

### 8.2 变异验证：删掉守卫，测试必须变红（`07` N27）

上游原话：*"配套测试已通过**变异验证** —— 删掉 DELETE 语句时该测试必然变红"*；*"两条既有测试原本是**靠这个 bug 才通过的**，各自伪造一个够老的 `updated_at` 来冒充『年龄』"*。

**→ 硬要求**：`FR-1.0.5` / `FR-1.0.26` / `FR-1.0.27` / `FR-1.0.28` / `FR-1.0.21` 这五条**每一条都要有反向验证** —— 把实现改回旧行为，对应测试必须失败。

> 第二类问题更隐蔽：**测试因为假造条件而通过**。我们做漂移 / 共享库测试时最容易犯 —— 例如手工伪造一个 `installed_hash` 来"制造漂移"，而不是在磁盘上真的造出那个状态。**必须断言真实状态，不伪造中间量。**

### 8.3 CI 覆盖缺口 = 返工（`07` N28）

上游原话：*"本次均为前端改动，而**仓库没有前端测试框架，`test.yml` 也不覆盖 `src/`**，因此验证手段是 lint、build 与复核"*；*"此前**Linux 只在发版 workflow 中编译**"*。

**→ 我们**（与 `05` P0-10 同一条）：

| 时点 | 动作 |
|---|---|
| P0 | `pytest` 上 `windows-latest` + `ubuntu-latest` |
| **P3** | 前端 `vitest` 进同一矩阵（编辑器 / diff / 冲突解决全在前端，不能等发版才编译） |
| 发版前 | macOS 列手动跑一次 |

### 8.4 交付物体例：三段式 + 诚实标注（`07` N30）

上游 `1.22.2` 把更新日志结构改成**按受众分三段**，且**每条带 issue 编号**、**诚实标注未修复项**：

1. **发布概览** —— 一句话，用户能感知的
2. **用户可见更新** —— 每条写"以前怎样 → 现在怎样 → 为什么"
3. **开发者与治理更新** —— 实现细节、为什么这么选、已知限制

**→ 直接用到黑客松材料上**：

- 项目说明书的"已完成 / 未完成"两节借用这个结构；
- **「诚实标注限制」对我们的评审价值极高** —— 例如主动写出「本期不做块内合并（OUT-11）」「窄克隆不做（OUT-16）」「对象级合并引擎不做（OUT-17）」。**主动说出边界比假装完美更可信**；
- §7 的 Demo 剧本天然符合这个顺序：能力总览（能感知）→ 漂移告警（以前怎样→现在怎样）→ 门禁与守卫（为什么难）。

### 8.5 产品设计专坑清单（`07` N29，已挑高价值项进 `00`）

| 已进需求 | 内容 |
|---|---|
| `FR-2.4.7` | 列出被删文件的弹窗**必须限高 + 可滚动**（上游 `#430`：超出窗口上下边缘，既没滚动条、按钮又在屏幕外，**完全无法操作**） |
| `FR-2.4.8` | **失效筛选自动清除**（上游 `1.28.5`：删掉某标签下最后一个技能后，pill 消失但筛选仍生效 → 列表静默变空，**界面上已经没有可关掉的筛选了**） |
| `FR-2.1.9` | 计数按**技能**而非按**副本**（上游 `1.40.0`：一个 skill 同步到三个 agent 就被数成三个） |
| `FR-1.0.25` | runtime 列表**只读后端返回的 `installed` 事实**，不做人工 curation（上游 `1.30.0`：手工维护的"主流 Agent 名单"几天就过时） |

**其余三条留给实现时注意**（不新增需求编号）：

| 项 | 上游事故 |
|---|---|
| 批量按钮必须显示**真正会被改变的数量** | 选中 30 个（其中 23 个本来就启用），按钮写"启用 30 个"却提示"已启用 7 个" |
| 选择集必须**裁剪到当前可见部分** | 选中 10 个 → 换标签 → 点删除，会把**已被筛掉、屏幕上看不到的 9 个一起删掉** |
| 移除功能时**必须清理其持久化设置** | 早期"保存默认 agent"按钮被删但设置留下 → 项目永远只部署到那个冻结子集，**界面上既看不到也无法修改** |

### 8.6 回归测试必须写明「为什么会有这个测试」（`06` B8）

上游的测试注释长这样：

```rust
/// Regression test for issue #99: the lock file must not live inside skills_dir
```

**→ 我们采纳为工程约定**：所有**跨平台回归测试**与**守卫类测试**，注释里必须写清三件事：

1. **对应的坑**（`07` / `06` 的编号，或上游 issue 号）；
2. **现象**（当年是什么表现）；
3. **不修会怎样**（一句话后果）。

理由很实际：这类测试**看代码完全看不出为什么要存在**（"为什么锁文件不能放在 `skills_dir` 里？"），下一个人会把它当成冗余断言删掉 —— 删掉之后，线上会在**另一个平台**上以**另一种方式**重新失效，且同样难查。

> 与 §8.2 的变异验证配对：**变异验证保证测试有效，注释保证测试不被误删。**
