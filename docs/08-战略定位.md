## 1. 定位改写

**旧定位**

> Skill OS —— Agent 能力的**包管理器**与分发层。写一次，多个 Runtime 都能用。

**新定位**

> Skill OS —— Agent 能力的**账本**与分发层。
> 写一次，多个 Runtime 都能用；**改一次，谁改的、什么时候、还能不能用，都答得上来。**

技术定义相应补两项：

> Skill 的 canonical 仓库 + 跨 Runtime 适配层 + 漂移感知 + 版本可追溯 + 可被 Agent 自管 + **稳定身份与溯源** + **健康度与折旧度量**

**这不是换个说法，是换了要解决的问题。** "包管理器"解决的是**装得上**；"账本"解决的是**这是谁的资产、它现在值多少**。前者是工具，后者是治理——而只有后者能同时卖给个人和公司。

### 第三次调整（v1.4，源自 `06` §6.3）：从"账本"到"治理控制台"

"账本"是对的，但**还不够锋利** —— 因为"账本"描述的是**我们做了什么**（记录），而评审问的是**它解决什么**（治理）。

| 版本 | 表述 | 问题 |
|---|---|---|
| v1.1 | 包管理器与分发层 | "跨 Agent 分发" —— **已被占位**（skills-manager，5532★、54 个 Agent、两年迭代） |
| v1.2 | 账本与分发层 | 准确，但偏"能力描述"，不直接回答"凭什么需要你" |
| **v1.4** | **Agent 能力治理的控制台** | **形态句**说清"看得见"（浏览器里），**能力句**说清"这条链"（分发 → 漂移 → **门禁**） |

**最终两句**（`00` §0 采用）：

> **Agent 能力治理的控制台。** 浏览器里看清所有 Agent 各自装了什么、谁改的、**过没过检查**。
>
> **Skill 不只是分发 —— 还要能被验证。** 分发 + 漂移检测 + 质量检查 + **门禁回归**。

> ⚠️ **一处口径必须守住**："评测回归"本期 = **门禁回归**（静态、结果落库、可对比历史，`FR-1.0.11` / `NFR-10.1`）；**运行时评测 / 跑分不做**（`OUT-2`，V2）。详见 `06` §6.3 的口径说明。
>
> **为什么这次调整是必要的**：`06` 证实"跨 Agent 分发"这个位置已有成熟产品，而**质量与治理是它唯一的空白**（`06` §6.2 的 D3）。把叙事移到空白处，不是换包装，是**把技术投入对准了差异点** —— 门禁、折旧、健康度这三件事本来就已在 `00` 里，现在只是让它们从"加分项"变成"主线"。

## 2. 为什么"资产"这个命题现在才成立

因为 **Agent 把 Skill 从"配置"变成了"能力"**。

`.vimrc` 不是资产，没人管它丢不丢。但"让 Agent 会做需求评审"这件事承载的是**方法**：

- 个人的 Skill = **个人的方法论**（攒了 200 小时的那 62 个）
- 公司的 Skill = **组织的流程知识**（谁都知道该怎么做，但只有老员工做得出来）

两者都是真资产，也都会流失。这才是命题的来源——不是"管理文件的工具"换个包装。

## 3. 资产化的四层阶梯

| 层 | 内容 | 现状 |
|---|---|---|
| **第 4 层 · 用得住** | 健康度 · 依赖失效 · 该不该留 | **空白** |
| **第 3 层 · 说得清** | 身份 · 溯源 · 谁改的 · 人能带走吗 | **空白** |
| **第 2 层 · 数得清** | 跨端清单 · 漂移告警 · 版本账本 | 局部（单工具内可见，跨工具/跨机器即散） |
| **第 1 层 · 装得上** | 安装 · 分发 · 多端同步 | 已被做透（skills-manager 适配 54 个 Agent） |

**两条推论**：

1. **第 1~2 层是包管理器，第 3~4 层才是资产管理。** 我们不与 skills-manager 在第 1 层竞争——那里它已经赢了 5532 个 star，且我们追不上。
2. **资产必须能"折旧"，否则不叫资产叫库存。** 折旧计量 = 质量与健康度评估 → **`07` 里判定"质量是对方唯一的功能空白"，在此升格为"资产这个词的必要条件"**。没有它，我们做的仍然是包管理器。

## 4. 个人与公司：同一根轴的两端

| 维度 | 个人 | 公司 | 是否同一件事 |
|---|---|---|---|
| 资产是什么 | 我的方法论 | 组织的流程知识 | ✅ 粒度不同 |
| 流失场景 | 换电脑 / 换 Agent / 换工作 | **人走了** | ✅ |
| 确权诉求 | 这是我改的 | 这是公司的，离职要留下 | ✅ |
| 计量诉求 | 我有多少、哪些过期 | 哪些在用、哪些是僵尸、覆盖哪些业务 | ✅ |
| 质量诉求 | 还能用吗 | 还能用吗 + 合规吗 + 有没有泄露密钥 | ✅ 公司多一层 |
| 流转诉求 | 跨设备、跨 Agent | 跨团队、新人入职 | ✅ |
| **付费意愿** | 低 | **高**（走 IT 治理 / 知识管理预算，非开发者工具预算） | ❌ 只差这里 |
| **决策者** | 就是使用者 | **采购的人不写 Skill** | ❌ 只差这里 |

最后两行是全部差别，由此推出两条硬性产品要求：

**R1 · 个人侧是产品，公司侧是生意。** 个人侧负责增长、口碑与真实数据；公司侧是付费主体。两者**不共用一个叙事**：对个人说"你的 Skill 库"，对公司说"团队的 AI 能力账本"。

**R2 · "决策者 ≠ 使用者"决定必须有一个管理者视图。** 它不是给写 Skill 的人看的，是给**不写 Skill 但要对结果负责的人**看的（覆盖度、僵尸 Skill、健康度分布、成员贡献）。
> **关键实现约束**：管理者视图与个人的能力总览**必须是同一个页面的两种读法**，不做两套。否则等于凭空多做一个 D2。—— 落在 `FR-2.1.1`。

## 6. 公司侧的两个支点（Q1=C 的讲法）

### 支点一 · 人走资产留（主叙事，放收尾）

**要回答的问题**：一个工程师离职，他攒的 40 个 Skill 是留在磁盘上烂掉，还是变成公司资产？

**技术基础**：`FR-1.0.22` 溯源（谁在什么时候改了什么）+ `FR-3.16` 不可变审计。
**为什么只有我们答得上来**：git 的 commit 天然不可变且带署名，**应用层不提供删除 / 改写历史的接口**。而"桌面单机 + SQLite"形态的工具做不到——它的记录可以被任何人清空重来。
**这同时是"为什么需要云端"的硬理由**：跨机器的不可变账本，本地单机给不了。而它**不需要云端变成数据面**——账本仍在 git 里，云端只提供视图。

### 支点二 · 团队能力复用（Demo 主线）

**要回答的问题**：20 人的团队，各自的 Skill 互不可见，新人上手要从零踩坑。

**技术基础**：`FR-2.1.1` 管理者视图（覆盖度 / 僵尸 Skill / 健康度分布）+ `FR-2.3.2` 共享库。
**可量化锚点**（比"效率提升"好算）：**新人上手时间**、**重复 Skill 数量**、**僵尸 Skill 占比**。

> **顺序不可颠倒**：先讲复用（有实物、主线里就有），后讲传承（一句话 + 一张图）。反过来会变成"卖治理概念、拿不出东西"。

## 8. 硬边界（本轮明确不做）

"公司"这个词会立刻带出：SSO、RBAC、审计日志产品化、私有部署、多租户、合规扫描。

**这 12 天一个都不做。** 它们不是"锦上添花"，是会吃掉全部时间并稀释技术亮点。评审看的是"你想清楚了"，不是"你做了企业版"。

保留下来的只有三件"不做以后补不上"的：

1. **身份**（`FR-1.0.21`）——Skill 的稳定 ID，跨 runtime / 跨机器 / 跨改名
2. **不可变溯源**（`FR-1.0.22` / `FR-3.16`）——谁改的、删不掉
3. **策略可插拔**（留接口，不实现）——谁能推、要不要审批
