### 2️⃣ · 契机：那个改错文件的下午

我电脑上同时装着三四个 AI Agent（Claude Code、Codex、WorkBuddy 这些）。我有个习惯：好用的提示词、工作流程，都会做成 Skill 存进各个 Agent 的目录。

攒着攒着出了事。有一天我在其中一个 Agent 里把一个 Skill 调好了，回头发现——**我改的是另一个目录下的旧副本，而 Agent 真正读的，是第三份。**

改了半天，改了个寂寞。

我当场把四个目录清点了一遍：**62 个技能目录，其实只有 50 个不同的技能——多出来的 12 份全是重复**。最多的一个名字，四个目录里各存了一份，而且没人说得清哪份是对的。

### 3️⃣ · 其实我一直想把这个事做了

这次翻车之前，我已经用"AI 帮我干活"的方式做过一串东西：【按你的真实情况填，比如：测试框架里的需求评审技能包、小程序项目、小红书的内容工作流……】。

做着做着就发现一个规律：**每个项目我都攒下几个 Skill，每个 Agent 目录里存一份，从来没人管过它们的版本、状态、还能不能用。**

项目会结束，但这些能力应该留下来。所以我决定这次不再忍了——做一个工具，专门管这件事。这就是 SkillOS 的起点。

---

### 4️⃣ · 第一步差点就走歪：需求不能写成"复制粘贴太累"

痛点是"太乱了"，但"太乱"没法当需求——你没法判断它什么时候算做完。

我逼自己把它写具体，最后落到两个性质完全不同的卡点：

- **分叉不可见**：改一处要同步三五个目录，漏一个就开始版本分叉，而且没有任何告警；
- **覆盖不可控**：目标目录里如果有不是我放的文件，一条复制命令直接盖掉，连句提示都没有。

这里有个细节我特别想说：我一开始差点把需求写成"**复制粘贴太累**"。真那么写，最后做出来的就是一个"批量复制工具"。**同一个痛点，你怎么描述它，决定了你会做出什么东西。**

---

### 5️⃣ · 调研泼了盆冷水，但把我泼醒了

写完需求我没动手，先去查了一圈——结果发现**这个位置已经有人了**：一个五千多 star 的开源项目，做了两年，把"写一次、多个 Agent 都能用"做得很透。

那一下挺泄气的，也认真想过要不要换题。后来我退回去问了自己一句：**同步过去之后呢？**

谁改的？还能不能用？三份副本长得不一样时，哪份是对的？——这些问题，同步工具一个都答不了。

顺着这条线，我给项目改了三次定位：从"包管理器"，到"账本"，最后落到"**Agent 能力治理的控制台**"。

回头看，**定位不是想出来的，是被调研逼出来的。**

### 6️⃣ · 想清楚做什么，更要想清楚不碰什么

我把能力拆成四层：装得上、数得清、说得清、用得住。然后做了个关键决定：**前两层不碰**——那是包管理器的事，别人已经做得很好；我只做第 3、4 层。

还拆了"给谁用"：个人用的人就是决策的人；公司那边，愿意付钱的人根本不写 Skill。所以我加了一个"管理者视图"，但强制它和个人的能力总览是**同一个页面的两种读法**，不做两套。

最后写了十份设计文档，每条需求编号冻结，还强制写了一份"**不做什么**"清单：单点登录、权限体系、多租户……全砍。**想清楚"不做什么"，比想清楚"做什么"更能说明你想明白了。**

### 7️⃣ · 重点来了：1.0 做出来长这样

上面是需求怎么定的，下面讲讲它最后长什么样。整个 1.0 是我跟 AI 结对，一轮一轮对话磨出来的。

**核心是一个 Web 控制台**，进去先看到的是所有 Agent 目录里 Skill 的能力总览：每个 Skill 叫什么、在哪些目录有副本、版本是不是一致、多久没动过——40 多份副本第一次变成了一页看得清的账。

### 8️⃣ · 1.0 的四个版块（对应我踩过的每一个坑）

逐个版块说，每个版块背后都是一次真实的事故：

**① 同步预览（dry-run）**：点同步之前，先告诉你"哪些文件会被写入、哪些会被新建"，确认了才真动手。这个功能后来还救过我一次，第 1️⃣1️⃣ 条讲。

**② 覆盖判据**：只有两边内容逐字节完全一致，才允许覆盖；其余情况一律拒绝，绝不静默盖掉别人的东西。

**③ 删除守卫 + 备份回滚**：删一个 Skill 之前强制备份，随时能回滚。

**④ 管理者视图**：给"不写 Skill 但要对结果负责的人"看的同一页面读法。

### 9️⃣ · 技术上连了哪些东西

学 miss王 报家底：这个系统目前连接的是——

- **本地 git 仓库**当唯一真值（云端不存文件内容，只管协同和分发）；
- **CLI + 常驻服务 + MCP 工具**同一个包，命令行、Agent 调用、控制台走的是同一套数据；
- **Web 控制台**给人看；
- **云端后端**负责登录和团队协作这一层。

同一套内核，两种交付形态：源码形态给自己用，编译形态可以打成各平台的可执行文件直接交付给别人——这也是后面 2.0 的伏笔。

### 🔟 · 做的过程中，一条对我影响最大的铁律

我最早的规则是"状态显示已同步，就允许覆盖"。后来意识到不对：**状态本质是一份缓存，它可能是过期的**。拿可能过期的状态决定覆不覆盖，结果就是静默删掉别人的改动，而且不报错。

崩溃是好事，立刻能发现；**静默错误才是地狱。**

所以最后定成八个字：**无法证明安全时，一个字都不写。**这不是技术问题，是底线——你只能做你能举证的事。

> 🖼 配图：02-覆盖判据.png

### 1️⃣1️⃣ · 这条铁律，在我自己身上应验了一次

写完这条规则没多久，它就在我自己的代码上应验了：验收那天我用 dry-run 检查一个全新的 Skill，界面上显示"已是最新"——**实际上四个目录一个都没写入**。工具对自己撒了谎。

幸好有 dry-run 这层，问题在"预览"阶段就暴露了，没有造成真覆盖。修完之后我把这条也记下了：**工具报"没问题"，和"真的没问题"，是两件事。**

另外两个坑也一起说了：

- 一段校验代码本机怎么跑都对，一到自动构建 Mac 和 Linux 全红——那边的文件名压根不一样。**本机跑不到的分支，造数据也要逼它跑一遍，靠猜一定猜错。**
- 一个依赖只写了"大于等于某版本"，换台新机器一装，装到新的大版本，接口早改了。**没边界的东西，边界一定会来找你。**

### 1️⃣2️⃣ · 2.0 我打算改什么

学完这期课程，我对 2.0 的想法：

1. **在线平台**：把控制台搬到云上，团队共用一套 Skill 账本，走治理预算的那类客户才能真正用起来；
2. **编译发行**：把源码形态编译成 Windows / Mac / Linux 一键安装的成品，交付不再要求对方配环境；
3. **块内合并**：两个副本各自改过时，不再简单拒绝，而是把改动块合并起来让人确认；
4. **把"砍掉的功能"按使用反馈捞回来**：1.0 砍了单点登录、审计日志这些，等有真实用户再决定补哪个。

给同样在做工具的同学提个醒：**砍需求不可怕，砍的时候把"什么情况下捞回来"写下来就行。**

### 1️⃣3️⃣ · 收尾：几点建议 + 一句话

最后给大家四条我这一个多月最实在的体会：

1. **痛点要写成"问题"，不要写成"感受"**——"复制粘贴太累"和"覆盖不可控"会做出两个完全不同的产品；
2. **动手前先查这个位置有没有人占**——被泼冷水花不掉十分钟，但会改掉你后面所有的安排；
3. **把 AI 当"能力很强、但必须被验证的实习生"**——它说"我改好了"，永远当没改；"我写成功了"和"它真的在那"，是两件事；
4. **需求会摇摆，编号让它不再摇摆**——把每条需求写进文档编号冻结，纠结的时候看文档，不重新吵。

如果今天只带一句话走，我希望是这句：**AI Agent 已经把"我用什么方法工作"变成了一种能存在磁盘上的能力。**一个人攒的是方法论，一个团队攒的是流程知识，都是真资产，也都会流失——因为没人说得清它现在是什么状态。

我做的就是这件事：**让人走，资产留下。**
